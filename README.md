# studio

Studio is a Claude Code plugin and TypeScript package for running a small software studio of coding-agent sessions from one control room: a lead session plans work from a board and a crew of role-based sessions carries it out, each in its own sandboxed clone.

Status: 0.16.0, stage (a) (board, planner, capacity, crew launch, guard, merge queue) with stage (a.1) (your own runners, crew credentials, usage limits), stage (a.2) (account blocks, owner-wide limits, pinned crew rules), stage (b) (the Studio board inside Claude Code, pause and resume, push notifications) and stage (c) (capabilities per crew, tiered review, third-party sources, role memory, model per role and item type, change failure rate and time to restore, flaky-test ledger, solutions store), plus components (work per part of the product, with their own WIP limit), an owner-wide overview, a lead heartbeat (`tick`) that carries items from ready to merged, a guided setup (`setup`, `/studio:init`, `/studio:add`), epics with a roadmap generated from the board and an automatic acceptance per epic, pushes to your phone when a decision is needed (ntfy), one automatic rerun for a CI failure outside a pull request, crew costs per item with a daily cap, a weekly lessons review for the lead, and restart safety (`recover`). See [CHANGELOG.md](CHANGELOG.md).

## Quick start

1. Install the plugin in Claude Code:

   ```
   /plugin marketplace add Besser-Sehen-Landshut/studio
   /plugin install studio@studio-marketplace
   ```

   Then restart Claude Code.

2. Once, in your own terminal: `studio setup --link`. One guided step each, skipped when it is done: `gh` installed and logged in; the crew's GitHub token (what it is and which permissions it needs, then hidden input); a Claude account for crews (it asks you to run `claude setup-token` in another tab and paste the token, hidden, with the label `main` unless you type another); and, with `--link`, a small `studio` shim in `~/.local/bin` so the command works in any terminal. It ends with the next step. Before the shim exists, call it by its path: `node <plugin>/bin/studio setup --link` (`/studio:init` prints the exact line, see [Install](#install)).
3. In Claude Code, in your project's folder (a clone of its GitHub repository): `/studio:init`. Claude runs `studio init`, which checks the prerequisites and proposes `.studio/studio.yaml`, explains the result in plain words, writes the files with `studio init --write` after your yes, shows the next steps and adds a first item from your description. Commit `.studio/studio.yaml` and `.studio/board.yaml`.
4. More work: `/studio:add the checkout page crashes when the cart is empty`, or ask in plain words. Claude turns it into `studio add "<title>" --type fix --path "src/checkout/**" --dod "..."`.
5. `/studio` opens the board pane. In a Claude Code session in the project, say "run the Studio lead loop" (skill `studio:studio-lead`). The lead runs `studio tick` every few minutes, which launches crews, collects their work, has every pull request reviewed and merges it.

## Install

```
/plugin marketplace add Besser-Sehen-Landshut/studio
/plugin install studio@studio-marketplace
```

The plugin ships the commands `/studio:init` (set up a project) and `/studio:add` (add work in plain words), two skills (`studio:studio-lead` for the control room, `studio:studio-crew` for crew sessions), the board pane `/studio` and a self-contained CLI. Claude Code puts a plugin's `bin/` on the Bash tool's `PATH` while the plugin is enabled ([plugin components, "Executables"](https://code.claude.com/docs/en/plugins/components)), so Claude simply runs `studio <command>`. Your own terminal does not get it: run `studio setup --link` there once (as `node <plugin>/bin/studio setup --link`, where `<plugin>` is the plugin's folder under `~/.claude/plugins/cache/`). When `~/.local/bin` is on your `PATH` it asks, then writes `~/.local/bin/studio`: a small shell script (a regular file, not a link) whose second line is `# studio-shim v1`, written through a temporary file and a rename, and the launcher's path to `$XDG_CONFIG_HOME/studio/launcher`. The plugin's folder changes with each version and Claude Code marks an old one with `.orphaned_at` and removes it 14 days after an update. The shim uses the cached path only while that file exists and its plugin folder has no `.orphaned_at`; otherwise it runs `claude plugin list --json`, takes the enabled `studio@…` entry (`readFromFolder` when present, else `installPath`), rewrites the cache and runs `node <path>/bin/studio`. So no new `--link` is needed after an update. Without the `claude` CLI on `PATH` it says so and stops. Studio never edits shell files; when `~/.local/bin` is not on `PATH` it says how to add it. It replaces only a file whose second line is exactly the marker, and refuses any other `studio` there (a file of yours, a link). The plugin needs no `pnpm install`: `bin/` loads the committed bundles in `dist-bundle/` (rebuilt with `pnpm bundle`; CI fails if they drift from `src/`).

## Prerequisites

- Claude Code CLI, `git`, and `gh` (authenticated for the control room's own use).
- The `superpowers` plugin: feature and fix items require its skills, and a launch refuses when one is definitely not installed (`studio doctor` shows it; a role can opt out with `skills.denied`).
- Node.js 24 or newer on `PATH` (the CLI and the crew guard hook run on it).
- A least-privilege crew token created by the repository owner (for example a fine-grained token limited to the project's repositories: contents and pull requests read/write, no administration, no merge rights beyond what branch protection allows). Store it with `studio secret set crew-token` (Studio then loads it itself), or export it and name the variable in `studio.yaml` under `crew_token.env`; the variable wins when it is set. Launch refuses without it unless `allow_ambient_credentials: true`.
- Server-side branch protection on `main` and on every ref listed in `crew_allowed_workflow_refs`.
- A platform where Claude Code's sandbox is supported.
- Model authentication for crew sessions in the control room's environment: crew sessions get an isolated `HOME`, so they authenticate with `CLAUDE_CODE_OAUTH_TOKEN` (passed through when set), with the Claude login in `CLAUDE_CONFIG_DIR` (default `~/.claude`), or through a credential provider (see [Crew credentials](#crew-credentials-and-usage-limits)). API billing is off by default: `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are removed from the crew's environment because an API key would otherwise take precedence over `CLAUDE_CODE_OAUTH_TOKEN`. Check on the first launch that the crew session starts and authenticates (`studio status`, the crew log in the state root).
- `sandbox.network_allow` lists every host the crew's shell commands may reach (GitHub for `git` and `gh`, your package registry); everything else is blocked.

## Writing the files by hand

`studio init` writes these files for you. To write them yourself instead, create `.studio/` in the project repository.

`.studio/studio.yaml`:

```yaml
studio: 1
primary_repo: org/app
repos: [org/app]
ci:
  provider: github
  runners: github-hosted
  runner_labels: []
  capacity: { total: 4, merge_max_busy: 3, check_twice_seconds: 30 }
merge:
  strategy: studio-queue
  contract_paths: []
roles:
  builder: { model: sonnet, wip: 2 }
  reviewer: { model: opus, wip: 1 }
sandbox: { network_allow: [github.com, api.github.com, registry.npmjs.org] }
crew_token: { env: STUDIO_CREW_TOKEN }
owner_only: []
deploy_commands: []
crew_allowed_workflows: []
crew_allowed_workflow_refs: []
review_bases: [] # base branches besides the default branch a pull request may be reviewed against
# acceptance: { suites: [{ workflow: .github/workflows/e2e.yml, job: browser }] } # optional: the full suites of an epic's acceptance, see "The acceptance"
```

`.studio/board.yaml`:

```yaml
items:
  - id: APP-1
    title: Add a health endpoint
    type: feature
    role: builder
    repo: org/app
    size: S
    priority: 1
    status: ready
    paths: []
    touches: ["src/health/**"]
    depends_on: []
    dod: ["GET /health returns 200", "test added"]
    plan: docs/plans/health.md
    history: []
```

Then, in a Claude Code session in that repository, ask the lead (skill `studio:studio-lead`) to run the loop, or run it by hand: `studio board`, `studio plan`, `studio launch APP-1`, `studio status`, `studio collect APP-1` (it opens the pull request and adds its review item), `studio launch` of that review, `studio collect` of it, `studio queue add org/app#12`, `studio queue run`. `studio tick` does all of that in one step, as often as it is run. JSON Schemas for editors are in `schema/`.

## init and add

`studio init` runs in the project folder (or `--project <dir>`). Without `--write` it is a dry run: it prints every check and the files it would write, writes nothing and exits 0, also with warnings or failed checks. With `--write` it writes `.studio/studio.yaml` and `.studio/board.yaml` only when no check failed; otherwise it writes nothing and exits 1. It never overwrites: when either file exists it refuses and says to edit it, or to use `setup ci`, `setup stack` and `doctor`. `--json` prints one object with `checks` (`name`, `status` `pass`, `fail` or `warn`, `detail`, `fix`), `config`, `board`, `stacks`, `warnings`, `written` and `nextSteps`.

- **Checks.** git 2.38 or newer, `gh` installed and logged in to github.com (`gh auth status --hostname github.com`, so a stale login to another host does not count), the `claude` CLI, Node.js 24 or newer, a platform where Claude Code's sandbox runs (macOS, Linux, WSL2), and `origin` naming a GitHub repository. A missing crew token, a missing stored Claude account and a missing `superpowers` plugin are warnings with the command to run: `studio setup` (or `studio secret set crew-token` and `studio account add <label>` one at a time) needs the owner in a terminal; the next steps name it once, with the `node <plugin>/bin/studio setup --link` line for a terminal without `studio`. A `.gitignore` that ignores `.studio/` is a warning too: those files belong in the repository, runtime state lives outside it. Each call to `gh` has 15 s and `claude --version` 10 s; one that does not answer in time is a failed check. Steps the checks find done (a stored crew token, a Claude account) are left out of the next steps.
- **What it proposes.** `primary_repo` and `repos` from `origin`; the `ci:` block of `setup ci` (when it has no usable proposal, for example because the runners cannot be read, GitHub-hosted runners, with a `ci` warning, a first next step and a comment in `studio.yaml` to run `studio setup ci`); the stacks of `setup stack`; a builder (`sonnet`, wip 2) and a reviewer (`opus`, wip 1); `sandbox.network_allow` with GitHub, the package registries of the manifests it found and the hosts a detected stack needs (Docker Hub for `docker`). Components: one per direct child of `apps`, `packages`, `services`, `crates` and `libs` that holds a `package.json`, `Cargo.toml`, `go.mod` or `pyproject.toml`, with the folder name as name, a unique id made from it, `primary_repo` and the path `<folder>/**`, and, next to them, a `tooling` component for `.github`, `tooling` and `scripts` when present. A single-package repository gets no components. No component gets a `wip`. Both files are parsed in memory by Studio's own loaders, also in a dry run, which writes no file anywhere; a proposal that would not load is a failed check. `--write` refuses a `.studio` that is a link or a file, creates each file only when it does not exist, and removes what it wrote when a later write fails.

`studio setup [--link]` is the owner's one-time setup, in a terminal (it refuses without one and under `STUDIO_ROLE=crew`). It runs five numbered steps and skips each one that is done: (1) `gh` installed and logged in to github.com, the same check as `init`; when not, it names the fix and stops. (2) The crew token: when none is set, it says what the token is for and which permissions it needs, then runs `secret set crew-token`, checked against `primary_repo` of `.studio/studio.yaml`, else the GitHub repository of `origin`, else a repository it asks for. (3) A Claude account for crews, when none is stored and no credential provider is set: it asks you to run `claude setup-token` in another tab, asks for a label (default `main`) and runs `account add`. The label is asked first at a visible prompt and checked before the hidden token prompt: one that starts with `sk-ant` or is longer than 32 characters is refused as a token typed at the wrong prompt, and so is a token typed at the visible repository prompt. (4) `studio` in your terminal: with `--link` the shim as under [Install](#install), without it a hint when `studio` is not on `PATH`. (5) Notifications to your phone (see [Push notifications](#push-notifications)): `ntfy` (Enter) or `none`; `ntfy` makes a new random topic, prints its subscribe link once with "Install the ntfy app and open this link", waits for Enter, sends a test push and stores the topic only when that push went out (else it says `test push failed: ntfy answered <status>` and stores nothing). `none` or an aborted prompt skips the step. `studio setup --notifications` runs only this step, also when notifications are set up already (a new topic replaces the old one). A failed step stops the run with exit code 1; nothing is ever echoed from a token. It ends with `/studio:init`.

`studio add "<title>"` appends a ready builder item: the next free id with the prefix most items use (else the letters of the repository name, `APP` for `org/app`), `size: S`, a priority after every other item, `--type` (default `fix`; a `feature` needs `--plan`), `--repo` (default `primary_repo`), each `--path` as one of `paths` and `touches` (relative, without `..`), each `--dod` as a line of the Definition of Done (at least one), `--component`, `--plan`. It checks the item against the board schema and the config and saves under the board lock. It prints the item; `missing` names what the planner still needs, `warnings` say that an item without `--path` conflicts with no other item and belongs to no component, and `notes` that a path below `.github/` makes it a CI item. `init` and `add` refuse under `STUDIO_ROLE=crew`.

`launch` refuses while a crew for the same item is still running and deletes a report an earlier run left in a reused clone. `collect` refuses while the item's crew process is still alive and refuses a report last modified before the crew started.

**Tests a crew cannot run.** Crews get no database, no Docker and no network outside the allow list, so CI is the authority for the full suite. A crew runs what its sandbox can for what it changed (the touched package, crate or workspace member, the Definition of Done's tests, lint, format) and lists a command that a missing service kept from running under `not_run_here`, with `command`, `missing` (`database`, `docker`, `network` or `service`) and `reason`; the report stays `done`. A test that ran and failed is `failed`, never `not_run_here`, and an entry without one of those four services refuses the report. `collect` then works as usual: it opens the pull request under the capacity check with a section listing those commands for CI, stores the list on the item (`not_run_here`) and prints how many there are and which services were missing (the commands themselves are crew text and stay on the item and in the pull request). An open pull request of the branch is reused and its text renewed, so the list there is the latest. A review launch writes it to `briefs/<id>.caps/pull-request/not-run-here.txt`. The reviewer names, for each command, the workflow file at the base that defines the job running it, the job, and why that job covers the command (`not_run_here_jobs`, with `command`, `workflow`, `job` and `covers`, one plain line of at most 600 characters). `collect` checks this in the owner's checkout at the pull request's base commit and at its head. The job must be in the file without `continue-on-error`; an `if:` is allowed, because a job it skips reports a skipped check, which never counts as passed. Either the workflow runs on `pull_request`, and its checks are `<job>`; or it is a reusable workflow (`on: workflow_call`) that a job of a `pull_request` workflow calls with `uses: ./.github/workflows/<file>`, and its checks are `<caller job> / <job>` in the caller's workflow. One level only: a job that calls a further reusable workflow, a file called only through another reusable workflow, and a remote `uses: <owner>/<repo>/...@<ref>` are refused, and a calling job may not have `continue-on-error` either. The workflow whose name the checks carry must have a unique name, the check names must be the same at the base and at the head, and the job's definition (with its callers) must be unchanged between them unless the item is a CI item. Every check of the job, each matrix leg ` (<leg>)` included, must have passed on the pull request; skipped, cancelled or missing counts as not passed. The gate does not test whether the job runs the command: task runners (`turbo`, `nextest`, `make`) hide it, so that is the reviewer's judgement in `covers`, which `collect` prints for the lead (`notRunHereJobs`). Otherwise the review item is blocked with a note naming the entry and the rule, and no approval is stored. An approval stores the jobs (`approved_jobs`), and the merge queue checks them again before it merges. An approval still counts only with green checks.

`pause` writes `pause.json` in the state root: `plan` assigns nothing (reason `paused`), `launch` refuses, and `queue run` holds before the next merge. Running crews continue. Any entry under that name counts as paused, readable or not; `resume` removes it. Both commands need a terminal and refuse under `STUDIO_ROLE=crew`. `queue run` also holds while old per-project state files are not yet merged into the owner root.

**Review item.** When `collect` opens or reuses a builder's pull request and moves the item to `in_review`, it adds a review item unless a review naming that pull request is still open (neither merged nor dropped): the next free id with the builder's prefix (`APP-8` after `APP-7`), title `Review of <id> (PR #<n>)`, `role: reviewer`, `type: review`, `status: ready`, the builder's repo, paths, DoD and named components, no touches or dependencies, and the note `review <repo>#<n>`. Its output names it (`review: <id>`). After a fix round the earlier review has finished, so the next collect adds a new one. Review and research items open no pull request and get none.

**`tick`.** One heartbeat of the lead, safe to run every few minutes; the lead skill runs it every 120 seconds. In order: (a) it collects every item in `assigned` or `in_progress` whose crew has ended, and (b) every item whose pull request was held for CI capacity, by the same code as `collect <id>`; then it adds a review item, as `collect` does, for a builder in review that has neither an open review nor a verdict (its review was dropped); before (c) it prepares each epic's acceptance (see [The acceptance](#the-acceptance)); (c) it plans and launches what the plan assigns, through every gate of `launch` (capacity, WIP, component WIP, holds, pause, usage limits, the launch lock), except a review whose pull request this tick opened, which waits for the next tick so CI can report its checks first; (d) it runs `queue add` for every builder in review whose approval is stored, unless a merge failed after that approval; (e) when the queue holds pull requests, an entry a killed run left current, or a `queued` item the queue no longer holds, and no run is active, it runs the queue in the same process (a running queue is left alone); (f) once in 30 days it runs `skills check` and prints `skillsCheck` with the items it added. Before (a) it finishes a launch a crash cut short (see [Recovery](#recovery-after-a-crash-or-restart)), and after (f) it runs the lessons review (see [Role memory](#role-memory)). It prints one JSON object: `collected` (the output of each collect), `reviews` (review items it added), `launched`, `queued`, `merged`, `held` (what waits, with the reason: a held pull request, an approval waiting for green checks, a deferred item, a running queue), `needsLead` (what needs a decision: a report that cannot be read or was rejected, a crew it cannot verify, a request for changes, a blocked item, a failed merge, a refused `queue add`) `reruns` (failed jobs outside a pull request that ran once more on the same commit, see [Flaky tests](#flaky-tests)), `flakyItems` (items it added to find the cause of a flaky job) `recovered` (only when a restart check repaired something), `lessonsReview` and `lessonsJudged`, `epicsReady`, `acceptance`, `epicsDone` and `epicsReopened` (only when there are any) and `errors` (per `item`, or per `phase` when a whole phase failed; a pull request held because the CI read itself failed is listed there too; a push that failed as `notify: <reason>`). One item's or one phase's failure is recorded and the rest goes on, and the JSON is always printed; the exit code is 1 when `errors` holds anything but `notify:` lines. After the phases it pushes what is new in `needsLead`, and every account block, to your phone (see [Push notifications](#push-notifications)). Only refusals that mean "not now" (a busy lock, an item the plan holds back, a pause or block) count as held; anything else is an error. A second tick while one runs does nothing (`held: tick`). The tick refreshes its lock per item and stops before the next phase when the lock was lost; it releases the lock before the queue run, which has its own. `tick` refuses under `STUDIO_ROLE=crew`.

`queue run` is meant to run in the background. It holds a lock in the state root (a second run exits 1 with "queue already running" while the holder lives; the lock records pid, start and a heartbeat refreshed on every step and poll, and is taken over with a note only when that pid is gone or the heartbeat is older than 15 minutes; SIGTERM, SIGINT and SIGHUP release it), picks up PRs added with `queue add` while it runs, and moves each board item as soon as its PR is done. On start it first applies results a previous run recorded but did not put on the board. Right after a head change (branch update or new push) a PR without any reported check counts as pending for 5 minutes, then fails with "no checks reported". `merge.strategy: native-queue` is not supported yet: `queue add` and `queue run` refuse it.

## The Studio board

In the owner's interactive Claude Code session in a Studio project, the plugin shows what Studio is doing. It only displays: it writes no file and starts no process. Crew sessions (`STUDIO_ROLE=crew`), `claude -p` and folders without `.studio/studio.yaml` get none of it.

- **Pane.** "Studio board", in one of three views. Every state has a sign and a word, never a colour alone; titles are cut with "…" by terminal cells (East Asian wide characters and emoji take two), never the id, the sign or the stage. A `state.json` that is missing, unreadable or the wrong shape gives a calm message, never an error.
  - **Work list** (the default): the project and how fresh the state is; one line of counts (`! decisions needed`, `● running`, `◷ waiting`, `✓ today`); a highlighted "Decision needed" block with each lead decision and line for you, and under it what you can say next (a hint always starts with `→` two cells in; wrapped text of an entry goes on four cells in, so nothing else can look like a hint). A lead decision shows a fixed phrase for its kind (`fix limit reached – decide`, `changes requested`, `merge failed`, `crew has a question`, `blocked`, `needs a decision`), never the crew's text; the full line is under "For the lead" in `/studio more`; then each epic with a progress bar and merged of total, its items sorted decision, running, waiting, ready (`<sign> <id> <title> <stage> <time in stage>`, a waiting item with its reason on a second, dimmed line, done items folded into `✓ n done`); then "Without epic" the same way; and one footer line with CI use, the median lead time and `/studio more`. Empty sections are left out. Example, 60 columns:

  - **Pipeline** (`/studio pipeline`): the first decision, then the columns READY, BUILDING n/wip, REVIEW n/wip (the WIP limits of the build roles and of the reviewer), QUEUE and TODAY with a card per item (sign and id, short title, epic code such as `E3`, time in stage, and what it waits for); a full column says `⚠ full`, blocked work has a row of its own below. A pane too narrow for five columns (about 60 to 70 cells), or whose columns cannot hold the sign and the longest id, draws the work list instead. Example, 72 columns:

    ```text
    Studio · shop                                          updated 1 min ago

      → say "show APP-15"

      E4

      APP-15 fix limit reached – decide (E3)

    ```

  - **Details** (`/studio more`): the earlier sections: the crew with a state per item (`working`, `waiting`, `blocked`, `stopped`, `crashed`, `done`), grouped under a heading per component when the project has components (see "Components"), the merge queue, CI use and the merge rule, the lines for you, the lead's full lines ("For the lead"), the state of the push builds on `main`, the last seven days merged and deployed, and usage per label. A `state.json` written by a Studio before 0.11.1 has no work list and draws this view.
  - **States.** No open item and nothing merged today: "No work yet." with an example of what to say. While paused: "Paused since HH:MM. Nothing starts or merges; running crews finish. → /studio resume". When the state is older than 10 minutes: "Last update n min ago. Is the lead loop still running? → say "start the Studio lead loop"". Paused and stale are shown above the view, not instead of it.
- **What it shows comes from `studio state`.** `state.json` carries every item that is not merged or dropped (reviews aside: their builder shows the stage) with its stage (`ready`, `building`, `pr_held`, `review`, `queued`, `blocked`), epic, components, the time it entered that stage and what it waits for (`ci_capacity` with busy, total and the merge limit, `checks_pending`, `review_pending`, `queue_held`, `queue_position`, `held`, ...); the latest tick's lead list (`needsLead`, each with a code, a short reason in Studio's own words, the full line as `detail`, and a next step to say; an item that moved after that tick is left out); the WIP limits; the merges of today with their items and epics; the project name (the repository name of `primary_repo`); and the pause with its time on the owner's clock (the zone of `crew_label_limits.timezone`, else the system zone, the same one that decides "today"). `studio tick` keeps its lead list and holds in `tick.json` in the state root for this; a tick that did not run, lost its lock or had a phase fail keeps the last good record; nothing else runs in the background. Reasons and next steps are English data; the pane translates what it has words for.
- **Language.** The displayed text is English or German; commands stay English in both. The pane follows `/studio lang de` or `/studio lang en` when set (kept in the plugin's store; `/studio lang auto` clears it), else Claude Code's `language` setting (German when it names German, for example `"language": "german"`), else the locale (`LC_ALL`, `LC_MESSAGES`, `LANG`, German for `de_*`), else English. The status line and the toasts follow it too.
- **Status line.** `● N working · N waiting · N queued · CI x/y · for you: n`, with `· paused` while paused.
- **Toasts.** One toast per refresh, only for lines that are new since the last one shown: a line for you, an account block, a red build on `main` and a crew that crashed and was not healed. A `usage-limit` line toasts once while it stands. Titles have control characters stripped.
- **Commands.** `/studio` opens the pane and always places it. `/studio list`, `/studio pipeline` and `/studio more` switch the view and open the pane; the choice is kept in the plugin's store for the next session. `/studio lang de|en|auto` sets the language. `/studio status` prints the status line text. `/studio pause` and `/studio resume` only print the terminal command to run, because pausing needs a terminal (`studio pause`, `studio resume`).
- **Where it reads.** The plugin reads `state.json` and `pause.json` from the project's state root (see below), not from `.studio/`, every 10 seconds. At session start it opens the pane by itself only when the terminal is wide (about 144 columns); in a narrower one it waits undrawn until you run `/studio`.
- **Keeping it fresh.** Only `studio state` writes `state.json`. The lead's heartbeat (`studio status` and `studio state` every 120 s, and `studio tick` in a loop of its own, see the lead skill) refreshes it and also reads crew logs, so an account block stops crews at most one heartbeat (120 s) after the event. Without a running lead nothing refreshes the board and nothing stops crews: a project with no lead is swept for a block only when another project reconciles.

`pnpm test:mod` runs the mod's tests with `claude plugin test`; it needs the `claude` CLI and is not part of CI.

## Components

A product often has parts that are developed and released on their own: an API server, a desktop app, an agent, a web app in a second repository. A project (one control room, one `.studio/`) lists them under `components:` in `studio.yaml`; projects that have nothing to do with each other stay separate control rooms. Without `components:` nothing changes.

```yaml
repos: [org/app, org/web]
components:
  - { id: api, name: API server, repo: org/app, paths: ["server/**", "shared/**"], wip: 2 }
  - { id: desktop, name: Desktop app, repo: org/app, paths: ["desktop/**", "shared/**"], wip: 1 }
  - { id: agent, name: Agent, repo: org/app, paths: ["agent/**"] }
  - { id: web, name: Web app, repo: org/web, paths: ["**"] }
```

- **Fields.** `id` (`^[a-z][a-z0-9-]{0,31}$`, unique), `name` (one line), `repo` (one of `repos`), `paths` (globs, at least one, same rules as `skills.when`) and an optional `wip`. The list, when present, holds at least one component.
- **Which component an item belongs to.** A board item may name one with `component: api`, or several with `components: [api, desktop]` for cross-cutting work; not both. An id the config does not know refuses the board, except on merged and dropped items, which keep the id they had after a component is removed. An item that names none belongs to every component whose `repo` is the item's repo and one of whose `paths` globs matches or may overlap one of the item's `paths` or `touches`. Overlap works as for touches in the planner: by the fixed part before the first wildcard, so a bare directory `server` stands for `server/**`, `server/**` overlaps `server/src/**`, and a glob without a fixed part (`**/*.ts`) overlaps every component of its repo. It errs towards counting an item against a component. In the example, an item touching `shared/**` is cross-cutting (api and desktop); one touching only `docs/**` belongs to none. An item with no `paths` and no `touches` belongs to no component unless it names one.
- **WIP.** `wip` is the most items of that component in `assigned` or `in_progress` at once, on top of the role's `wip`. A cross-cutting item counts against each of its components. `plan` defers an item over the limit with the reason `component <id> wip full`, so no component takes all crews.
- **Where it shows.** `studio board` and `studio status` get a component column, `studio board --component <id>` lists one component's items, `studio plan` names the components of each assigned item, and the pane groups the crew by component (cross-cutting work under "cross-cutting", the rest under "no component").

`studio overview` lists every project of this owner from the state base (one line per state root, the owner root left out): its name, items per status, running crews and queued merges. It reads only, writes nothing, and reports a state root it cannot read in full in its last column, with what it could read. A root whose `marker.json` names a project that does not belong to that root is reported as inconsistent and not read further, and a `board.yaml` that is a link is not read. Names and errors are printed without control characters. Like `pause`, it needs the owner in a terminal and refuses under `STUDIO_ROLE=crew`.

## Epics and the roadmap

An epic is a larger piece of work the owner asks for: a goal, the lines it is accepted by, and the items that build it. The board is the truth: epics live next to the items in `board.yaml`, and `ROADMAP.md` is rendered from it. A board without `epics:` loads and saves as before.

```yaml
items:
  - {
      id: APP-4,
      title: Invoice form in the checkout,
      type: fix,
      role: builder,
      repo: org/app,
      size: S,
      priority: 4,
      status: ready,
      dod: [a test covers it],
      epic: E-1,
    }
epics:
  - id: E-1
    title: Pay by invoice
    status: open
    goal: Customers can pay by invoice
    acceptance:
      - an invoice order reaches the backend
      - the customer gets the invoice by email
```

- **Fields.** `id` (`E-<n>`; `studio epic add` takes the next free number, a dropped epic's number is not reused), `title` (one line), `goal` (one line of plain text), `acceptance` (at least one line), optional `components` (ids from `studio.yaml`, checked like an item's while the epic is open or accepting), `status` and `history` like an item's, and `imported_from` and `notes` after an import. An item names its epic with `epic: E-<n>`; the epic must be on the board, and only a merged or dropped item may keep a dropped epic.
- **Status.** `open` until every item of the epic is merged (at least one; dropped items do not count), then `accepting` (shown as "in acceptance"): every move of an item applies this rule, and `studio tick` lists accepting epics under `epicsReady`, each with its acceptance item (the key is left out while none is accepting, so a tick without epics prints what it printed before). New work added to an accepting epic takes it back to `open`, shown as `reopened` once it has been accepting. `done` comes only with a green acceptance (see below), or from an import. `epic drop` sets `dropped` and is refused while the epic has open items; an acceptance that waits is dropped with it, one that runs refuses.
- **Commands.** `studio epic add "<title>" --goal "<text>" --acceptance "<line>"...` prints the new id; `studio add ... --epic E-1` attaches an item; `studio epic list` shows each epic with its items by status and merged of total (`--json` too); `studio board --epic E-1` lists its items; `studio epic edit E-1 --acceptance "<line>"...` replaces the acceptance lines (or `--title`, `--goal`). Adding, editing and dropping epics, and writing the roadmap, are refused under `STUDIO_ROLE=crew`.
- **Where it shows.** `studio board` gets an epic column and, below the items, each epic with its stage (`open`, `in acceptance`, `done`, `reopened`), merged of total and its acceptance item; `studio epic list` and `epic show` show the same. The pane lists the open and accepting epics, and those done in the last day, with their progress and stage above the crew working on their items.
- **The roadmap.** `studio roadmap` prints markdown: the header `<!-- generated by studio roadmap; edit the board, not this file -->`, one line per epic in id order, `- [ ] E-3 — <title> (<merged>/<total>)` (`[x]` done, `[~]` accepting, with items in progress, or imported as in progress and without items yet; `· in acceptance` or `· reopened` after the count; dropped epics left out) with its goal and acceptance as nested bullets, then the open items in no epic (review items left out, merged ones counted in one line). The same board gives the same text. `--write` writes it to `ROADMAP.md` (or `--out <file>`) through a temporary file and a rename, and refuses a file that does not start with the header unless `--force`. The target must stay inside the project by its real path (a linked folder that leads out is refused, and so is a target that is a link), not below `.studio/` or `.git/`, and `--force` takes only a `.md` file. Never edit the file by hand: edit the board and write it again.
- **Importing a hand-written roadmap.** `studio roadmap import ROADMAP.md` reads lines like `- [ ] Phase 4 — Search`, `- [~] Phase 5 – Checkout @claim:session-b` or `- [x] **Phase 3: Cart rewrite**` (separators `—`, `–`, `-` or `:`, bold markers and trailing `@` tags dropped) and plans one epic per phase not imported yet. The file must be a regular file inside the project, not a link, at most 1 MB with at most 500 phases; a line longer than 2000 characters, a phase number that is none, or a phase that would make an invalid epic is listed under `skipped` with its line and reason, and the rest goes on. Each epic gets the title up to the next separator, the goal what follows (else the title), acceptance `imported from ROADMAP: define acceptance`, `done` for `[x]`, `open` otherwise (for `[~]` with the note `in progress at import`, plus `(claim: <session>)` from an `@claim:` tag), and `imported_from: "ROADMAP.md#Phase <n>"`, so a second import skips it. A phase number that comes twice in the file is imported once and the repeat is listed as skipped. It prints the plan and writes nothing; `--write` adds the epics. It creates no items. Then give each imported epic its acceptance lines with `studio epic edit`, compare `studio roadmap` with the hand-written file, and only with nothing skipped and the owner's yes replace it with `studio roadmap --write --force`.

### The acceptance

Each pull request of an epic passed its own gate before the merge. What none of them can show is checked once the epic's items are all merged: the full E2E and browser suites on main, which no crew sandbox can run, and a review of the epic's combined diff for how the pull requests fit together and for gaps against the acceptance lines. It runs without the owner.

- **The item.** An epic that is `accepting` when 0.16 first ticks (also one from an older Studio) gets its item on that tick. An imported epic whose acceptance is still the import's placeholder (`imported from ROADMAP: define acceptance`) gets none: the lead hears `define acceptance first` until `studio epic edit` replaces it. When an epic becomes `accepting`, `tick` adds one acceptance item: `Acceptance of E-<n>: <title>`, `type: review`, `role: reviewer`, `triggers: [epic-end]` (so the full scans run), the epic's acceptance lines as its Definition of Done, `epic: E-<n>`, and the notes `acceptance E-<n>` and `acceptance-state: <hash>`. The hash names which items the epic had; the same state never gets a second acceptance item, also across ticks and crashes (the item is added under the board lock). Dropping the item asks for a fresh one. The acceptance item is no piece of the epic: it does not count in merged of total and does not reopen it. One that has not started (ready or blocked) is dropped by the next tick when its epic moved on (new work joined, or the epic is no longer accepting), with the note `superseded: E-<n> changed before it started`. It runs in the repository most of the epic's pull requests are in; pull requests in another repository are listed to the reviewer as not in its checkout.
- **The full suites.** Name them in `studio.yaml`: `acceptance: { suites: [{ workflow: .github/workflows/e2e.yml, job: browser }, ...] }`: the workflow by its file, never its display name (two workflows can share one, and a change can rename it), and the job name (letters, digits, spaces and `. _ - ( ) / :`; each matrix leg `<job> (<leg>)` counts). Studio finds the workflow's id with `gh workflow list` and its runs on the commit by that id. Every run of the workflow on the commit counts: one red run makes the suite red whatever else passed, and a file GitHub lists for two workflows fails closed. Without `acceptance:` every workflow that ran on the main commit counts, named by its file, except one whose runs there were all skipped (a path filter): that checks only what CI ran on that commit, which may not include the E2E suites (a path-filtered E2E workflow after a docs-only merge), so name the suites where you have them. A commit with no run at all is never accepted as green: after 10 minutes on it (or on a newer head) the lead gets `no CI run on main at <sha>; set acceptance.suites ... or rerun CI`. `acceptance: { suites: [] }` is the explicit choice of a repository without CI: the acceptance is then the review alone. Before anything launches, `tick` reads the suites on the head of the default branch and keeps waiting on that commit (`held`: `acceptance waits for <suite> on main at <sha>`) until all of them have completed; then it pins the commit with the note `acceptance-main: <sha>`, and only then does the plan launch the item (until then it is deferred with `ci pending`). A failed suite is a result, not a wait. A configured suite with no run on the commit is started once with `gh workflow run <workflow id> --ref <branch>` after 10 minutes (CI may still start it); the start is recorded in `acceptance-runs.json` in the state root before gh runs, so a crash never starts it twice; while that file exists but cannot be read, nothing is started and the lead hears of it. A suite cancelled or skipped there, or with no run at all, gives way to a newer head of main. `needsLead` gets a start GitHub refused, a started suite with no run after 30 minutes, and without configured suites a run with no result on an unchanged main.
- **The review.** A reviewer crew loads main at the pinned commit and gets, as data files beside its brief, the suite results and each pull request of the epic with its merge commit and files (titles are crew text). It builds the combined diff from the merge commits, runs the analyzers of the epic-end full scan over it (diff review, spec check against the acceptance lines, security, performance, bugs, dead code, the similar-bug scan; no mutation probe is owed), and reports `verdict`, `accepts: E-<n>`, `head_sha: <the pinned commit>` and `findings` (one line each, at most 20; a longer one is cut, a tab or line break becomes a space, so a finding never rejects the report). A done report without a verdict is rejected. The same report and collect path as a review: `collect` holds the report to what the launch recorded (the epic, its state, main and the suites, never taken from the report), refuses an approval with an analyzer missing, an owed one skipped, a `green:` probe or a finding, and refuses changes requested without a finding.
- **The result.** In the same board save as the move of the acceptance item: each finding becomes a `fix` item for a builder in the epic, `E-<n>: acceptance finding <k> of <acceptance item>`, with the Definition of Done "Fix the finding recorded in the acceptance report (the data file of this brief); a test shows it" and the note `finding of <acceptance item>`. The finding itself is crew text: it is kept in the item's `finding` field and reaches the builder only as a data file beside its brief (`acceptance-finding.txt`, marked as data), never in a title, Definition of Done or note. Each failed suite gets one item: `E-<n>: make the suite "<workflow file> / <job>" pass on main` for a configured suite, `E-<n>: failed suite <k> of <acceptance item>` with the name as data otherwise (note `suite: <hash>`, one open item per suite). Fix items get the acceptance's paths without `.github/` ones, so none is a CI item. From the third round that found work on (changes requested or a failed suite, whatever the verdict), the new items are added `blocked` with the note `acceptance limit reached: ...`, `tick` lists the epic in `needsLead` (`acceptance limit reached for E-<n>`) and in `epicsReopened` with `held: true`: the lead decides. New items take the epic back to `open` (`reopened`); once they are merged it is accepting again and gets its next acceptance. Without new items an approval makes the epic `done`, with `accepted: { item, sha, at }` on the epic, if it is still accepting with the same items it was launched for; otherwise the result is `superseded` and the epic's next acceptance follows. `collect` prints `acceptance: { epic, result: done | reopened | superseded, findings }`; `tick` lists `epicsDone` and `epicsReopened`.

## Capabilities

`capabilities/INDEX.yaml` says, per role, item type, stack, phase, changed path, risk tag and trigger, which skills a crew must use or may use, which analyzers a reviewer runs and which knowledge files apply. The denied list wins over everything. At launch Studio works this out, names the skills in the brief (only a named skill is used reliably) and copies only the matching files beside the brief; a crew never gets the rest. A required skill that is definitely not installed refuses the launch; an optional one reads `skipped: skill not installed`. A malformed index refuses the launch.

- **Stacks.** `studio setup stack` reads manifest files in the root and one level of `apps`, `packages`, `services`, `crates` and `libs` (the folders `init` proposes components from), proposes `stacks:` for `studio.yaml`, and stores it with `--write`. It never opens `.env` and never follows a link.
- **Per item.** Optional board fields: `risk` (`ui`, `landing`, `auth`, `security`, `data`, `migration`), `triggers` (`epic-end`, `release`), `model`. Roles can add `skills.when` entries with `paths`, `item_types`, `required` and `allowed`. A glob is limited in length, wildcards and braces (no nested braces); one over the limits is refused in a config file.
- **Model.** `roles.<role>.model`, `roles.<role>.types.<item type>` for another model per item type, and `escalate_to`. `studio escalate <id>` sets the item's `model`, which wins; the status stays as it is.

## Review

A review item has `type: review` and `role: reviewer` together, a Definition of Done and the note `review <owner/repo>#<n>`; a launch refuses otherwise. Studio reads the pull request and writes a routine into the brief, by tier.

- **Small:** at most 400 changed lines outside markdown. Diff review and spec check.
- **Large:** more lines, a risk tag `auth`, `security`, `data` or `migration`, a security-sensitive change, or a file list it cannot read completely. Adds performance, and accessibility, design and motion analyzers where they apply.
- **Security always** when a changed path concerns auth, sessions, logins, passwords, permissions, API routes, middleware, migrations, DB schema, signup, reset, OTP, upload, access policies, workflows or local actions, and when a changed file matches a glob of `merge.contract_paths` (contracts and migrations of the project). A file list that cannot be read, or a path with a control character, counts as such a change. Spellings are matched case-insensitively.
- **Later rounds and epic end.** After an earlier `changes_requested` the similar-bug scan runs; `triggers: [epic-end]` or `[release]` add the full scans.

The spec check runs last and alone and holds a mutation probe: break the guarding line in the checkout, the named test must go red, restore. An approval is refused when the test stayed green, and in the large tier or for a fix when the probe did not run.

### The gate on every pull request

Every pull request gets the full gate before the merge, and its depth scales with size and risk. The brief names each mandatory analyzer with one line on why, and each gate analyzer it leaves out with why (`- security: not run: no risk tag, no security-sensitive or contract path changed`). A small pull request that changes only docs gets diff review and spec check, no security.

| Analyzer     | Owed when                                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| diff review  | every pull request                                                                                                                 |
| spec check   | every pull request; its mutation probe must run in the large tier, for an item of type `fix` and in a fix round                    |
| security     | a risk tag, a security-sensitive path, a path under `merge.contract_paths`, a file list that cannot be read, epic end or release   |
| similar bugs | after a fix round; in the first round when diff review reports `findings` (it then looks for those patterns in the whole codebase) |
| performance  | the large tier                                                                                                                     |

The record written at launch holds what is owed (`mandatory`, `onFinding`, `probeRequired`). `collect` refuses an approval while an owed result is missing or reads `skipped:`, and names them all at once (`approval refused: no result for spec-check; mandatory analyzer skipped: similar-bugs`). The other analyzers may be skipped with a reason; the output lists them under `skipped`.

A launch draws a random report file name, known only to that crew's brief, and `collect` reads only that file, so a report shipped inside a pull request never counts. A review report also carries `head_sha`, which must be the pull request's head at collect.

`collect` holds a finished review to the record written at launch (`briefs/<id>.caps.json`): `reviews` must name the recorded pull request, for every verdict. An approval needs a result for every listed analyzer (`pass`, `findings` or `skipped: <reason>`) and `mutation_probe`, and cannot skip an owed analyzer (above). Output lists skipped analyzers by id, also those launch could not provide; reasons stay in the report. A missing analyzer source reads `skipped: <reason>`, never a pass.

**What the reviewer gets as data.** In the sandbox a reviewer may not reach GitHub with `gh`, so the launch reads the pull request outside the sandbox and writes its files to `briefs/<id>.caps/pull-request/`: `description.md` (title and text, marked as crew text to read as data), `checks.txt` (each check and its state at launch), `files.txt` (the changed files) and, when the builder listed any, `not-run-here.txt`. The brief names the files, never their content. A review launch refuses when no board item holds the pull request, since the approval is stored there; `studio link <id> <repo>#<n>` (owner, terminal) ties a pull request opened by hand to its item after checking repository, fork and branch `studio/<id>`. An approval counts only while the checks are green: `collect` refuses it while any check fails, is cancelled or still runs, and nothing moves until it is collected again. The reviewer reads CI workflows at the base (`git show origin/<base>:.github/workflows/<file>`), never in the pull request head, which the crew could have edited. A change under `.github/` (workflows, actions) blocks the approval unless the item holding the pull request is a CI item that declares the changed path in its `paths` or `touches`; a symbolic link there always counts. Launch reads the change in the owner's checkout (`git diff --name-only --no-renames <base>...<head>`, any case, symbolic links at `.github` or below count), and a change it cannot read counts as one; `collect` then refuses the approval.

Fix limit: 3 attempts per finding (`finding_attempts`), hard stop after 6 rounds of requested changes. Reaching it blocks the builder item with a note, and `queue run` merges only an item that is `queued` on the board at that moment.

## Third-party sources

Nothing with an unknown or copyleft licence is copied into this repository; MIT and Apache-2.0 content only with its notice (`capabilities/NOTICE.md`). `capabilities/SOURCES.yaml` lists every source with its licence. `studio setup sources` fetches the referenced ones below the owner root with hooks and links off; nothing from them ever runs.

Vendored content is watched upstream: a vendored source lists the upstream files it adapts under `watch:` in `SOURCES.yaml` (the platform files of `ehmo`), and `setup sources` and `sources check` fetch and judge those files like the `reads` of a referenced source; nothing of them reaches a crew. A source whose licence is `unknown` (today `better-auth`) is not used until it is cleared: `setup sources` and `sources check` leave it out (`notUsed` in the JSON), and a brief never copies it; its row reads `skipped: licence unknown`.

`studio sources check` holds one rule. `setup sources` records a sha256 for every file the source's contract reads and for its licence files. `fits`: every one of those files is byte-identical to its recorded hash. `unclear`: one changed, is new or is missing, or something could not be read; the output names the files, and a person or the lead reads the diff. `conflict`: a licence file is missing or changed. Files outside the contract are not judged, because they never reach a crew. A brief copies a fetched file only when it still matches its hash; otherwise the row reads `skipped:`. It installs nothing, not even a `fits`. `studio sources apply <id>` judges the candidate again and adopts only a `fits`; there is no command that adopts a held update.

## Skills and updates

**Only the skills the matrix names.** A crew gets exactly the skills `capabilities/INDEX.yaml` and the role's `skills:` name for its item: required, offered and required-when-installed, plus `studio:studio-crew`. Every other skill installed in the crew's Claude config dir (user skills, plugin skills and commands, from the install paths in `installed_plugins.json` and from the plugin cache) is denied in its session settings as a `permissions.deny` rule `Skill(<name>)`, together with the denied list. A plugin skill is allowed only by its full `<plugin>:<name>`; a bare name in the matrix allows only a skill without a plugin, and the matrix writes every plugin skill with its plugin (a test holds it to that). An offered skill counts as installed only under that exact name. A skill is named by the `name` of its `SKILL.md` front matter, read with the YAML parser as a strict subset: exact `---` lines at the start, a map with plain string keys and unique keys, no anchors, aliases, tags or merge keys anywhere, and `name` a plain top-level string; other keys may hold nested blocks such as `metadata:`. Its directory name is denied as well. A command below `commands/` is named by its path with `:` (`commands/db/migrate.md` is `db:migrate`), and its bare file name is denied as well. It fails closed: an installed skill or command whose name no rule can hold (spaces, brackets, a leading dot), a `SKILL.md` that cannot be read for sure (two `name` keys, a list, no closing line, no YAML, blank lines before it, over 256 KiB), or a command entry Studio cannot map (another extension, a link, an unreadable folder) refuses the launch, naming where it sits. Claude Code has no skill allowlist that holds under `--permission-mode bypassPermissions`: allow rules have no effect there, deny rules hold in every mode (https://code.claude.com/docs/en/permission-modes), so the list is built from what is installed. Skills bundled with Claude Code itself are not on disk: they count as present, and each one the brief does not name gets a deny rule from a fixed list (the "Skill" entries of https://code.claude.com/docs/en/commands, plus `security-review`). The crew settings also set `syncClaudeAiSkills: false` and `syncClaudeAiPlugins: false`, so nothing synced from a claude.ai account reaches a crew. A missing required skill refuses the launch, as before. A missing offered skill does not: the brief names it under "Offered but not installed", and `collect` prints it under `skillsMissing`.

**Pinned plugin versions.** `plugins:` in `.studio/studio.yaml` pins each plugin crews need at one exact version, over the defaults (`superpowers@superpowers-marketplace` and `studio@studio-marketplace` at Studio's own version). studio.yaml is repository content, so it can only set versions: it cannot change the marketplace of a default (that refuses `setup-plugins`, the launch and the skills check), and it cannot add a plugin or marketplace of its own. Extra plugins come from `allowed_plugins` in the owner config, outside every repository, with their marketplace; one studio.yaml names without that is never installed, and `setup-plugins` and `doctor` say so. A change of `.studio/studio.yaml` in a pull request always gets the security analyzer.

```yaml
# .studio/studio.yaml
plugins:
  - { name: superpowers@superpowers-marketplace, version: 7.0.2 }
  - { name: pg@aiguide, version: 1.2.0 }
# owner config ($XDG_CONFIG_HOME/studio/config.yaml)
allowed_plugins:
  - { name: pg@aiguide, marketplace: "https://github.com/<owner>/<repo>" }
```

`claude plugin install` takes no version (https://code.claude.com/docs/en/plugins/cli-reference), so `studio account setup-plugins` adds the marketplaces, installs the plugins, reads `claude plugin list --json`, runs `claude plugin update` once for a plugin at another version, and fails naming both versions when it still differs. Claude Code records each install with its version in `<config dir>/plugins/installed_plugins.json` (https://code.claude.com/docs/en/plugins/loading); a launch reads it and refuses while a pinned plugin is installed at another version. `studio doctor` shows each pin with the installed version.

**`studio skills check`.** Compares each pin with what its marketplace offers (`claude plugin marketplace update` and `claude plugin list --json --available` in the crew config dir, nothing installed) and runs `sources check`, the watched upstream files of vendored content included. Versions from marketplaces and from the CLI are untrusted: one that is not a plain version (`^[0-9A-Za-z][0-9A-Za-z.+-]{0,63}$`) is dropped and named under `problems`, never written into a title, note or output, and table output has control characters replaced. Each update becomes one board item, a `chore` for a builder: `Update <name> to <version>` or `Review upstream change in <source>`, with a Definition of Done to compare the change, run the stored skill scenarios in `test/skills/` against it where they apply, propose the adaptation of Studio's own rules, and adopt only after a green review. An update already on the board (by its note `skills-update: ...`, in any status) gets no second item. A security update gets priority 0: one whose marketplace entry names an advisory (`security`, `CVE-`, `GHSA-`, `vulnerability`, `advisory`, or `security: true`), or one the lead names with `--security <name>`, which also raises an open item to 0. A source that cannot be judged (not fetched, upstream unreadable) is listed under `problems`, not as an item. `tick` runs the check at most once in 30 days per project (`skills-check.json` in the state root holds the last run) and lists what it added under `skillsCheck`; `skills check` alone says when it is due next, `--now` and `--security` run it at once.

## Role memory

`.studio/roles/<role>.md` holds the role's brief and a `## Lessons` section of at most 40 lines. `collect` stores a report's lessons as proposals in the state root (`lessons.json`), with the report and the pull request of that run as evidence; only `studio lessons accept <n>` moves one into the file, which the lead then commits. Lessons are crew text: `lessons list` says so and shows each with its age, source item and evidence, each is reduced to one plain line (control and format characters, escape sequences and leading markup removed), `accept` copies only that line into the file, never the evidence, and a brief shows them in a labelled data block apart from the role's instructions. Nothing in a proposal is ever run.

**Lessons review.** Once a week `tick` (or `studio lessons review --now` at once) bundles what is pending: proposals of one role whose text is the same once case and punctuation are ignored become one, the oldest, which keeps the others' items and evidence (`alsoFrom`). Then each role with pending proposals and no open review gets one board item, `Review crew lessons for <role> (<n>)` (`chore`, role `researcher`, notes `lessons-review: <role>` and the proposal numbers, never their text). Its Definition of Done: judge each proposal against the role file and its evidence, accept the ones that hold beyond their one run, drop the rest with `studio lessons drop <n> --reason "<one line>"`, keep the Lessons within 40 lines (`lessons prune` first when full) and commit the role file. `lessons accept` refuses a crew, so the item is the lead's: the planner never assigns it (`held` with `lead work: ...`) and it is not pushed to the phone. `tick` lists open ones under `lessonsReview` with how many proposals still wait, and closes an item, as `merged` with the note `judged: <a> accepted, <d> dropped`, once each of its proposals was accepted, dropped or folded into another; that tick prints it under `lessonsJudged`. Verdicts and reasons stay in `lessons.json` (`judged`, the last 500).

## Recovery after a crash or restart

After a crash of the lead session or a restart of the machine, the next `studio tick` picks up the thread without starting anything twice, and `studio recover` runs the same checks explicitly, with more of them, and prints what it found (`findings`, each with `check`, `subject`, `found` and, when it acted, `did`) and what needs the lead (`needsLead`). `studio recover --dry-run` only reads. Both are safe to run again: a second run finds nothing left to do. `recover` refuses under `STUDIO_ROLE=crew`.

- **Locks.** Every lock (`tick`, `queue.run`, `queue.json`, `board`, `ci-reruns`, `lessons`, `costs`, `crew` in the state root; `launch`, `limits`, `blocks`, `push`, `notify`, `migrate` in the owner root) records the holder's pid, its process start time and a heartbeat. A lock counts as stale when its pid is not running, or when the pid now belongs to another process (the start time differs, as after a reboot); the next taker breaks it with a note. A live holder whose start time matches is never broken, however long it has been silent; one whose start time cannot be read (or that recorded none) is taken over only after a very long silence (four times its usual limit, at least an hour). A lock without a pid goes by its heartbeat. A queue run whose lock was taken over anyway stops before its next step, and a launch beats its lock before and after the clone. `recover` lists every lock that is held (`silent <n> min, holder alive` when it has been quiet) or stale and breaks only the stale ones. `crew.json` is changed only under `crew.lock`, so a launch, a stop and a reconcile in different processes never lose each other's records. It also removes what a cut-short write or lock break left at the top of a state root: a `*.tmp` file whose writer is gone, a `*.stale` file older than a minute.
- **Launches.** The crew record with its pid is written right after the start, before anything else. A launch cut short before the start leaves the item `ready`, and the next tick launches it once (the clone is reused or made again). One cut short after the record leaves a `ready` item with a crew started for it: `tick` moves it to `assigned` with that crew, as the launch would have, and never starts a second one. This repair waits while any launch holds the launch lock, and while a record without its start time is younger than 2 minutes (a launch may still be writing it); a launch that finds its item already moved to its crew counts as done. A record whose start time was not read yet counts as unverified: no signal, the lead decides.
- **Crews.** A crew that ended while nobody watched is collected by the next tick when its report holds; without a report it goes to `needsLead` (`studio stop <id> --requeue`) and is never relaunched by itself. An `assigned` or `in_progress` item without any crew record goes to `needsLead` too: to drop it when its log is quiet, or to look by hand first when the log was written in the last 30 minutes. `collect` stores a report's lessons before it moves the item, so a failed move loses none.
- **Merges.** The queue records each step before it runs it. A run killed after GitHub merged but before the board moved resumes at that step; it reads the pull request first and books it as merged, never merging twice. A result recorded but not put on the board is applied by the next run. An item in review that the queue already holds (`queue add` stopped between the queue entry and the board) is moved to `queued` first. A `queued` item the queue holds neither as entry nor as result goes to `needsLead`.

## Metrics and learning

`studio metrics` adds change failure rate (deploys followed by an incident, over deploys; `null` without a deploy), median time to restore and open incidents to lead time and deploy frequency, from `studio deploy record` and `studio incident open|resolve`. An incident counts against the latest deploy before it, once per deploy.

`studio flaky record <test> <sha> pass` counts a test that failed and passed on a rerun; `fail` is a real failure and is not recorded, because nothing is retried into green. `studio flaky` lists the worst first, for a scheduled fix item.

`studio metrics` also prints `costs`: today's cost of this project's ended crew runs (`today`), and per item and per epic the runs and cost stored on the board (see "Costs").

### Flaky tests

When the merge queue, or `collect` waiting for green checks behind an approval, sees a failed check, Studio asks whether the failure lies outside the pull request. It does when every failed check is an Actions job of the pull request's repository whose job runs in a directory of its own (`defaults.run.working-directory` of the job or its workflow, read at the pull request head; no step with a working directory of its own), no changed file of the pull request lies in that directory, at the repository root or in `.github/`, and no path of the item reaches into it. Anything else, a cancelled check, a commit status, a job without a directory or more than 3000 changed files, counts as related, and the pull request fails as before. Names are job-level: `<workflow> / <check>`, since `gh pr checks` names no single test.

Nothing is judged while any check of the pull request still runs. An unrelated failure then gets one rerun of its failed jobs on the same commit (`gh run rerun <run> --failed`), once CI is under the merge capacity (`merge_max_busy`, read twice like a merge); until then, and while the rerun runs, the queue waits. The commit is recorded in `ci-reruns.json` in the state root before the rerun starts, so it never gets a second one, also after a crash; a rerun GitHub refuses for now (the run still runs, HTTP 403 or 422) gives that allowance back and is tried again on the next poll. Rerun passed: the job goes into the flaky ledger (`studio flaky`, as `<repo>: <workflow> / <check>`) and the queue goes on. Failed again: a real failure, which never counts as flaky. A failure of the same job in the same repository on any pull request within 14 days of one whose rerun passed adds one board item, `Find the cause of flaky <job>` (`fix`, builder, with the run ids in its notes; its Definition of Done: find the cause, make it deterministic under load, never raise a timeout without a measured cause), unless one for that job is still open. `tick` lists both under `reruns` and `flakyItems`, `queue run` too when there are any.

`.studio/solutions/*.md` is a store of earlier solutions, one file per topic with a `# Title`. `studio solutions search`, `studio plan` and builder and designer briefs answer with paths and titles.

## Costs

Each crew run writes a stream-json log (`<state root>/logs/<id>.jsonl`). Claude Code ends a run with one `result` event; Studio reads `total_cost_usd` from it (else the sum of `costUSD` in `modelUsage`) and the tokens from `modelUsage` (`inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, over every model of the run), else from `usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`). A run is a `system`/`init` event. A run without a `result` (stopped at a limit, killed, crashed) is estimated from its `assistant` events: the last `usage` of each message, priced by model family (Haiku, Sonnet, Opus) at the first-party API prices of November 2026, cache writes at 1.25 times input, an unknown model at the highest rates so that an estimate errs high under a cap; such a run is marked `estimated` on the item and in the ledger, and its estimate counts toward the cap like a reported cost. Lines that do not parse or values that are not numbers are skipped. The cost is what Claude Code reports; on a subscription it is an estimate, not a bill.

- **Per item.** `collect` sums every run in the item's log and in the logs of the reviews of its pull request, and stores it on the board item as `usage: { runs, tokens_in, tokens_out, tokens_cache, cost_usd }`. A review counts for the builder item it reviews, not for itself. The sum is computed from the logs each time, so collecting again never counts twice. `studio metrics` lists it per item and epic, `studio epic list` adds a `COST` column (`costUsd` with `--json`), and the pane's footer shows `today $n` once today's runs cost anything.
- **Daily cap.** `limits: { daily_cost_usd: 25 }` in `studio.yaml` caps one project, the same key in the owner config caps all projects of the owner together. Both are optional. Before each plan (with an owner cap, in every project of the owner, also one that had no plan since), before a launch replaces an item's crew record and before `accounts-clear` moves the log start of crews, Studio enters every crew run that has ended into `costs.json` in the state root, on the local day it saw the result (`crew_label_limits.timezone`, default the system zone), so a run across midnight counts for the day it ended; runs are kept for eight days. A run has ended when its process is gone or its pid belongs to another process now (the start time stored at launch); a live process Studio cannot verify counts as running. Writers take `costs.lock` and merge with the file as it is then. Once today's sum reaches a cap, nothing new is planned or launched: every ready item is deferred with `daily cost cap reached ($x of $y)` (`owner daily cost cap reached …` for the owner cap), `tick` lists it under `held`, and `state.json` shows one `usage-limit` line. Running crews finish; their cost counts once they have ended, so a day can end above the cap by what was running. The next day starts from zero. While a cap is set, an unreadable `costs.json` holds every launch.

## Using your own runners

`studio setup ci` reads the runners GitHub shows for your repository and proposes the `ci:` block of `.studio/studio.yaml`. It needs `primary_repo` (`owner/name`) in that file and a logged-in `gh`.

- **Detection.** It lists the organisation's runners first and the repository's runners as a fallback. Runners with the `self-hosted` label are grouped by their exact label set; the largest group becomes `runner_labels`, `ci.capacity.total` is its size, and a name prefix shared by the group becomes an anchored `runner_name_pattern`. If a read fails, the result is "unknown" and nothing is proposed. Without any self-hosted runner it proposes `github-hosted`, and so it does when self-hosted runners exist but all workflows use GitHub-hosted labels (a job whose runner cannot be classified, such as an expression, a group alone or a reusable workflow, keeps the runners in the proposal); a note then names how many runners stay unused. Workflows that use both kinds of runner give `runners: both`. Organisation runners restricted to other repositories by runner groups are counted, because the API call does not show those restrictions. Capacity supports organisation runners only: with repository-level runners, or when a read finds no runner matching `runner_name_pattern`, it reports fully busy with an error instead of idle.
- **Labels.** The command also lints `.github/workflows/*.yml` and `*.yaml`: every job whose `runs-on` names self-hosted labels needs an online runner that carries all of them, otherwise the job would wait forever instead of failing. A `runs-on` map with `group` and `labels` is checked by its labels, with a warning that group membership cannot be verified; `group` alone only warns. Workflows triggered by both `push` and `pull_request` must use a concurrency group of the form `<prefix>-${{ github.head_ref || github.ref_name }}`, for example `ci-…`, with `cancel-in-progress: true`. The prefix may hold letters, digits, `.`, `_` and `-`. Concurrency groups are repo-wide, so two workflows sharing a group is an error naming both files when a sharer is a `push` and `pull_request` workflow with `cancel-in-progress: true`: give each its own prefix. Sharers that only deploy, with `cancel-in-progress: false`, pass.
- **Merge rule.** `merge_max_busy` is about 62% of `total` (at least 1). Studio opens pull requests and merges only while the busy self-hosted runners stay at or below it. With `runners: both`, only self-hosted runners count toward `ci_busy`; GitHub-hosted runs (in progress plus queued) are counted separately and compared with `github_hosted_limit`. `githubHostedBusy` counts all runs of the repository, including runs whose jobs use self-hosted runners. Until you set that limit the check is skipped, and Studio says so in a warning.
- **Public repositories.** A self-hosted runner on a public repository would run code from fork pull requests, so the command reports an error and `--write` refuses to write. There is no override, even when fork pull request workflows are blocked: use GitHub-hosted runners, or edit the `ci:` block by hand at your own risk. When the visibility cannot be read, the repository counts as public.
- **Shared host.** Set `ci.shared_host: true` when the runners share their machine with other work. Capacity then also requires the 1-minute load average of the machine Studio runs on to stay at or below `ci.capacity.host_load_max`, or at the number of CPU cores when that is unset. An explicit `host_load_max` applies with or without `shared_host`.
- **Where capacity applies.** Studio gates CI load where it causes it. A launch does not wait for CI runners: a crew builds and tests in its own clone and puts no load on CI until a pull request exists. A launch of a fix, feature or chore waits only for the host load above (reason `host load` in `studio plan`), besides role WIP, credentials, overlaps, dependencies and a pause. The load average is one reading that lags behind new work, so a plan assigns at most one build; the other ready builds show `host load: one build start per plan`, and each `studio launch` reads the host again and may start one of them. When `collect` opens the pull request for a crew, it first checks the merge rule twice, `check_twice_seconds` apart, like the merge queue; a read error counts as busy. If CI has no room, nothing is opened: the item keeps its status and branch, gets the note `pr held: ci capacity (busy N of M, limit L)`, and `collect` exits 1; run `studio collect <id>` again later, and it opens the pull request once and removes the note. An item that changed during the capacity wait gets no pull request. An open pull request of the branch is taken without waiting. The merge queue keeps its own check before every merge.
- **A review waits for CI.** A review item is deferred with the reason `ci pending` while any check of its pull request head still runs, or while the checks cannot be read; a launch refuses then too. Red checks do not hold it: the reviewer sees them. A repository that reports no checks at all does not wait. The routine tells the reviewer to approve code that is fine with green checks, and to ask for changes only where the code needs one, never because checks still run.
- **Crew pushes.** Studio assumes a crew's `git push` of `studio/<id>` starts no CI and does not block that push. A workflow whose `push` trigger matches crew branches (no branch filter, `**`, `studio/*` and the like) would start CI on every crew push that no capacity check sees, so `setup ci` warns about it. Limit `on.push.branches` to the default branch and let `pull_request` run the checks.

Without `--write` nothing changes. With `--write` the command changes only the `ci:` block (other keys and comments stay, but comments inside a replaced list are lost), validates the whole file first, and writes it atomically. Any error, from the proposal or from the workflow lint, makes it write nothing and exit 1. `--json` prints one object with `detection`, `proposal` (`ci`, `notes`), `errors`, `warnings` and `written`.

## Claude accounts

Studio can keep the Claude login of crews apart from your own. You store a long-lived token per account; crews then use it with their own Claude config dir, so logging in or switching accounts in your own sessions never changes theirs. You are responsible for using your accounts within the terms that apply to them.

1. `claude setup-token`: creates a token valid for one year and prints it. It needs a Pro, Max, Ultra, Team or Enterprise plan.
2. `studio account add <label>`: asks for the token with hidden input and stores it. The first account becomes the active one and sets up the crew config dir.
3. `studio doctor`: shows the accounts, which one is active and how crews log in.

`studio account list` shows each label with the day it was added, whether it is free, parked until a reset, blocked or at its limit, and its runs today; never a token. `studio account use <label>` makes another account the active one. `studio account remove <label>` removes one, and refuses while a crew runs on it. `add`, `use` and `remove` are for the owner and need a terminal; `setup-plugins` handles no secret and also runs for the lead without one (never for a crew), since every Studio update moves the pins; `remove` refuses while a launch is in progress, and warns when the last account goes, since launches then use the environment or your main login again. Crews use the active account only: while it is parked, blocked or at its limit, nothing starts until it is free again.

Studio checks only that a token has a plausible form (no spaces or control characters, 20 to 4096 characters). The Claude Code documentation names no way to check a token without a model call, so a wrong token shows up only when a crew starts. `account list` and `doctor` warn from 30 days before one year has passed since a token was added; after that a launch refuses and names `claude setup-token`.

**Crew config dir.** Crews of stored accounts use `$XDG_CONFIG_HOME/studio/claude` (default `~/.config/studio/claude`, mode 0700) as `CLAUDE_CONFIG_DIR`, never `~/.claude`. The first `account add` installs the pinned plugins there (by default `superpowers` and `studio`, see "Skills and updates"); `studio account setup-plugins` does it again and checks the installed versions. It runs `claude plugin marketplace add` with the HTTPS addresses of both marketplaces and `claude plugin install` with only `CLAUDE_CONFIG_DIR`, `HOME` and `PATH` in the environment, no token. A launch refuses while this directory is missing, and a role whose required skill is missing there, as for any config dir.

**Which way a launch takes.** A configured `crew_credential_command` comes first and is unchanged. Without one, stored accounts come next, with the active label. Without accounts, the environment and your normal Claude login are used, as before, under the label `default`.

## Crew credentials and usage limits

**GitHub token.** `studio secret set crew-token` asks for the token with hidden input (it refuses without a terminal), strips whitespace, checks the token once against the GitHub API for `primary_repo`, and only then writes `$XDG_CONFIG_HOME/studio/crew-token` (default `~/.config/studio/crew-token`) with mode 0600. It prints `valid for <repo>` or the failing permission and nothing from `gh`; after a failed check nothing changes. The check shows the token can use the repository; it does not prove the token's scope, so check yourself that it is least-privilege. At launch a `crew_token.env` variable that is set comes first, then this file. A file with a mode wider than 0600 or another owner makes the launch refuse.

**`studio doctor`** shows how crews log in to Claude (credential provider, the active stored account, a token in the environment, or your main login), the stored accounts with their state and expiry, and lists the crew token and its source, the credential provider, `allow_api_billing`, the names of API key variables in the environment and whether `studio.yaml` and the owner config are readable. It never prints a value. It exits 1 when the crew token is missing, unless `allow_ambient_credentials: true`.

**API billing** stays off unless the owner config sets `allow_api_billing: true`. Then `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` pass through to the crew. Without it, a launch also refuses when the `settings.json` in the crew's Claude config dir sets `apiKeyHelper`, `env.ANTHROPIC_API_KEY` or `env.ANTHROPIC_AUTH_TOKEN`. An unparsable settings file, or one that is not a regular file, refuses in either case. Crew settings written by Studio never contain `apiKeyHelper`.

**Settings sources.** Crews ignore the project and local Claude Code settings of the clone (`.claude/settings.json`, `.claude/settings.local.json`): Studio starts every crew, fresh or resumed, with `--setting-sources user`, so only the user settings and the file Studio passes with `--settings` apply. Hooks, `env` and `apiKeyHelper` from the repository therefore have no effect, and Studio no longer reads those files. Crews also do not auto-load the project `CLAUDE.md`, rules, skills, commands or subagents; Studio reads `AGENTS.md` and `CLAUDE.md` itself, in the owner's checkout, at the SHA of a freshly fetched `origin/main` (replace objects ignored), and saves copies next to the crew's brief in the state root (`briefs/<id>.rules/`); the brief points to those copies. The crew can read them but not write them, and a reused clone with moved refs cannot change them. A launch refuses when the fetch fails, when an entry is not a plain file (mode 100644, so no symlinks) or when a file is over 256 KiB. Items in another repository get the rules of the project checkout. The guard denies `git update-ref`, `git replace`, `git symbolic-ref` and fetch refspecs that write below `refs/remotes/`. Claude Code auto memory is off for crew runs (`autoMemoryEnabled: false` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`). These files cannot change settings or Studio's rules, and can never direct a crew to handle credentials, change remotes, reach new hosts or change the report contract. Before a launch, Studio refuses a role whose required skill is definitely absent from the crew's Claude config dir (`skills/<name>/SKILL.md` or a plugin cache `skills/<name>/SKILL.md`, any `plugin:` prefix stripped); an unreadable directory does not refuse. A required skill that is not available in the session means a `blocked` report naming it.

**Credential provider.** You can set `crew_credential_command` in the owner config (it is refused in `studio.yaml`). It is the absolute path of an executable file you own that neither group nor others can write. Studio runs it without a shell, with a 30 s timeout, and with only `PATH`, `HOME`, `STUDIO_ITEM`, `STUDIO_ROLE` (both empty when a plan only asks whether a credential is available) and `STUDIO_EXCLUDE` (comma-separated labels that are parked). It reads exactly one JSON line from stdout, at most 64 KiB; stderr is discarded:

```json
{ "label": "label-a", "env": { "CLAUDE_CONFIG_DIR": "/absolute/path/below/the/owner/config/dir" } }
```

`env` has exactly one key: `CLAUDE_CODE_OAUTH_TOKEN`, the verified fallback, or `CLAUDE_CONFIG_DIR`, which is also accepted (a login directory that must exist, belong to you and have a real path below the owner config dir). The config dir form has not yet been verified with an isolated `HOME` on macOS. The label matches `^[A-Za-z0-9._-]{1,64}$`. Only the label goes into state and board; a token reaches only the environment of the crew process. Any failure, a parked label in the answer, or an empty answer while no label is parked keeps the crew from starting. Without a provider Studio uses stored accounts (see "Claude accounts"), else the environment as described under Prerequisites, under the label `default`.

**Stored accounts, as a contract for providers.** A provider may hand out the tokens that `studio account add` stores, without its own copy. The layout is stable within a major version:

- `$XDG_CONFIG_HOME/studio/tokens/` (default `~/.config/studio/tokens/`): a directory, mode 0700, owned by the user, no symlink.
- `tokens/<label>.json`: one per account, mode 0600, owned by the user, no symlink, holding one JSON object `{"label": "<label>", "token": "<token>", "addedAt": "<ISO 8601 time>"}`. `label` equals the file name without `.json` and matches `^[A-Za-z0-9._-]{1,64}$`, not starting with a dot.
- `tokens/active`: mode 0600, the active label and a newline.
- `$XDG_CONFIG_HOME/studio/claude/`: the crew config dir with the plugins. For these tokens a provider returns `CLAUDE_CODE_OAUTH_TOKEN`.

Whenever a provider answers in the `CLAUDE_CODE_OAUTH_TOKEN` form, for a stored account or any other token, the crew gets this crew config dir as `CLAUDE_CONFIG_DIR`, as on the built-in way, never `~/.claude`; a launch refuses while it is missing (`studio account setup-plugins`). The `CLAUDE_CONFIG_DIR` form keeps the directory the provider names.

Studio reads these files only when no provider is configured. A provider reading them must apply the same checks (owner, mode, no link) and must never print a token except in its one JSON line.

**Usage limits.** At the start of `status`, `plan`, `launch` and `state`, Studio reads the end of each active crew's log. Only events Claude Code itself emits count; tool output that quotes a limit message does not. A `rate_limit` retry alone never stops a running crew; it counts only when the crew exited without a report and no later successful event shows it recovered. On a limit it stops the run, parks the label in `limits.json` in the owner root, for all projects, and returns the item to `ready` with a note; clone and branch stay. A label is parked until the reset when the event gives an absolute time, otherwise for one hour, and clears by itself afterwards. The next launch resumes the session when the clone is still there and the session is usable with the new credential (same label, or the token form with the same config dir), otherwise it starts fresh. A crew that left a report is not treated as limited, and a clone that left its branch is not replaced: the launch refuses and names it.

When no credential is available (without a provider: `default` is parked; with one: it answers empty while labels are parked), nothing is planned or started, and `state.json` shows one `forOwner` line with the earliest reset. Work continues by itself once a label is free. An unreadable `limits.json` counts as all parked and is reported.

**Usage limits per credential.** Each credential label has a ceiling set in the owner config under `crew_label_limits`: `max_parallel` (default 2) crews running at once, and optionally `max_runs_per_day` crew launches per day; `timezone` (an IANA name such as `Europe/Berlin`, default the system zone) decides where the day ends. A crew counts as running while its process is alive, whatever the board says. A launch counts when the crew is started, also when the start fails. Counts per day and label are kept in `usage.json` in the owner root and shown in `state.json` as `labelUsage` (labels only). A label at its limit is added to `STUDIO_EXCLUDE` like a parked one; a provider that returns it anyway makes the launch refuse. `plan` asks the provider with a growing exclude list (at most 16 calls, token never kept) and plans only as many items as the free labels allow; the rest wait with the reason `credential limit`, and with no free label `state.json` shows one `usage-limit` line. A provider must honour `STUDIO_EXCLUDE`: one that returns an excluded label makes the launch refuse and also holds `plan` (nothing is planned), even when no label is full. A live crew counts whatever the board says about its item. The counts are owner-wide, like account blocks and parks: two projects using the same credential share its limits. A crew stays running when another project parks its label; it hits the limit itself. An unreadable `usage.json` counts as all labels full, and an unreadable `crew.json` in any project refuses launches, since its crews cannot be counted. Launches of all projects are serialised with a `launch.lock` in the owner root, and the checks run again under the lock, after the clone is prepared and just before the run is counted and started; a launch that lost the lock refuses.

**Account blocks.** When an account looks blocked, Studio stops, so automation never makes it worse. At the start of `status`, `plan`, `launch` and `state`, it looks in the current run of every crew not yet stopped on an `assigned` or `in_progress` item, and of every running crew it can verify in another unfinished status, for events Claude Code itself emits: a failed authentication (also with no earlier success), an account on hold, disabled, suspended or banned, a disabled organization, a usage policy refusal. Tool output that quotes such a message does not count, and neither do billing errors or usage limits. A retry with a block category counts at once, also for a running crew, unless a later successful event shows the run recovered; a crew that left a report still counts.

Studio records the label and a reason code in `blocks.json` in the owner root (`<state base>/owner`), then stops every running crew of all your projects, of all labels, except on `merged` and `dropped` items, also when a board cannot be read. Another project's board is only read; its items move back the next time Studio runs there. It signals a crew only when the process start time stored at launch still matches; a running crew it cannot verify is not signalled but reported with item and pid, so check it by hand. `assigned` and `in_progress` items return to `ready` with a note; clone and branch stay. An item whose crew left a report stays where it is, so `collect` still works. Nothing starts and no credential provider is called while any block exists, under any label. `state.json` shows one `forOwner` line (`account-block`) and one entry per block under `notifications`. An unreadable `blocks.json` (malformed, a symlink, not a file) counts as blocked in the same way; a missing file means no block.

Nothing clears by itself. `studio accounts-clear <label>` removes that label's entries, moves the scan start of that label's crews in all projects to the end of their logs so an old event does not return, restarts nothing, and needs a terminal. Crews cannot write the owner root, because the sandbox lets them write only their own clone, tmp dir and `HOME`; those lie below the state base, but not in the owner root. On an unreadable file it refuses: inspect or remove the file.

**Upgrading.** Older versions kept `blocks.json`, `limits.json` and `usage.json` per project. The first command that needs them merges them into the owner root and removes the old files: blocks by label and reason with the earliest time, per label the later park, usage summed. A file that cannot be read is not interpreted. It is kept as `<owner root>/<name>.legacy-<project root>` (for a symlink, only a note), and until you inspect and remove that entry the file counts as unreadable, so nothing starts.

## Security model

The crew guard is a convenience layer, not a security boundary. The boundary is the sandbox, a least-privilege token and server-side branch protection. The guard does not contain a malicious crew: `package.json` scripts, and any program a crew writes, can run anything, so no list of denied commands can stop one. Owner-only commands (`pause`, `resume`, `accounts-clear`) need a terminal, which a crew does not have; that is the real barrier for them.

Layers, outermost first:

1. Sandbox: crew shell commands run sandboxed. Each item gets its own blob-less clone (no `git worktree` on the owner's repository) and an isolated, freshly recreated `HOME` that holds only a git identity and a credential helper reading the crew token. The clone is made from the project's origin, then its `origin` is set to `https://github.com/<item repo>.git`, so the crew pushes over HTTPS with the crew token even when the owner's origin is an ssh URL. An item's `repo` must be `primary_repo` or listed in `repos`; launch refuses anything else. Writes are limited to that clone, a per-item tmp dir and that `HOME`. Reads deny the whole real home directory (plus explicit credential locations such as `gh`, ssh, netrc, gnupg, aws, docker and keychain paths, and `GH_CONFIG_DIR` / `XDG_CONFIG_HOME` entries when set); only the clone, the tmp dir, the crew `HOME` and the real paths of the owner's `crew_toolchain_paths` (see below; nothing is derived from `PATH`) are allowed back in. Studio never runs git inside a crew clone after the crew started.
2. Least-privilege token: the crew token cannot merge, release or administer.
3. Server-side branch protection: `main` and every ref listed in `crew_allowed_workflow_refs` must be protected on the server. `loadConfig` callers can read `configWarnings(config)` for a reminder.
4. Guard hook: allows only the tools a crew needs (Bash, Read, Edit, Write, MultiEdit, NotebookEdit, Grep, Glob, Skill, TodoWrite, Task, Agent) and denies every other tool, including WebFetch, WebSearch and all MCP tools (crew settings deny these too, and crew sessions start with `--strict-mcp-config` and an empty MCP config). It denies risky constructs outright (force pushes, tag pushes, merges, deploys, writes outside the worktree, secret files, `eval`, shells with command strings, `xargs`, command substitution inside `git` and `gh`, running `studio` directly, `node` except `--version`, `--help`, `--test` with relative paths or plain patterns, or a literal relative script path, unquoted arithmetic and `${VAR:=x}`, `npx`, `pnpx`, `bunx`, `bun x`, `corepack`, `dlx`, `create` and `init` of npm, pnpm, yarn and bun, `npm x` and `npm exec`, `--shell*` and `--script-shell`, setting or unsetting `STUDIO_*`, `NODE_PATH`, `PATH`, `HOME` and package manager variables). These are conveniences that catch mistakes, not a wall. The hook blocks the call when node or the guard script is missing. Crew sessions write commit messages with `git commit -F <file>` and pull request bodies with `gh pr create --body-file <file>`. The guard allows listed forms, not a model of gh's or git's option grammar: `gh pr view|checks|diff|list|status` with an exact list of flags each (no clusters, no `--web`) and exactly `gh pr create --head studio/<id> --base <item base> --title <text> --body-file <file>` from the clone root (each option once, the file a relative path inside the clone), `gh workflow run <listed> --ref <listed>` when `crew_allowed_workflows` is set, no other gh; git global options from a short list; `git fetch` and `git pull` with listed options from `origin` only, `git ls-remote origin [<ref>...]`, `git push` to `origin` only, all from the clone root; no `git clone`, `init`, `fetch-pack` or `archive --remote`/`--output`; `git remote` and `git submodule` only to read; no writes below any `.git`.

npm, pnpm, yarn and bun pass with any command and any option (`--filter`, `-C`, `-r`), except the denylist above; a crew runs an installed tool with `pnpm exec <tool>`. `node` takes `--version`, `--help`, `--test [<relative paths or patterns>]` or a plain relative script path. A pattern after `--test` follows the same allowlist as Glob patterns (letters, digits, `_ - . / * ? , { }`, flat braces, no `..`), and one that could name the studio binary is refused. Variable names are matched case-sensitively, except `npm_config_*`.

## State root and owner config

Runtime state never lives in the repository. Per project it goes to `$XDG_STATE_HOME/studio/<hash>-<name>` (default `~/.local/state/studio/<hash>-<name>`; `<hash>` is the first 16 hex digits of the SHA-256 of the project directory's real path, `<name>` its sanitised base name): clones, crew homes, tmp dirs, settings, briefs, logs, guard contexts, `crew.json` and `marker.json`. The marker binds the root to the project's real path and origin URL; a launch with a mismatching marker, or into a non-empty root without one, is refused, and so is a state root that equals, lies inside or contains the project directory. A reused clone must still name the project's origin in its `.git/config` (read as a file), otherwise it is cloned again. Directories are created with mode 0700; Studio refuses to write or delete through a symlink below that root. Crew shell commands cannot read the state base `…/studio` except their own clone, tmp dir and home. The project's `.studio/` keeps `studio.yaml`, `board.yaml` and `roles/` (committed) and `reports/` (crew reports, written untracked in the crew clone as the last step).

Settings that open reads on the owner's machine are not the repository's call. They live in the owner config `$XDG_CONFIG_HOME/studio/config.yaml` (default `~/.config/studio/config.yaml`; schema `schema/owner.schema.json`; a missing file means defaults):

```yaml
crew_toolchain_paths: [] # absolute directories a crew may read, e.g. a version manager's install dir
crew_allow_macos_trust_service: false # true lets crew shells on macOS reach the TLS trust service so gh works; weakens the network boundary, see SECURITY.md
crew_credential_command: /absolute/path/to/provider # optional, see "Crew credentials and usage limits"
allow_api_billing: false # true lets crew runs bill the API
# notify: # optional, see below
#   quiet: "22:00-07:00" # local hours in which pushes that are not urgent wait
#   timezone: Europe/Berlin # the zone of the quiet hours; default the system zone
#   language: de # en or de; default from LC_ALL, LC_MESSAGES, LANG
#   ntfy_server: https://ntfy.example.org # self-hosted ntfy; default https://ntfy.sh
#   channel: my-channel # with command: hand state's owner lines to your own executable
#   command: /absolute/path/to/notify
crew_label_limits: # usage limits per credential label, see "Usage limits per credential"
  max_parallel: 2 # crews running at once per label
  # max_runs_per_day: 20 # optional launches per label and day
  # timezone: Europe/Berlin # optional, where the day ends; default the system zone
# limits: { daily_cost_usd: 50 } # optional, all projects together, see "Costs"
```

Tools installed below your home, such as `cargo` from rustup or `node` from a version manager, run in a crew only when their directories are listed here; `studio doctor` names any it finds on `PATH` that are not. For Rust list `~/.cargo/bin` and `~/.rustup`, never `~/.cargo` itself, which holds the registry credentials and is refused. Crews then get `RUSTUP_HOME` pointing to the rustup dir (read-only) and `CARGO_HOME` in their own `HOME`, so crates are fetched again per run and `~/.cargo/credentials*` stay denied.

A `studio.yaml` that still contains `crew_toolchain_paths` is refused. At launch every toolchain path must exist; Studio resolves it to its real path (which goes into the sandbox) and refuses it, comparing literal and real spellings and case-insensitively on macOS, when it is the home or a parent of it, equals, contains or lies inside a credential store, `~/.claude` or `CLAUDE_CONFIG_DIR`, or equals, contains or lies inside the project directory or the state root.

### Push notifications

**To your phone (ntfy).** `studio setup` (or `studio setup --notifications`) sets it up: ntfy needs no account. Studio makes a random topic (`studio-` and 24 url-safe characters, 144 bits) and stores it in `notify-secret` in the owner config dir (`$XDG_CONFIG_HOME/studio`, mode 0600, never readable by crews). Whoever knows the topic reads your pushes, so the setup prints the subscribe link once in your terminal and nothing else ever shows it: not `doctor` (it says `notifications: ntfy`, `none` or `invalid`), not `tick`, not any state file. Pushes go out as a plain HTTPS POST to `<server>/<topic>` (the topic is never in a command line), title `Studio`.

`tick` pushes each new entry of its `needsLead` and each account block. A push is one line in your language, a fixed phrase, the item id and the project name (the repository name of `primary_repo`; `primary_repo` and `repos` must be `owner/repo`), never a note, question or other crew text: `Fix limit reached: APP-3 in app`, `Merge failed`, `Changes requested`, `Crew has a question`, `Blocked`, `Account blocked`, `Decision needed`. A decision is the item, its kind and the time the item entered its status; it is pushed once (`pushed.json` in the owner state root holds what was sent, no secret). At most one push per project in 10 minutes: what comes up meanwhile waits and goes out bundled (`3 decisions needed in app`). During `notify.quiet` (in `notify.timezone`, else the system zone) pushes wait too, unless urgent: an account block passes quiet hours and the throttle, with high priority. A failed push is listed under `errors` as `notify: <reason>` and tried again on the next tick; it never fails the tick.

**To your own command.** With `notify: { channel, command }` in the owner config (a `notify` block in `studio.yaml` stays parsed, has no effect, and `studio` warns), `studio state` hands each line for you and each account block to `command` once. `channel` matches `[A-Za-z0-9._-]{1,64}`; `command` is checked like the credential provider (absolute, a regular file you own, not group- or world-writable) and runs without a shell, with a 30 s timeout, output ignored. Its environment is exactly `PATH`, `HOME`, `STUDIO_NOTIFY_CHANNEL`, `STUDIO_NOTIFY_KIND` (`owner-item`, `usage-limit` or `account-block`), `STUDIO_NOTIFY_ID`, `STUDIO_NOTIFY_PROJECT` and `STUDIO_NOTIFY_TEXT` (control characters replaced by spaces, at most 500 characters). Sent messages are remembered in `notified.json` in the owner state root; a failing command is retried on the next run, a line that vanishes and returns is sent again, at most 20 are sent per run, and an unreadable `notified.json` sends nothing. `studio doctor` shows only whether notify is set.
