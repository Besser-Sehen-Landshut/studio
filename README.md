# studio

Studio is a Claude Code plugin and TypeScript package for running a small software studio of coding-agent sessions from one control room: a lead session plans work from a board and a crew of role-based sessions carries it out, each in its own sandboxed clone.

Status: 0.26.0, stage (a) (board, planner, capacity, crew launch, guard, merge queue) with stage (a.1) (your own runners, crew credentials, usage limits), stage (a.2) (account blocks, owner-wide limits, pinned crew rules), stage (b) (the Studio board inside Claude Code, pause and resume, push notifications) and stage (c) (capabilities per crew, tiered review, third-party sources, role memory, model per role and item type, change failure rate and time to restore, flaky-test ledger, solutions store), plus components (work per part of the product, with their own WIP limit), an owner-wide overview, a lead heartbeat (`tick`) that carries items from ready to merged, a guided setup (`setup`, `/studio:init`, `/studio:add`), epics with a roadmap generated from the board and an automatic acceptance per epic, pushes to your phone when a decision is needed (ntfy), one automatic rerun for a CI failure outside a pull request, crew costs per item with a daily cap, a weekly lessons review for the lead, restart safety (`recover`), exceptions by evidence (a guard hit a built-in proof shows a false alarm, such as comments only, is waived and logged; otherwise the lead decides), a release gate per component (`studio release`: the note, the owner's and third parties' approvals, one trigger of a named workflow, the checks after the deploy), and workers on other machines (`runs_on`, `studio worker`: an atomic claim on GitHub, the same crew rules plus a deny list per machine, the report back on the claim), and reverse engineering for the researcher role alone (`research.artifacts`: the REA server at an owner-pinned, integrity-checked version started outside the crew's clone and environment, a static, read-only tool allowlist, one read-only analysis directory, tool classes the owner opens per item, results as structure behind a privacy check), with trust mode by default (every REA tool class, a full install on first use after one confirmation by the owner), groups of related projects (`groups:` in the owner config: a member's crews get the main project's contracts, decisions and glossary as a read-only excerpt, items wait for items of another project, a contract change gives each affected member a check item, the pane shows one line per project), a hard time limit for every analyzer subagent and every review (`skipped: timeout`, which never passes a mandatory analyzer), automatic clean-up of finished items (`studio gc`), any pull request through the merge queue (`studio merge`) with an optional runner-load gate, a register of migration numbers (`studio migration`), a shared build cache filled by its own crew role, `comments_only` for Rust, TypeScript/JavaScript, YAML and TOML, project proof commands in a sandbox (`proof: command`), and native Windows workers (experimental: each crew as a dedicated standard user behind a loopback proxy, proven by a probe before every claim). See [CHANGELOG.md](CHANGELOG.md).

## Quick start

1. Install the plugin in Claude Code:

   ```
   /plugin marketplace add Besser-Sehen-Landshut/studio
   /plugin install studio@studio-marketplace
   ```

   Then restart Claude Code.

2. Once, in your own terminal: `studio setup --link`. One guided step each, skipped when it is done: `gh` installed and logged in; the crew's GitHub token (what it is and which permissions it needs, then hidden input); a Claude account for crews (it asks you to run `claude setup-token` in another tab and paste the token, hidden, with the label `main` unless you type another); with `--link`, a small `studio` shim in `~/.local/bin` so the command works in any terminal; push notifications; and, optionally, REA (reverse engineering) for researcher crews. It ends with the next step. Before the shim exists, call it by its path: `node <plugin>/bin/studio setup --link` (`/studio:init` prints the exact line, see [Install](#install)).
3. In Claude Code, in your project's folder (a clone of its GitHub repository): `/studio:init`. Claude runs `studio init`, which checks the prerequisites and proposes `.studio/studio.yaml`, explains the result in plain words, writes the files with `studio init --write` after your yes, shows the next steps and adds a first item from your description. Commit `.studio/studio.yaml` and `.gitignore`: the board (`.studio/board.yaml`) stays on this machine and is not committed (see [The board lives on the lead machine](#the-board-lives-on-the-lead-machine)).
4. More work: `/studio:add the checkout page crashes when the cart is empty`, or ask in plain words. Claude turns it into `studio add "<title>" --type fix --path "src/checkout/**" --dod "..."`.
5. `/studio` opens the board pane. In a Claude Code session in the project, say "run the Studio lead loop" (skill `studio:studio-lead`). The lead runs `studio tick` every few minutes, which launches crews, collects their work, has every pull request reviewed and merges it.

## Install

```
/plugin marketplace add Besser-Sehen-Landshut/studio
/plugin install studio@studio-marketplace
```

The plugin ships the commands `/studio:init` (set up a project) and `/studio:add` (add work in plain words), two skills (`studio:studio-lead` for the control room, `studio:studio-crew` for crew sessions), the board pane `/studio` and a self-contained CLI. Claude Code puts a plugin's `bin/` on the Bash tool's `PATH` while the plugin is enabled ([plugin components, "Executables"](https://code.claude.com/docs/en/plugins/components)), so Claude simply runs `studio <command>`. Your own terminal does not get it: run `studio setup --link` there once (as `node <plugin>/bin/studio setup --link`, where `<plugin>` is the plugin's folder under `~/.claude/plugins/cache/`). When `~/.local/bin` is on your `PATH` it asks, then writes `~/.local/bin/studio`: a small shell script (a regular file, not a link) whose second line is `# studio-shim v1`, written through a temporary file and a rename, and the launcher's path to `$XDG_CONFIG_HOME/studio/launcher`. The plugin's folder changes with each version and Claude Code marks an old one with `.orphaned_at` and removes it 14 days after an update. The shim uses the cached path only while that file exists and its plugin folder has no `.orphaned_at`; otherwise it runs `claude plugin list --json`, takes the enabled `studio@…` entry (`readFromFolder` when present, else `installPath`), rewrites the cache and runs `node <path>/bin/studio`. So no new `--link` is needed after an update. Without the `claude` CLI on `PATH` it says so and stops. Studio never edits shell files; when `~/.local/bin` is not on `PATH` it says how to add it. It replaces only a file whose second line is exactly the marker, and refuses any other `studio` there (a file of yours, a link). The plugin needs no `pnpm install`: `bin/` loads the committed bundles in `dist-bundle/` (rebuilt with `pnpm bundle`; CI fails if they drift from `src/`).

## Prerequisites

- Claude Code CLI, `git`, and `gh` (authenticated for the control room's own use).
- The `superpowers` plugin: feature and fix items require its skills, and a launch refuses when one is definitely not installed (`studio doctor` shows it; a role can opt out with `skills.denied`).
- Node.js 24 or newer on `PATH` (the CLI and the crew guard hook run on it).
- A least-privilege crew token created by the repository owner (for example a fine-grained token limited to the project's repositories: contents and pull requests read/write, no administration, no merge rights beyond what branch protection allows). Store it with `studio secret set crew-token` (Studio then loads it itself), or export it and name the variable in `studio.yaml` under `crew_token.env`; the variable wins when it is set. Launch refuses without it unless `allow_ambient_credentials: true`.
- Server-side branch protection on `main` and on every ref listed in `crew_allowed_workflow_refs`.
- A platform where Claude Code's sandbox is supported.
- Model authentication for crew sessions in the control room's environment: crew sessions get an isolated `HOME`, so they authenticate with `CLAUDE_CODE_OAUTH_TOKEN` (passed through when set), with the Claude login in `CLAUDE_CONFIG_DIR` (default `~/.claude`), or through a credential provider (see [Crew credentials](#crew-credentials-and-usage-limits)). API billing is off by default: `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are removed from the crew's environment because an API key would otherwise take precedence over `CLAUDE_CODE_OAUTH_TOKEN`. Check on the first launch that the crew session starts and authenticates (`studio status`, the crew log in the state root).
- `sandbox.network_allow` lists every host the crew's shell commands may reach (GitHub for `git` and `gh`, your package registry); everything else is blocked.

## Writing the files by hand

`studio init` writes these files for you. To write them yourself instead, create `.studio/` in the project repository.

`.studio/studio.yaml`:

```yaml
studio: 1
primary_repo: org/app
repos: [org/app]
ci:
  provider: github
  runners: github-hosted
  runner_labels: []
  capacity: { total: 4, merge_max_busy: 3, check_twice_seconds: 30 }
merge:
  strategy: studio-queue
  contract_paths: []
roles:
  builder: { model: sonnet, wip: 2 }
  reviewer: { model: opus, wip: 1 }
sandbox: { network_allow: [github.com, api.github.com, registry.npmjs.org] }
crew_token: { env: STUDIO_CREW_TOKEN }
owner_only: []
deploy_commands: []
crew_allowed_workflows: []
crew_allowed_workflow_refs: []
review_bases: [] # base branches besides the default branch a pull request may be reviewed against
# acceptance: { suites: [{ workflow: .github/workflows/e2e.yml, job: browser }] } # optional: the full suites of an epic's acceptance, see "The acceptance"
# evidence: [] # optional: guard jobs a built-in proof can show false alarms, see "Exceptions by evidence"
# migrations: { dir: db/migrations } # optional: the register of reserved migration numbers, see "Migration numbers"
# components: [...] # optional: parts released on their own, with a release: block each, see "Components" and "Releases"
# workers: { windows: { deny: { paths: [], ports: [] } } } # optional: what crews on workers of a label never touch, see "Workers on other machines"
# cache: { enabled: true, every_days: 7, timeout_min: 60 } # optional, off by default; needs roles.cache, see "Build cache"
```

`.studio/board.yaml`: (not committed: add `/.studio/board.yaml` to `.gitignore`, see below)

```yaml
items:
  - id: APP-1
    title: Add a health endpoint
    type: feature
    role: builder
    repo: org/app
    size: S
    priority: 1
    status: ready
    paths: []
    touches: ["src/health/**"]
    depends_on: []
    dod: ["GET /health returns 200", "test added"]
    plan: docs/plans/health.md
    history: []
```

### The board lives on the lead machine

The board (`.studio/board.yaml`) is the lead machine's working state: Studio edits it in the working tree on every collect, launch and merge, and nothing keeps it committed. So it is not committed: `studio init --write` adds `/.studio/board.yaml` to `.gitignore`, and `studio doctor` warns while git tracks it (`git rm --cached .studio/board.yaml`, then commit that and the `.gitignore` line). `.studio/studio.yaml` and `.studio/roles/` stay committed: they change through pull requests like any code. To share the plan, `studio roadmap --write` renders `ROADMAP.md` from the board, and that file is committed. Cross-project dependencies and the epics of a group read each other project's board from its folder on this machine, the working tree, never from git (see [Groups of related projects](#groups-of-related-projects)), so an untracked board is all they need. Workers never read the board: an offer carries the item's fields.

Then, in a Claude Code session in that repository, ask the lead (skill `studio:studio-lead`) to run the loop, or run it by hand: `studio board`, `studio plan`, `studio launch APP-1`, `studio status`, `studio collect APP-1` (it opens the pull request and adds its review item), `studio launch` of that review, `studio collect` of it, `studio queue add org/app#12`, `studio queue run`. `studio tick` does all of that in one step, as often as it is run. JSON Schemas for editors are in `schema/`.

## init and add

`studio init` runs in the project folder (or `--project <dir>`). Without `--write` it is a dry run: it prints every check and the files it would write, writes nothing and exits 0, also with warnings or failed checks. With `--write` it writes `.studio/studio.yaml` and `.studio/board.yaml` only when no check failed, and adds `/.studio/board.yaml` to `.gitignore` (created when missing; nothing added when the board is ignored already; a `.gitignore` that is a link is left alone with a warning); otherwise it writes nothing and exits 1. It never overwrites: when either file exists it refuses and says to edit it, or to use `setup ci`, `setup stack` and `doctor`. `--json` prints one object with `checks` (`name`, `status` `pass`, `fail` or `warn`, `detail`, `fix`), `config`, `board`, `stacks`, `warnings`, `written` and `nextSteps`.

- **Checks.** git 2.38 or newer, `gh` installed and logged in to github.com (`gh auth status --hostname github.com`, so a stale login to another host does not count), the `claude` CLI, Node.js 24 or newer, a platform where Claude Code's sandbox runs (macOS, Linux, WSL2), and `origin` naming a GitHub repository. A missing crew token, a missing stored Claude account and a missing `superpowers` plugin are warnings with the command to run: `studio setup` (or `studio secret set crew-token` and `studio account add <label>` one at a time) needs the owner in a terminal; the next steps name it once, with the `node <plugin>/bin/studio setup --link` line for a terminal without `studio`. A `.gitignore` that ignores `.studio/studio.yaml` or `.studio/roles/` (for example all of `.studio/`) is a warning too: those files belong in the repository, runtime state lives outside it; only the board is ignored. Each call to `gh` has 15 s and `claude --version` 10 s; one that does not answer in time is a failed check. Steps the checks find done (a stored crew token, a Claude account) are left out of the next steps.
- **What it proposes.** `primary_repo` and `repos` from `origin`; the `ci:` block of `setup ci` (when it has no usable proposal, for example because the runners cannot be read, GitHub-hosted runners, with a `ci` warning, a first next step and a comment in `studio.yaml` to run `studio setup ci`); the stacks of `setup stack`; a builder (`sonnet`, wip 2) and a reviewer (`opus`, wip 1); `sandbox.network_allow` with GitHub, the package registries of the manifests it found and the hosts a detected stack needs (Docker Hub for `docker`). Components: one per direct child of `apps`, `packages`, `services`, `crates` and `libs` that holds a `package.json`, `Cargo.toml`, `go.mod` or `pyproject.toml`, with the folder name as name, a unique id made from it, `primary_repo` and the path `<folder>/**`, and, next to them, a `tooling` component for `.github`, `tooling` and `scripts` when present. A single-package repository gets no components. No component gets a `wip`. Both files are parsed in memory by Studio's own loaders, also in a dry run, which writes no file anywhere; a proposal that would not load is a failed check. `--write` refuses a `.studio` that is a link or a file, creates each file only when it does not exist, and removes what it wrote when a later write fails.

`studio setup [--link]` is the owner's one-time setup, in a terminal (it refuses without one and under `STUDIO_ROLE=crew`). It runs six numbered steps, the sixth optional, and skips each one that is done: (1) `gh` installed and logged in to github.com, the same check as `init`; when not, it names the fix and stops. (2) The crew token: when none is set, it says what the token is for and which permissions it needs, then runs `secret set crew-token`, checked against `primary_repo` of `.studio/studio.yaml`, else the GitHub repository of `origin`, else a repository it asks for. (3) A Claude account for crews, when none is stored and no credential provider is set: it asks you to run `claude setup-token` in another tab, asks for a label (default `main`) and runs `account add`. The label is asked first at a visible prompt and checked before the hidden token prompt: one that starts with `sk-ant` or is longer than 32 characters is refused as a token typed at the wrong prompt, and so is a token typed at the visible repository prompt. (4) `studio` in your terminal: with `--link` the shim as under [Install](#install), without it a hint when `studio` is not on `PATH`. (5) Notifications to your phone (see [Push notifications](#push-notifications)): `ntfy` (Enter) or `none`; `ntfy` makes a new random topic, prints its subscribe link once with "Install the ntfy app and open this link", waits for Enter, sends a test push and stores the topic only when that push went out (else it says `test push failed: ntfy answered <status>` and stores nothing). `none` or an aborted prompt skips the step. `studio setup --notifications` runs only this step, also when notifications are set up already (a new topic replaces the old one). (6) Reverse engineering (optional): REA for researcher crews, asked once (Enter is no, and a skip is kept); `studio setup research` runs this step on its own (see [Reverse engineering for the researcher](#reverse-engineering-for-the-researcher)). A failed step stops the run with exit code 1; nothing is ever echoed from a token. It ends with `/studio:init`.

`studio add "<title>"` appends a ready builder item: the next free id with the prefix most items use (else the letters of the repository name, `APP` for `org/app`), `size: S`, a priority after every other item, `--type` (default `fix`; a `feature` needs `--plan`), `--repo` (default `primary_repo`), each `--path` as one of `paths` and `touches` (relative, without `..`), each `--dod` as a line of the Definition of Done (at least one), `--component`, `--plan`. It checks the item against the board schema and the config and saves under the board lock. It prints the item; `missing` names what the planner still needs, `warnings` say that an item without `--path` conflicts with no other item and belongs to no component, and `notes` that a path below `.github/` makes it a CI item. `init` and `add` refuse under `STUDIO_ROLE=crew`.

`launch` refuses while a crew for the same item is still running and deletes a report an earlier run left in a reused clone. `collect` refuses while the item's crew process is still alive and refuses a report last modified before the crew started.

**Tests a crew cannot run.** Crews get no database, no Docker and no network outside the allow list, so CI is the authority for the full suite. A crew runs what its sandbox can for what it changed (the touched package, crate or workspace member, the Definition of Done's tests, lint, format) and lists a command that a missing service kept from running under `not_run_here`, with `command`, `missing` (`database`, `docker`, `network` or `service`) and `reason`; the report stays `done`. A test that ran and failed is `failed`, never `not_run_here`, and an entry without one of those four services refuses the report. `collect` then works as usual: it opens the pull request under the capacity check with a section listing those commands for CI, stores the list on the item (`not_run_here`) and prints how many there are and which services were missing (the commands themselves are crew text and stay on the item and in the pull request). An open pull request of the branch is reused and its text renewed, so the list there is the latest. A review launch writes it to `briefs/<id>.caps/pull-request/not-run-here.txt`. The reviewer names, for each command, the workflow file at the base that defines the job running it, the job, and why that job covers the command (`not_run_here_jobs`, with `command`, `workflow`, `job` and `covers`, one plain line of at most 600 characters). `collect` checks this in the owner's checkout at the pull request's base commit and at its head. The job must be in the file without `continue-on-error`; an `if:` is allowed, because a job it skips reports a skipped check, which never counts as passed. Either the workflow runs on `pull_request`, and its checks are `<job>`; or it is a reusable workflow (`on: workflow_call`) that a job of a `pull_request` workflow calls with `uses: ./.github/workflows/<file>`, and its checks are `<caller job> / <job>` in the caller's workflow. One level only: a job that calls a further reusable workflow, a file called only through another reusable workflow, and a remote `uses: <owner>/<repo>/...@<ref>` are refused, and a calling job may not have `continue-on-error` either. The workflow whose name the checks carry must have a unique name, the check names must be the same at the base and at the head, and the job's definition (with its callers) must be unchanged between them unless the item is a CI item. Every check of the job, each matrix leg ` (<leg>)` included, must have passed on the pull request; skipped, cancelled or missing counts as not passed. The gate does not test whether the job runs the command: task runners (`turbo`, `nextest`, `make`) hide it, so that is the reviewer's judgement in `covers`, which `collect` prints for the lead (`notRunHereJobs`). Otherwise the review item is blocked with a note naming the entry and the rule, and no approval is stored. An approval stores the jobs (`approved_jobs`), and the merge queue checks them again before it merges. An approval still counts only with green checks.

`pause` writes `pause.json` in the state root: `plan` assigns nothing (reason `paused`), `launch` refuses, and `queue run` holds before the next merge. Running crews continue. Any entry under that name counts as paused, readable or not; `resume` removes it. Both commands need a terminal and refuse under `STUDIO_ROLE=crew`. `queue run` also holds while old per-project state files are not yet merged into the owner root.

**Review item.** When `collect` opens or reuses a builder's pull request and moves the item to `in_review`, it adds a review item unless a review naming that pull request is still open (neither merged nor dropped): the next free id with the builder's prefix (`APP-8` after `APP-7`), title `Review of <id> (PR #<n>)`, `role: reviewer`, `type: review`, `status: ready`, the builder's repo, paths, DoD and named components, no touches or dependencies, and the note `review <repo>#<n>`. Its output names it (`review: <id>`). After a fix round the earlier review has finished, so the next collect adds a new one. Review and research items open no pull request and get none.

**`tick`.** One heartbeat of the lead, safe to run every few minutes; the lead skill runs it every 120 seconds. In order: (a) it collects every item in `assigned` or `in_progress` whose crew has ended, and (b) every item whose pull request was held for CI capacity, by the same code as `collect <id>`; then it adds a review item, as `collect` does, for a builder in review that has neither an open review nor a verdict (its review was dropped); before (c) it prepares each epic's acceptance (see [The acceptance](#the-acceptance)) and, when the build cache is on and due, adds its item, and once a day removes caches over the disk cap (see [Build cache](#build-cache)); (c) it plans and launches what the plan assigns, through every gate of `launch` (capacity, WIP, component WIP, holds, pause, usage limits, the launch lock), except a review whose pull request this tick opened, which waits for the next tick so CI can report its checks first; (d) it runs `queue add` for every builder in review whose approval is stored, unless a merge failed after that approval; (e) when the queue holds pull requests, an entry a killed run left current, or a `queued` item the queue no longer holds, and no run is active, it runs the queue in the same process (a running queue is left alone); (f) once in 30 days it runs `skills check` and prints `skillsCheck` with the items it added. Before (a) it finishes a launch a crash cut short (see [Recovery](#recovery-after-a-crash-or-restart)), and after (f) it runs the lessons review (see [Role memory](#role-memory)). It prints one JSON object: `collected` (the output of each collect), `reviews` (review items it added), `launched`, `queued`, `merged`, `held` (what waits, with the reason: a held pull request, an approval waiting for green checks, a deferred item, a running queue), `needsLead` (what needs a decision: a report that cannot be read or was rejected, a crew it cannot verify, a request for changes, a blocked item, a failed merge, a refused `queue add`) `reruns` (failed jobs outside a pull request that ran once more on the same commit, see [Flaky tests](#flaky-tests)), `flakyItems` (items it added to find the cause of a flaky job) `recovered` (only when a restart check repaired something), `lessonsReview` and `lessonsJudged`, `epicsReady`, `acceptance`, `epicsDone`, `epicsReopened` and `cache` (`added`, `removed`; only when there are any) and `errors` (per `item`, or per `phase` when a whole phase failed; a pull request held because the CI read itself failed is listed there too; a push that failed as `notify: <reason>`). One item's or one phase's failure is recorded and the rest goes on, and the JSON is always printed; the exit code is 1 when `errors` holds anything but `notify:` lines. After the phases it pushes what is new in `needsLead`, and every account block, to your phone (see [Push notifications](#push-notifications)). Only refusals that mean "not now" (a busy lock, an item the plan holds back, a pause or block) count as held; anything else is an error. A second tick while one runs does nothing (`held: tick`). `studio tick --dry-run` prints what the next tick would do and changes nothing: the crews it would collect (`collect`), the review items it would add, the plan's launches with each researcher's REA decision (`ready`, `install` after the owner's confirmation, `needs-owner` with the line the lead would get, or `declined`), the offers to workers, the pull requests it would queue and whether it would run the queue (`queueRun`), a group member's contract check (what it would fetch and the last record), accepting epics, open releases, a due skills check, and `held`, `needsLead` and `errors` as a tick lists them, with `dryRun: true`. It takes no lock, binds no state root, fetches nothing, starts no crew, writes no board, ledger or record and pushes nothing; what only acting decides (a report's verdict, a merge, a contract change) it names as what the tick would try. The tick refreshes its lock per item and stops before the next phase when the lock was lost; it releases the lock before the queue run, which has its own. `tick` refuses under `STUDIO_ROLE=crew`.

`queue run` is meant to run in the background. It holds a lock in the state root (a second run exits 1 with "queue already running" while the holder lives; the lock records pid, start and a heartbeat refreshed on every step and poll, and is taken over with a note only when that pid is gone or the heartbeat is older than 15 minutes; SIGTERM, SIGINT and SIGHUP release it), picks up PRs added with `queue add` while it runs, and moves each board item as soon as its PR is done. On start it first applies results a previous run recorded but did not put on the board. Right after a head change (branch update or new push) a PR without any reported check counts as pending for 5 minutes, then fails with "no checks reported". `merge.strategy: native-queue` is not supported yet: `queue add` and `queue run` refuse it. A result that ran out of the queue's time limit (4 hours per entry: checks still pending, capacity, runner load or a main build that did not clear) is recorded with `timeout: true` and shown as `TIMEOUT`.

**Merging any pull request.** `studio merge <pr> [--repo owner/name] [--by <name>]` hands a pull request that has no board item, for example one a session outside the board opened, to the same merge queue; `--repo` defaults to `primary_repo` and must be in `repos`, `--by` (default `lead`) records who asked. The entry is marked `external: { by, at, head }`, `head` being the pull request's head at that moment; `queue run`, and so the next `tick`, merges it in turn. Only that head is merged: when the pull request has another head at any read of the queue (before the checks, after them, right before the merge, or when GitHub refuses the pinned head), the entry fails with `head moved since enqueue: <old> -> <new>; re-run studio merge`, so nothing the lead has not seen is merged. `--follow-head` (stored as `followHead: true`) opts out: a new head is read again, waits for its own checks and is merged with `--match-head-commit`. A pull request a board item holds (any status but `dropped`) is refused: it merges through its review and `queue add`. Without a board item there is no Studio approval, so the gates are the ones that make sense without one: the queue does not update the branch (it is not Studio's), waits while checks are pending and stops on the first failed or cancelled check (no rerun, no flaky ledger, no exception by evidence), waits while a push build runs on the pull request's base branch (a merge would cancel or race it; a read that fails counts as running), waits for CI capacity and `merge.runner_load`, reads the board again right before the merge (a board item or an open review that took the pull request meanwhile refuses it), reads the head again and merges with `--match-head-commit`, so a push in between is never merged unseen. Approvals and branch protection are GitHub's: Studio adds none, and a merge GitHub refuses fails the entry with its message. The result never moves the board and is not counted in the metrics. `tick` lists a failure in `needsLead` and pushes each result of the last day once (`Merged` or `Merge failed`, with `<repo>#<pr>`). `--wait` runs the queue in this process until the entry is done (while another run holds the queue it reads `queue.json` every 30 seconds) and prints `status`: `MERGED` (exit 0), `FAILED` or `TIMEOUT` with the reason (exit 1); a pause or account block ends the wait with `QUEUED` and the entry stays in the queue.

**Runner load (`merge.runner_load`, optional).** For CI on self-hosted runners that Studio's own capacity rule does not see, for example those of another organisation:

```yaml
merge:
  strategy: studio-queue
  contract_paths: []
  runner_load:
    org: example-org
    name_pattern: "^ci-runner-[0-9]"
    max_busy: 5
    samples: 2
    interval_s: 30
```

Before every merge of the queue, board items and external entries alike, Studio reads the organisation's runners (`GET /orgs/<org>/actions/runners`) `samples` times (1 to 10, default 2), `interval_s` apart (default 30), and counts the online runners whose name matches `name_pattern` and that are busy. It merges only when every read finds at most `max_busy`; otherwise it waits a minute and reads again, until the queue's time limit. A failed or unparsable read, a timeout and a read that finds no runner matching the pattern count as busy. Without `runner_load` nothing changes. The token `gh` uses needs to read the organisation's runners.

## The Studio board

In the owner's interactive Claude Code session in a Studio project, the plugin shows what Studio is doing. It displays and starts no process; the one file it writes is the owner's REA install confirmation, when the person presses its button (see "Reverse engineering for the researcher"). Crew sessions (`STUDIO_ROLE=crew`), `claude -p` and folders without `.studio/studio.yaml` get none of it.

- **Pane.** "Studio board", in one of three views. Every state has a sign and a word, never a colour alone; titles are cut with "…" by terminal cells (East Asian wide characters and emoji take two), never the id, the sign or the stage. A `state.json` that is missing, unreadable or the wrong shape gives a calm message, never an error.
  - **Work list** (the default): the project and how fresh the state is; one line of counts (`! decisions needed`, `● running`, `◷ waiting`, `✓ today`); a highlighted "Decision needed" block with each lead decision and line for you, and under it what you can say next (a hint always starts with `→` two cells in; wrapped text of an entry goes on four cells in, so nothing else can look like a hint). A lead decision shows a fixed phrase for its kind (`fix limit reached – decide`, `changes requested`, `merge failed`, `crew has a question`, `blocked`, `needs a decision`), never the crew's text; the full line is under "For the lead" in `/studio more`; then each epic with a progress bar and merged of total, its items sorted decision, running, waiting, ready (`<sign> <id> <title> <stage> <time in stage>`, a waiting item with its reason on a second, dimmed line, done items folded into `✓ n done`); then "Without epic" the same way; and one footer line with CI use, the median lead time and `/studio more`. Empty sections are left out. Example, 60 columns:

    ```text
    Studio · shop                              updated 1 min ago
    ! 1 decision needed  ● 2 running  ◷ 1 waiting  ✓ 3 today

    Decision needed
    ! APP-15 fix limit reached – decide
      → say "show APP-15"

    E-3 Connection limits                              █░░░░ 1/4
      ! APP-15 Retry on timeout                     decide   30m
      ● APP-14 Header timeout                       review   12m
      ○ APP-16 Idle timeout                         ready
      ✓ 1 done

    E-4 Privacy tests                                  ██░░░ 1/3
      ● APP-17 Backup log line                      building  4m
      ○ APP-19 More log tests                       ready
      ✓ 1 done

    Without epic
      ◷ APP-12 Duplicate header lines               waiting   3m
        queue: runners 6/8 busy, merge at ≤5
      ✓ 1 done today

    CI ██████░░ 6/8 · lead time 3.1 h · /studio more
    ```

  - **Pipeline** (`/studio pipeline`): the first decision, then the columns READY, BUILDING n/wip, REVIEW n/wip (the WIP limits of the build roles and of the reviewer), QUEUE and TODAY with a card per item (sign and id, short title, epic code such as `E3`, time in stage, and what it waits for); a full column says `⚠ full`, blocked work has a row of its own below. A pane too narrow for five columns (about 60 to 70 cells), or whose columns cannot hold the sign and the longest id, draws the work list instead. Example, 72 columns:

    ```text
    Studio · shop                                          updated 1 min ago
    ! APP-15 fix limit reached – decide
      → say "show APP-15"

    READY 2       BUILDING 1/4  REVIEW 1/2    QUEUE 1       TODAY ✓3
    ────────────  ────────────  ────────────  ────────────  ────────────
    ○ APP-16      ● APP-17      ● APP-14      ◷ APP-12      ✓ APP-11
      Idle time…    Backup lo…    Header ti…    Duplicate…  ✓ APP-18
      E3            E4 4m         E3 12m        3m          ✓ APP-10
    ○ APP-19                                    CI 6/8
      More log …
      E4

    ■ BLOCKED 1
      APP-15 fix limit reached – decide (E3)

    CI ██████░░ 6/8 · lead time 3.1 h · /studio more
    ```

  - **Details** (`/studio more`): the earlier sections: the crew with a state per item (`working`, `waiting`, `blocked`, `stopped`, `crashed`, `done`), grouped under a heading per component when the project has components (see "Components"), the merge queue, CI use and the merge rule, the lines for you, the lead's full lines ("For the lead"), the state of the push builds on `main`, the last seven days merged and deployed, and usage per label. A `state.json` written by a Studio before 0.11.1 has no work list and draws this view.
  - **States.** No open item and nothing merged today: "No work yet." with an example of what to say. While paused: "Paused since HH:MM. Nothing starts or merges; running crews finish. → /studio resume". When the state is older than 10 minutes: "Last update n min ago. Is the lead loop still running? → say "start the Studio lead loop"". Paused and stale are shown above the view, not instead of it.
- **What it shows comes from `studio state`.** `state.json` carries every item that is not merged or dropped (reviews aside: their builder shows the stage) with its stage (`ready`, `building`, `pr_held`, `review`, `queued`, `blocked`), epic, components, the time it entered that stage and what it waits for (`ci_capacity` with busy, total and the merge limit, `checks_pending`, `review_pending`, `queue_held`, `queue_position`, `held`, ...); the latest tick's lead list (`needsLead`, each with a code, a short reason in Studio's own words, the full line as `detail`, and a next step to say; an item that moved after that tick is left out); the WIP limits; the merges of today with their items and epics; the project name (the repository name of `primary_repo`); and the pause with its time on the owner's clock (the zone of `crew_label_limits.timezone`, else the system zone, the same one that decides "today"). `studio tick` keeps its lead list and holds in `tick.json` in the state root for this; a tick that did not run, lost its lock or had a phase fail keeps the last good record; nothing else runs in the background. Reasons and next steps are English data; Studio's own lines (owner lines, holds, account block reasons, the queue step) also carry a code and its values (`code`, `params`; a wait's `reason`), which the pane words in its language. A line without a code shows its English text.
- **Language.** Studio ships English and German; only displayed text is translated, while commands, codes, config keys, defaults and the phrases to say to the lead stay English in every language. The pane, the status line, the toasts and the `/studio` replies follow `/studio lang <code>` when set (kept in the plugin's store; `/studio lang auto` clears it), else Claude Code's `language` setting (a code or a name, for example `"language": "german"`), else the locale (`LC_ALL`, then `LC_MESSAGES`, then `LANG`; `de_DE.UTF-8` and `de-AT` read as `de`), else English. The first of these that names a language decides: one without a locale file means English. Pushes and the notify command follow the same chain, with `notify.language` in place of `/studio lang` (see "Push notifications"), so the pane and the pushes agree unless you set them apart. Numbers, plurals, decimals, the cost and the duration units follow the language too (`Intl`).
  - **English everywhere:** `/studio lang en` for the pane and `notify: { language: en }` in the owner config for pushes.
  - **Adding a language** is one file: copy `hooks/locales/de.ts` to `hooks/locales/<code>.ts` (the ISO 639 code, two or three lower-case letters), set `code` and `names` (lower-case names a `language` setting may use), translate the texts, and run `pnpm locales` (or `pnpm bundle`, which runs it) to write the registry `hooks/locales/index.ts`. The code then works in `/studio lang`, `notify.language`, the setting and the locale. Every text left out shows in English; list keys you leave to English on purpose under `english`, so the parity test (`test/i18n.test.ts`) accepts them. Commands and phrases to say stay English.
- **Status line.** `● N working · N waiting · N queued · CI x/y · for you: n`, with `· paused` while paused.
- **Toasts.** One toast per refresh, only for lines that are new since the last one shown: a line for you, an account block, a red build on `main` and a crew that crashed and was not healed. A `usage-limit` line toasts once while it stands. Titles have control characters stripped.
- **Group view** (`/studio group`, a project of a group only): one line per project, its id with the words `main` and `here`, and its counts by sign (`! decisions`, `● running`, `◷ waiting`, `■ blocked`, `○ ready`, or `✓ nothing open`); above them every lead decision of every project in one "Decision needed" block, each as `! <project> · <id> <fixed phrase>` with `→ /studio group <project>` under it. `/studio group <project>` opens that project's work list from its own state file, read only, with `Group <name> · back: /studio group` on top; the status line and the toasts stay this project's; `/studio list` comes back. A pane too narrow for the counts beside the id puts them on a line of their own, four cells in; an id is never cut. A project whose state cannot be read says so on its line. Example, 60 columns:

  ```text
  Group shop                                 updated 1 min ago
  ! 2 decisions needed

  Decision needed
  ! platform · APP-15 fix limit reached – decide
    → /studio group platform
  ! web · WEB-3 merge failed
    → /studio group web

  platform (main, here)                     ! 1  ● 2  ◷ 1  ○ 3
  web                                                 ! 1  ■ 1
  mobile                                          no state yet

    → open a project: /studio group <project>
  ```

- **Commands.** `/studio` opens the pane and always places it. `/studio list`, `/studio pipeline`, `/studio more` and `/studio group` switch the view and open the pane; the choice is kept in the plugin's store for the next session. `/studio lang <code>|auto` sets the language (the usage text lists the shipped codes, `de|en|auto`). `/studio status` prints the status line text. `/studio pause` and `/studio resume` only print the terminal command to run, because pausing needs a terminal (`studio pause`, `studio resume`). `/studio off` turns the board off in this session only (the pane closes, the status line clears, no toasts, nothing is read; the command stays), `/studio on` turns it on again; the choice holds until the session ends, also over a plugin reload.
- **Nested worktrees.** A session in a git worktree nested under a Studio project (its folder's `.git` is a file, and a folder above it holds `.studio/studio.yaml`) finds that project's board as any session below it does, so by default it shows the parent's board. With `pane: { nested_worktrees: hide }` in the owner config such a session starts with the board off: no pane, status line or toasts, while `/studio on` brings it back for that session. The default is `show`. The project's own session and every other session are unchanged. The mod reads this one key of the owner config itself, without a YAML library (block or flow form, comments allowed); anything it cannot read counts as `show`.
- **Where it reads.** The plugin reads `state.json` and `pause.json` from the project's state root (see below), not from `.studio/`, every 10 seconds. At session start it opens the pane by itself only when the terminal is wide (about 144 columns); in a narrower one it waits undrawn until you run `/studio`.
- **Keeping it fresh.** Only `studio state` writes `state.json`. The lead's heartbeat (`studio status` and `studio state` every 120 s, and `studio tick` in a loop of its own, see the lead skill) refreshes it and also reads crew logs, so an account block stops crews at most one heartbeat (120 s) after the event. Without a running lead nothing refreshes the board and nothing stops crews: a project with no lead is swept for a block only when another project reconciles.

`pnpm test:mod` runs the mod's tests with `claude plugin test`; it needs the `claude` CLI and is not part of CI.

## Components

A product often has parts that are developed and released on their own: an API server, a desktop app, an agent, a web app in a second repository. A project (one control room, one `.studio/`) lists them under `components:` in `studio.yaml`; projects that have nothing to do with each other stay separate control rooms. Without `components:` nothing changes.

```yaml
repos: [org/app, org/web]
components:
  - { id: api, name: API server, repo: org/app, paths: ["server/**", "shared/**"], wip: 2 }
  - { id: desktop, name: Desktop app, repo: org/app, paths: ["desktop/**", "shared/**"], wip: 1 }
  - { id: agent, name: Agent, repo: org/app, paths: ["agent/**"] }
  - { id: web, name: Web app, repo: org/web, paths: ["**"] }
```

- **Fields.** `id` (`^[a-z][a-z0-9-]{0,31}$`, unique), `name` (one line), `repo` (one of `repos`), `paths` (globs, at least one, same rules as `skills.when`) and an optional `wip`. The list, when present, holds at least one component.
- **Which component an item belongs to.** A board item may name one with `component: api`, or several with `components: [api, desktop]` for cross-cutting work; not both. An id the config does not know refuses the board, except on merged and dropped items, which keep the id they had after a component is removed. An item that names none belongs to every component whose `repo` is the item's repo and one of whose `paths` globs matches or may overlap one of the item's `paths` or `touches`. Overlap works as for touches in the planner: by the fixed part before the first wildcard, so a bare directory `server` stands for `server/**`, `server/**` overlaps `server/src/**`, and a glob without a fixed part (`**/*.ts`) overlaps every component of its repo. It errs towards counting an item against a component. In the example, an item touching `shared/**` is cross-cutting (api and desktop); one touching only `docs/**` belongs to none. An item with no `paths` and no `touches` belongs to no component unless it names one.
- **WIP.** `wip` is the most items of that component in `assigned` or `in_progress` at once, on top of the role's `wip`. A cross-cutting item counts against each of its components. `plan` defers an item over the limit with the reason `component <id> wip full`, so no component takes all crews.
- **Where it shows.** `studio board` and `studio status` get a component column, `studio board --component <id>` lists one component's items, `studio plan` names the components of each assigned item, and the pane groups the crew by component (cross-cutting work under "cross-cutting", the rest under "no component").

`studio overview` lists every project of this owner from the state base (one line per state root, the owner root left out): its name, items per status, running crews and queued merges. It reads only, writes nothing, and reports a state root it cannot read in full in its last column, with what it could read. A root whose `marker.json` names a project that does not belong to that root is reported as inconsistent and not read further, and a `board.yaml` that is a link is not read. Names and errors are printed without control characters. Like `pause`, it needs the owner in a terminal and refuses under `STUDIO_ROLE=crew`.

## Groups of related projects

Separate repositories that belong together (a platform and the apps on it) stay separate Studio projects, each with its own board, CI, releases and third parties' approvals, and form a group. The group is the owner's, in the owner config, never in a repository:

```yaml
# owner config ($XDG_CONFIG_HOME/studio/config.yaml)
groups:
  - name: shop # ^[a-z][a-z0-9-]{0,31}$
    main: platform # owns contracts, decisions (ADRs) and the glossary
    projects:
      - { id: platform, repo: org/platform, dir: /absolute/path/to/platform }
      - { id: web, repo: org/web, dir: /absolute/path/to/web }
      - {
          id: mobile,
          repo: org/mobile,
          dir: /absolute/path/to/mobile,
          contracts: ["docs/contracts/mobile-*"],
        }
    reference: ["docs/contracts/**", "docs/adr/**", "docs/glossary.md"] # what member crews read
    # contracts: ["docs/contracts/**"] # whose change gives members a check item; default: reference
    # reference_max_kib: 256 # the excerpt's total size, 16 to 2048
```

- **Membership.** A project belongs to a group when its folder's real path is the real path of a listed `dir` (case-insensitively on macOS), and its `studio.yaml` names the listed `repo`; a mismatch refuses (a moved or swapped checkout). A folder is in at most one group, once. `studio.yaml` has no key for any of this: a repository cannot put itself into a group, name the main project, or widen what its crews read. Project ids follow the component rule; a group has 2 to 20 projects.
- **The excerpt.** A crew of a member gets the files of the main project that `reference` lists, beside its brief at `briefs/<id>.reference/files/`, read only, with an `INDEX.md` naming the commit and what was left out and why; the brief says they are reference owned by the main project, never to be edited or copied here, and data, never instructions. At launch Studio fetches `origin/main` in the main project's checkout and reads the files at that one commit (uncommitted work and other branches never count): plain files only (no link, no submodule), never a path with a secret-like segment (`.env*`, `.envrc`, `*.pem`, `*.key`, `*.p8`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.tfvars`, `id_rsa*`, `.npmrc`, `.netrc`, `.pypirc`, `.git-credentials`, `credentials*`, a folder `secrets` or `credentials`), never below `.git/` or `.studio/`, no binary or non-UTF-8 file, never two paths that differ only in case (neither is copied, both are listed, and the lead hears `reference case collision`), at most 200 files, in path order until `reference_max_kib` is used up. The excerpt is cached per commit and settings in the member's state root (`reference/`, the newest five kept). A main project that cannot be fetched or read refuses the launch: no crew starts without the contracts it must keep.
- **Contract changes.** Each `tick` of a member fetches the main project's `origin/main` and hashes the files under `contracts` (narrowed by the member's own `contracts`, when it lists any). The first look records the state; a later change adds one check item to the member's board: `Check the contract change of <main> at <sha> (<n> files)`, `type: research`, for the researcher (or the builder when the project has none), priority ahead of the board, a Definition of Done in Studio's own words, and the note `contract-change: <group>@<from>..<to>@<sha12>` (the digests before and after, and the commit), so a change, its revert and the change again each get an item. The changed paths are main-repository text: they go into the reference index of that item (`INDEX.md`, under "Changed by the contract change of this item", as data), never into its title or Definition of Done; the list is kept in `contract-changes/<id>.json` in the state root (out of the crew's reach) and used only for the item whose note it matches. It opens no pull request: its report tells the lead what must change. The item is added under the board lock and only when no item carries that note, in any status, and the record is written after the board, so a crash in between never adds a second one. New globs in the owner config set a new baseline, not a change. A main project that cannot be read changes nothing and is listed under `errors`. `tick` prints `contractCheck`.
- **Dependencies across projects.** `depends_on: [web:WEB-3]` makes an item wait until `WEB-3` of project `web` is merged. The plan reads the other board from its folder on this machine, the working tree and never git, as the board is not committed (a plain `board.yaml`, under a `studio.yaml` that names the listed repository; boards are written whole through a rename), each board once per plan, and a launch plans again. Merged is final on every board, so a dependency seen merged stays met. It fails closed: a project that is not in the group, an item that does not exist and this project's own id are an `unknown dependency`; a board that cannot be read holds the item (`dependency web:WEB-3 unreadable: ...`), and the lead hears of it; a cycle through any number of projects (a bounded walk over the group's boards, at most 2000 items; a larger graph holds the item) is a `dependency cycle`, which the lead hears. `waiting on web:WEB-3` is a hold like a local one. A crew's pull request that changes `.studio/board.yaml` gets no approval and is blocked for the owner, like a change of the owner's blocks in `studio.yaml`: dependencies and member items there reach into other projects.
- **Epics across projects.** An epic of the main project can hold items of members: `studio epic edit E-1 --member web:WEB-3 --member mobile:MOB-2` (main project only; replaces the list; saved as `member_items`). They count in its progress (`studio epic list`, `epic show` lists them with their status, the pane's epic bar), and the epic becomes `accepting` only when they are merged too and every member board could be read; an unreadable one counts as not merged and holds the epic where it is. Its acceptance runs in the main project; the members' pull requests are not in its checkout.
- **Where it shows.** `studio state` adds the group to `state.json` (one row per project, read from their state files: counts, lead decisions as item and code, never their text), the pane draws it in the group view (see "The Studio board"), and `studio status --group <name>` prints it (`--json` too).

## Epics and the roadmap

An epic is a larger piece of work the owner asks for: a goal, the lines it is accepted by, and the items that build it. The board is the truth: epics live next to the items in `board.yaml`, and `ROADMAP.md` is rendered from it. A board without `epics:` loads and saves as before.

```yaml
items:
  - {
      id: APP-4,
      title: Invoice form in the checkout,
      type: fix,
      role: builder,
      repo: org/app,
      size: S,
      priority: 4,
      status: ready,
      dod: [a test covers it],
      epic: E-1,
    }
epics:
  - id: E-1
    title: Pay by invoice
    status: open
    goal: Customers can pay by invoice
    acceptance:
      - an invoice order reaches the backend
      - the customer gets the invoice by email
```

- **Fields.** `id` (`E-<n>`; `studio epic add` takes the next free number, a dropped epic's number is not reused), `title` (one line), `goal` (one line of plain text), `acceptance` (at least one line), optional `components` (ids from `studio.yaml`, checked like an item's while the epic is open or accepting), `status` and `history` like an item's, and `imported_from` and `notes` after an import. An item names its epic with `epic: E-<n>`; the epic must be on the board, and only a merged or dropped item may keep a dropped epic.
- **Status.** `open` until every item of the epic is merged (at least one; dropped items do not count), then `accepting` (shown as "in acceptance"): every move of an item applies this rule, and `studio tick` lists accepting epics under `epicsReady`, each with its acceptance item (the key is left out while none is accepting, so a tick without epics prints what it printed before). New work added to an accepting epic takes it back to `open`, shown as `reopened` once it has been accepting. `done` comes only with a green acceptance (see below), or from an import. `epic drop` sets `dropped` and is refused while the epic has open items; an acceptance that waits is dropped with it, one that runs refuses.
- **Commands.** `studio epic add "<title>" --goal "<text>" --acceptance "<line>"...` prints the new id; `studio add ... --epic E-1` attaches an item; `studio epic list` shows each epic with its items by status and merged of total (`--json` too); `studio board --epic E-1` lists its items; `studio epic edit E-1 --acceptance "<line>"...` replaces the acceptance lines (or `--title`, `--goal`). Adding, editing and dropping epics, and writing the roadmap, are refused under `STUDIO_ROLE=crew`.
- **Where it shows.** `studio board` gets an epic column and, below the items, each epic with its stage (`open`, `in acceptance`, `done`, `reopened`), merged of total and its acceptance item; `studio epic list` and `epic show` show the same. The pane lists the open and accepting epics, and those done in the last day, with their progress and stage above the crew working on their items.
- **The roadmap.** `studio roadmap` prints markdown: the header `<!-- generated by studio roadmap; edit the board, not this file -->`, one line per epic in id order, `- [ ] E-3 — <title> (<merged>/<total>)` (`[x]` done, `[~]` accepting, with items in progress, or imported as in progress and without items yet; `· in acceptance` or `· reopened` after the count; dropped epics left out) with its goal and acceptance as nested bullets, then the open items in no epic (review items left out, merged ones counted in one line). The same board gives the same text. `--write` writes it to `ROADMAP.md` (or `--out <file>`) through a temporary file and a rename, and refuses a file that does not start with the header unless `--force`. The target must stay inside the project by its real path (a linked folder that leads out is refused, and so is a target that is a link), not below `.studio/` or `.git/`, and `--force` takes only a `.md` file. Never edit the file by hand: edit the board and write it again.
- **Importing a hand-written roadmap.** `studio roadmap import ROADMAP.md` reads lines like `- [ ] Phase 4 — Search`, `- [~] Phase 5 – Checkout @claim:session-b` or `- [x] **Phase 3: Cart rewrite**` (separators `—`, `–`, `-` or `:`, bold markers and trailing `@` tags dropped) and plans one epic per phase not imported yet. The file must be a regular file inside the project, not a link, at most 1 MB with at most 500 phases; a line longer than 2000 characters, a phase number that is none, or a phase that would make an invalid epic is listed under `skipped` with its line and reason, and the rest goes on. Each epic gets the title up to the next separator, the goal what follows (else the title), acceptance `imported from ROADMAP: define acceptance`, `done` for `[x]`, `open` otherwise (for `[~]` with the note `in progress at import`, plus `(claim: <session>)` from an `@claim:` tag), and `imported_from: "ROADMAP.md#Phase <n>"`, so a second import skips it. A phase number that comes twice in the file is imported once and the repeat is listed as skipped. It prints the plan and writes nothing; `--write` adds the epics. It creates no items. Then give each imported epic its acceptance lines with `studio epic edit`, compare `studio roadmap` with the hand-written file, and only with nothing skipped and the owner's yes replace it with `studio roadmap --write --force`.

### The acceptance

Each pull request of an epic passed its own gate before the merge. What none of them can show is checked once the epic's items are all merged: the full E2E and browser suites on main, which no crew sandbox can run, and a review of the epic's combined diff for how the pull requests fit together and for gaps against the acceptance lines. It runs without the owner.

- **The item.** An epic that is `accepting` when 0.16 first ticks (also one from an older Studio) gets its item on that tick. An imported epic whose acceptance is still the import's placeholder (`imported from ROADMAP: define acceptance`) gets none: the lead hears `define acceptance first` until `studio epic edit` replaces it. When an epic becomes `accepting`, `tick` adds one acceptance item: `Acceptance of E-<n>: <title>`, `type: review`, `role: reviewer`, `triggers: [epic-end]` (so the full scans run), the epic's acceptance lines as its Definition of Done, `epic: E-<n>`, and the notes `acceptance E-<n>` and `acceptance-state: <hash>`. The hash names which items the epic had; the same state never gets a second acceptance item, also across ticks and crashes (the item is added under the board lock). Dropping the item asks for a fresh one. The acceptance item is no piece of the epic: it does not count in merged of total and does not reopen it. One that has not started (ready or blocked) is dropped by the next tick when its epic moved on (new work joined, or the epic is no longer accepting), with the note `superseded: E-<n> changed before it started`. It runs in the repository most of the epic's pull requests are in; pull requests in another repository are listed to the reviewer as not in its checkout.
- **The full suites.** Name them in `studio.yaml`: `acceptance: { suites: [{ workflow: .github/workflows/e2e.yml, job: browser }, ...] }`: the workflow by its file, never its display name (two workflows can share one, and a change can rename it), and the job name (letters, digits, spaces and `. _ - ( ) / :`; each matrix leg `<job> (<leg>)` counts). Studio finds the workflow's id with `gh workflow list` and its runs on the commit by that id. Every run of the workflow on the commit counts: one red run makes the suite red whatever else passed, and a file GitHub lists for two workflows fails closed. Without `acceptance:` every workflow that ran on the main commit counts, named by its file, except one whose runs there were all skipped (a path filter): that checks only what CI ran on that commit, which may not include the E2E suites (a path-filtered E2E workflow after a docs-only merge), so name the suites where you have them. A commit with no run at all is never accepted as green: after 10 minutes on it (or on a newer head) the lead gets `no CI run on main at <sha>; set acceptance.suites ... or rerun CI`. `acceptance: { suites: [] }` is the explicit choice of a repository without CI: the acceptance is then the review alone. Before anything launches, `tick` reads the suites on the head of the default branch and keeps waiting on that commit (`held`: `acceptance waits for <suite> on main at <sha>`) until all of them have completed; then it pins the commit with the note `acceptance-main: <sha>`, and only then does the plan launch the item (until then it is deferred with `ci pending`). A failed suite is a result, not a wait. A configured suite with no run on the commit is started once with `gh workflow run <workflow id> --ref <branch>` after 10 minutes (CI may still start it); the start is recorded in `acceptance-runs.json` in the state root before gh runs, so a crash never starts it twice; while that file exists but cannot be read, nothing is started and the lead hears of it. A suite cancelled or skipped there, or with no run at all, gives way to a newer head of main. `needsLead` gets a start GitHub refused, a started suite with no run after 30 minutes, and without configured suites a run with no result on an unchanged main.
- **The review.** A reviewer crew loads main at the pinned commit and gets, as data files beside its brief, the suite results and each pull request of the epic with its merge commit and files (titles are crew text). It builds the combined diff from the merge commits, runs the analyzers of the epic-end full scan over it (diff review, spec check against the acceptance lines, security, performance, bugs, dead code, the similar-bug scan; no mutation probe is owed), and reports `verdict`, `accepts: E-<n>`, `head_sha: <the pinned commit>` and `findings` (one line each, at most 20; a longer one is cut, a tab or line break becomes a space, so a finding never rejects the report). A done report without a verdict is rejected. The same report and collect path as a review: `collect` holds the report to what the launch recorded (the epic, its state, main and the suites, never taken from the report), refuses an approval with an analyzer missing, an owed one skipped, a `green:` probe or a finding, and refuses changes requested without a finding.
- **The result.** In the same board save as the move of the acceptance item: each finding becomes a `fix` item for a builder in the epic, `E-<n>: acceptance finding <k> of <acceptance item>`, with the Definition of Done "Fix the finding recorded in the acceptance report (the data file of this brief); a test shows it" and the note `finding of <acceptance item>`. The finding itself is crew text: it is kept in the item's `finding` field and reaches the builder only as a data file beside its brief (`acceptance-finding.txt`, marked as data), never in a title, Definition of Done or note. Each failed suite gets one item: `E-<n>: make the suite "<workflow file> / <job>" pass on main` for a configured suite, `E-<n>: failed suite <k> of <acceptance item>` with the name as data otherwise (note `suite: <hash>`, one open item per suite). Fix items get the acceptance's paths without `.github/` ones, so none is a CI item. From the third round that found work on (changes requested or a failed suite, whatever the verdict), the new items are added `blocked` with the note `acceptance limit reached: ...`, `tick` lists the epic in `needsLead` (`acceptance limit reached for E-<n>`) and in `epicsReopened` with `held: true`: the lead decides. New items take the epic back to `open` (`reopened`); once they are merged it is accepting again and gets its next acceptance. Without new items an approval makes the epic `done`, with `accepted: { item, sha, at }` on the epic, if it is still accepting with the same items it was launched for; otherwise the result is `superseded` and the epic's next acceptance follows. `collect` prints `acceptance: { epic, result: done | reopened | superseded, findings }`; `tick` lists `epicsDone` and `epicsReopened`.

## Capabilities

`capabilities/INDEX.yaml` says, per role, item type, stack, phase, changed path, risk tag and trigger, which skills a crew must use or may use, which analyzers a reviewer runs and which knowledge files apply. The denied list wins over everything. At launch Studio works this out, names the skills in the brief (only a named skill is used reliably) and copies only the matching files beside the brief; a crew never gets the rest. A required skill that is definitely not installed refuses the launch; an optional one reads `skipped: skill not installed`. A malformed index refuses the launch.

- **Stacks.** `studio setup stack` reads manifest files in the root and one level of `apps`, `packages`, `services`, `crates` and `libs` (the folders `init` proposes components from), proposes `stacks:` for `studio.yaml`, and stores it with `--write`. It never opens `.env` and never follows a link.
- **Per item.** Optional board fields: `risk` (`ui`, `landing`, `auth`, `security`, `data`, `migration`), `triggers` (`epic-end`, `release`), `model`. Roles can add `skills.when` entries with `paths`, `item_types`, `required` and `allowed`. A glob is limited in length, wildcards and braces (no nested braces); one over the limits is refused in a config file.
- **Model.** `roles.<role>.model`, `roles.<role>.types.<item type>` for another model per item type, and `escalate_to`. `studio escalate <id>` sets the item's `model`, which wins; the status stays as it is.

## Review

A review item has `type: review` and `role: reviewer` together, a Definition of Done and the note `review <owner/repo>#<n>`; a launch refuses otherwise. Studio reads the pull request and writes a routine into the brief, by tier.

- **Small:** at most 400 changed lines outside markdown. Diff review and spec check.
- **Large:** more lines, a risk tag `auth`, `security`, `data` or `migration`, a security-sensitive change, or a file list it cannot read completely. Adds performance, and accessibility, design and motion analyzers where they apply.
- **Security always** when a changed path concerns auth, sessions, logins, passwords, permissions, API routes, middleware, migrations, DB schema, signup, reset, OTP, upload, access policies, workflows or local actions, and when a changed file matches a glob of `merge.contract_paths` (contracts and migrations of the project). A file list that cannot be read, or a path with a control character, counts as such a change. Spellings are matched case-insensitively.
- **Later rounds and epic end.** After an earlier `changes_requested` the similar-bug scan runs; `triggers: [epic-end]` or `[release]` add the full scans.

The spec check runs last and alone and holds a mutation probe: break the guarding line in the checkout, the named test must go red, restore. An approval is refused when the test stayed green, and in the large tier or for a fix when the probe did not run.

### The gate on every pull request

Every pull request gets the full gate before the merge, and its depth scales with size and risk. The brief names each mandatory analyzer with one line on why, and each gate analyzer it leaves out with why (`- security: not run: no risk tag, no security-sensitive or contract path changed`). A small pull request that changes only docs gets diff review and spec check, no security.

| Analyzer     | Owed when                                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| diff review  | every pull request                                                                                                                 |
| spec check   | every pull request; its mutation probe must run in the large tier, for an item of type `fix` and in a fix round                    |
| security     | a risk tag, a security-sensitive path, a path under `merge.contract_paths`, a file list that cannot be read, epic end or release   |
| similar bugs | after a fix round; in the first round when diff review reports `findings` (it then looks for those patterns in the whole codebase) |
| performance  | the large tier                                                                                                                     |

The record written at launch holds what is owed (`mandatory`, `onFinding`, `probeRequired`). `collect` refuses an approval while an owed result is missing or reads `skipped:`, and names them all at once (`approval refused: no result for spec-check; mandatory analyzer skipped: similar-bugs`). The other analyzers may be skipped with a reason; the output lists them under `skipped`.

**Time limits.** Every analyzer subagent of a review has `review.analyzer_timeout_minutes` (in `studio.yaml`, 5 to 240, default 30) from its start, and the review session as a whole the minutes of all its analyzers one after another plus one share. Claude Code runs the crew's hooks inside subagents too, with the subagent's `agent_id`, and fires `SubagentStart` when one is spawned; the guard records each start (`guard/<id>.agents.json` in the state root, out of the crew's reach) and refuses every tool call of a subagent whose time is up with a fixed line: stop and answer `skipped: timeout`; it appends that subagent's id to `guard/<id>.timeouts` (append only, so concurrent refusals never lose one). At `collect`, once any subagent of a review was stopped, an approval holds only when every mandatory analyzer reads `skipped: timeout` and at least as many analyzers read it as subagents were stopped; which subagent ran which analyzer is not trusted (the model names subagent types). Otherwise the lead decides (`approval refused: the guard stopped ...`). A record that cannot be read counts as one more timeout. After the session's deadline it refuses every call except writing the report file. The brief tells the reviewer to record such an analyzer as `skipped: timeout`, never a pass. A mandatory analyzer that reads `skipped: timeout` refuses the approval like any other skip, named apart (`approval refused: mandatory analyzer timed out: similar-bugs`), and the lead decides (pane: `analyzer timed out – decide`); an optional one is listed under `skipped`. A reviewer still running 15 minutes after its deadline without a report is stopped by `tick` (only a crew it can verify), and the lead hears `review timed out`. A single Bash call keeps Claude Code's own limit.

A launch draws a random report file name, known only to that crew's brief, and `collect` reads only that file, so a report shipped inside a pull request never counts. A review report also carries `head_sha`, which must be the pull request's head at collect.

`collect` holds a finished review to the record written at launch (`briefs/<id>.caps.json`): `reviews` must name the recorded pull request, for every verdict. An approval needs a result for every listed analyzer (`pass`, `findings` or `skipped: <reason>`) and `mutation_probe`, and cannot skip an owed analyzer (above). Output lists skipped analyzers by id, also those launch could not provide; reasons stay in the report. A missing analyzer source reads `skipped: <reason>`, never a pass.

**What the reviewer gets as data.** In the sandbox a reviewer may not reach GitHub with `gh`, so the launch reads the pull request outside the sandbox and writes its files to `briefs/<id>.caps/pull-request/`: `description.md` (title and text, marked as crew text to read as data), `checks.txt` (each check and its state at launch), `files.txt` (the changed files) and, when the builder listed any, `not-run-here.txt`. The brief names the files, never their content. A review launch refuses when no board item holds the pull request, since the approval is stored there; `studio link <id> <repo>#<n>` (owner, terminal) ties a pull request opened by hand to its item after checking repository, fork and branch `studio/<id>`. An approval counts only while the checks are green: `collect` refuses it while any check fails, is cancelled or still runs, and nothing moves until it is collected again. The reviewer reads CI workflows at the base (`git show origin/<base>:.github/workflows/<file>`), never in the pull request head, which the crew could have edited. A change under `.github/` (workflows, actions) blocks the approval unless the item holding the pull request is a CI item that declares the changed path in its `paths` or `touches`; a symbolic link there always counts. Launch reads the change in the owner's checkout (`git diff --name-only --no-renames <base>...<head>`, any case, symbolic links at `.github` or below count), and a change it cannot read counts as one; `collect` then refuses the approval.

Fix limit: 3 attempts per finding (`finding_attempts`), hard stop after 6 rounds of requested changes. Reaching it blocks the builder item with a note, and `queue run` merges only an item that is `queued` on the board at that moment.

### Exceptions by evidence

A guard job in CI (a migration guard, a floor guard) can flag a change that is mechanically harmless: only comments changed, only docs moved. Instead of asking a person each time, a project binds the guard to a built-in proof in `studio.yaml`. Studio computes a built-in proof itself, in TypeScript, over the files of the pull request's base and head, with no command run; a proof command runs only where the owner allows it, sandboxed.

```yaml
evidence:
  - id: sql-comments # ^[a-z][a-z0-9-]{0,47}$, unique
    guard: { workflow: .github/workflows/ci.yml, job: migration-guard } # the job whose failure it explains
    proof: comments_only # or paths_only
    languages: [sql] # comments_only only: sql, rust, typescript, javascript, yaml, toml
    paths: ["migrations/**"] # every changed file of the pull request must lie here
    owner_only: false # true: a hit the proof does not explain goes to the owner
  - id: docs-only
    guard: { workflow: .github/workflows/ci.yml, job: floor-guard }
    proof: paths_only
    paths: ["docs/**", "**/*.md"]
  - id: migration-lint # a command of the project, sandboxed; needs allow_proof_commands in the owner config
    guard: { workflow: .github/workflows/ci.yml, job: migration-guard }
    proof: command
    command: [node, scripts/prove-migration.mjs] # no shell; the program: a name on the sandbox PATH, an absolute path, or a file of the base tree
    timeout_seconds: 60 # 1 to 600: wall clock and CPU seconds
    paths: ["migrations/**"]
```

- **The proofs.** Both cover every changed file of the pull request: one outside `paths` proves nothing, because a change elsewhere could be what the guard saw. `paths` match case-sensitively (`docs/**` never covers `DOCS/run.sh`), and a path with a control character proves nothing.
  - `comments_only`: each changed file is a plain change of a regular file in one of `languages`, chosen by its extension, in which only plain comment text was edited, added or removed, the boring case. A file with any other extension proves nothing. Code, string literals and the like, and comments with a meaning must stay byte for byte where they are. In free-form languages only "a blank here" and "a line break here" count between tokens, and a line comment always ends a line; in YAML every line of code stays byte for byte, indentation included, and only lines that hold nothing but a plain comment or blanks may come and go. A rule that names another language is refused. Shell (`.sh`, `.bash`) and Python (`.py`) are left out on purpose: a script can read its own source and line numbers in too many ways (`$0`, `LINENO`, `caller`, `eval`, `set -v`, `__file__`, `inspect`, frames, `logging`, `warnings`, encoding lines), so a comment-only diff there may change what it does. For such files the proof does not apply.

    | Language     | Extensions                    | What is content, not comment                                                                                        |
    | ------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
    | `sql`        | `.sql`                        | strings, quoted identifiers, dollar-quoted bodies (PostgreSQL, see below)                                           |
    | `rust`       | `.rs`                         | strings, byte and C strings, raw strings `r#"..."#`, char literals (told from lifetimes); block comments nest       |
    | `typescript` | `.ts`, `.tsx`, `.mts`, `.cts` | strings, templates with `${...}`, regular expressions, JSX text and attributes (not in `.ts`, `.mts`, `.cts`)       |
    | `javascript` | `.js`, `.jsx`, `.mjs`, `.cjs` | as `typescript`, JSX in every file                                                                                  |
    | `yaml`       | `.yml`, `.yaml`               | quoted scalars, block scalars (`\|`, `>`) with every line below them; both versions must also load to the same data |
    | `toml`       | `.toml`                       | basic, literal and multi-line strings                                                                               |

    Doc comments in Rust (`///`, `//!`, `/** */`, `/*! */`) are never plain: they are `#[doc]` attributes, a code block in them runs as a doctest, and derive macros put their text into the program (command-line help, API schemas). Only `//` and `/* */` prose is plain there.
  - `paths_only`: every changed path, both sides of a rename, matches `paths`.
  - `whitespace_only` is not in this version: a rule that names it is refused. It comes later.
- **SQL: PostgreSQL only, and only the boring case.** `comments_only` reads SQL as PostgreSQL does and proves nothing for anything else:
  - files: an added, deleted or renamed file, a mode change, a symlink, a submodule, a file over 2 MiB, bytes that are not valid UTF-8 (read exactly, as bytes; a byte order mark counts), a NUL byte;
  - characters anywhere in the base or the head, also inside comments and strings: a backslash (`E'...'` escapes, other dialects' strings), a carriage return not right before a line feed (PostgreSQL ends a `--` comment there), a form feed or vertical tab, and line endings that are neither all LF nor all CRLF, or that change between base and head;
  - forms: `--` without a blank after it (and so `--+` hints), a nested block comment, a block comment whose `/*` is not followed by a blank or `*` (`/*!...*/` runs in MySQL, `/*+...*/` is a hint), a backtick, a `$` that is neither a dollar quote with an ASCII tag of at most 63 characters nor a positional parameter `$1`, and anything unterminated.

  Comments with a meaning must be byte-identical in base and head and sit between the same tokens: line comments with a migration or query directive (`-- +goose Up`, `-- name: ...`, `-- no-transaction`) and any comment that names a tool (`goose`, `sqlx`, `flyway`, `liquibase`, `migrate`, `sqlc`, `noqa`, any `lint`, `ignore` or `disable`, and more; see `src/proofs.ts`). Each comment is judged on its own. The tokenizer is linear in the size of the file. When in doubt, not proven.
- **The other languages, only the boring case.** Each tokenizer reads what it can classify for sure and proves nothing for anything else (`src/proof-languages.ts`):
  - everywhere: the file rules above, a byte order mark, a line or paragraph separator or NEL (JavaScript and YAML end a line there), a bidirectional control character, and anything unterminated or unbalanced;
  - code: a backslash outside a string, and a character that is not ASCII outside strings and comments (YAML excepted);
  - Rust: a lifetime glued to a quote, a name glued to a quote or `#` that is no literal prefix, `line!` or `column!` anywhere (a moved line changes their value);
  - TypeScript and JavaScript: a `/` or a `<` that may start a regular expression or JSX as well as not, that is after `)` of `if`, `while`, `for` or `with`, after `}`, after `++` or `--`, after a postfix `!`, or after a contextual word (`await`, `yield`, `of`, `type`, ...); `<!--` and `-->`; a JSX tag that does not close as it opened;
  - YAML: a quoted scalar over several lines, a plain scalar over several lines outside a flow collection, a block scalar that is no mapping value or sequence entry, a tab in indentation, and a file that does not load or loads to other data in the `yaml` package.

  Comments with a meaning count as code, also in these languages: a shebang line, tool words (`noqa`, `pragma`, `type:`, `fmt:`, `eslint`, `biome`, `prettier`, `shellcheck`, `clippy`, `SAFETY`, `renovate`, `yaml-language-server`, `$schema`, `coding`, and more), a `#` comment that starts with a word and a colon (`# key: value`), and in TypeScript and JavaScript any `@tag` (JSDoc types count under `checkJs`), triple-slash directives, `//#`, `/*!`, `#__PURE__` and bundler hints. Line numbers in stack traces and panic messages may still move with an added comment line.

  The diff comes from git with pinned options (`-c core.quotePath=false diff --no-color --no-ext-diff --no-textconv --ignore-submodules=none --no-renames`).
- **When it applies.** Only when the rule is in `studio.yaml` at the pull request's base commit on the default branch, and the owner's checkout has evidence rules too (a rule not pulled yet applies to nothing). When a check fails and every failed check (a plain failed job; a cancelled check, a skipped required one or a commit status never) is a check of a rule's guard, `collect` (for an approval) and the merge queue judge it; any other failure fails as before. The guard job must be the same at the base and at the head.
- **Bound to one diff.** An exception holds for the pull request at exactly that base and head commit. A later push, a branch update or a moved base is another key, and the proof is computed again there. The merge queue judges again right before the merge, and reads the base commit once more immediately before `gh pr merge`: when it moved, it judges again.
- **The log.** `exceptions.jsonl` in the state root is append-only. Each entry has `at`, `outcome` (`applied` or `not_proven`), `by` (`evidence`, `lead`, `owner`), `rule`, `guard`, `repo`, `pr`, `item`, `base`, `head`, `diff` (sha256 of the diff), `proof`, and `why` for a proof that did not hold, or `reason` for a grant.
  - Each answer is logged once per rule, pull request, base and head, under `exceptions.lock`.
  - A pull request or a file that cannot be read is retried, unlogged, and after 5 tries per head goes to the lead (`evidence-retries.json`).
  - A line that does not parse never counts.
  - Where it shows: `studio exceptions` lists the log (`--json` too), `studio board` lists the exceptions of open items, and the pane's details view (`/studio more`) those of the last seven days. `collect`, `tick` and `queue run` print `exceptions` when they applied one.
- **Without a proof.** A guard hit no rule proves goes to the lead, with one line: `evidence: <job> failed on <repo>#<n> at <head> and no evidence proved a false alarm (<rule>: <why>); decide: studio exceptions grant <repo>#<n> <rule> --reason "<one line>", or a fix through a crew`.
  - At `collect` the approval waits and nothing moves; in the queue the merge fails with that line. It is not pushed to the owner's phone.
  - `studio exceptions grant` logs the lead's decision for the current head (`by: lead`). The next tick then takes the approval, or `studio queue add` queues a pull request whose merge failed.
  - A guard with an `owner_only` rule sends the line as `evidence (owner): ...`, which is pushed. It is waived only by a proof or by the owner's grant, in a terminal (`by: owner`), never by a lead's grant through any rule of that guard. An item marked `owner_only` takes the owner's grant too.
- **Who is trusted.** The lead is trusted at this point: it runs as the owner. `owner_only` tells the owner's grant from the lead's by a terminal, not by authentication, so it guards against a lead's mistake, not against a compromised lead session.
- **What a crew cannot do.** Crews cannot write the state root, so they cannot add to the log, and `studio exceptions grant` refuses `STUDIO_ROLE=crew`. A pull request that changes `evidence:` in `studio.yaml` gets no approval from Studio: the review item is blocked with `approval refused: ...; evidence is the owner's`, and the owner reviews and merges such a change himself. That check runs for every approval, from `studio.yaml` at the base, whatever the owner's checkout holds, and the approval waits when the check cannot be made. A pull request that adds a rule gains nothing for itself, because the rules come from the base.
- **Proof commands (`proof: command`).** A rule can run a command of the project to prove a property of the change, for example a script that checks the changed migration. Off by default: it runs only on a machine whose owner config sets `allow_proof_commands: true`, and never without the proof sandbox. Elsewhere it proves nothing, with the reason in the lead line.
  - **Where it comes from.** Like every rule, only from `studio.yaml` at the pull request's base on the default branch. The command starts in that base tree, written out blob by blob as git stores it (no `.gitattributes` processing; a tree with a link, a submodule, an odd path, more than 128 MiB or 50,000 files runs nothing), so its script is the base's too: a pull request can neither bring nor change its own proof, and one that changes `evidence:` gets no approval.
  - **What it gets.** Its cwd is the base tree. `STUDIO_PROOF_HEAD_TREE` is the head tree, to read as data only: a proof command must never execute head content (a script, a config, a plugin, a build), or the pull request decides its own verdict. `STUDIO_PROOF_DIFF` is the diff, `STUDIO_PROOF_FILES` the changed paths (NUL-separated), plus `STUDIO_PROOF_RULE`, `_REPO`, `_PR`, `_BASE`, `_HEAD` and `STUDIO_PROOF_NONCE_FD=3`. Both trees are bare, with no installed dependencies: use programs on the sandbox PATH or self-contained scripts.
  - **How it proves.** By exiting 0 and printing a line `proven <nonce>`, with the nonce drawn for that run. The nonce comes on file descriptor 3, never in the environment: read fd 3 to the end and close it before starting anything (`readFileSync(3, "utf8")` in Node), so no child can read it. Any other exit, a missing line, more than 1 MiB of output or the timeout means not proven. A start or extraction failure is retried like an unreadable pull request. A command that answered on a diff never runs on it again: the answer is in the log (`command` in the entry).
  - **The sandbox** (`src/proof-sandbox.ts`): Seatbelt (`sandbox-exec`) on macOS, bubblewrap (`bwrap`, from `/usr/bin` or `/usr/local/bin`) on Linux, nothing anywhere else (native Windows refuses). No network. The run dir is readable and only its `tmp` is writable (HOME and TMPDIR point there). The system's programs and `crew_toolchain_paths` (checked as for crews) are readable. The home, other homes, the shared temp dirs, the state, the owner and Claude config, and on Linux everything not mounted in explicitly stay out. The environment is an allow-list (PATH, HOME, TMPDIR, a C.UTF-8 locale, `TZ=UTC`, the `STUDIO_PROOF_*` values). Limits are CPU time and file size (`ulimit`, inherited by children), the wall clock with the whole process group killed, and 1 MiB of stdout. Details and limits: SECURITY.md.
- **Server-side protection still wins.** A guard that branch protection requires keeps GitHub from merging whatever Studio waives: leave guards that may be waived out of the required checks, or the merge fails with GitHub's reason.

## Releases

`studio release <component>` is the release gate of one component: it drafts the release note, logs the announcement to the owner, collects the approvals the release needs, starts the project's release workflow once, follows the checks after the deploy and stops on red. Studio never runs a command of its own for a release and never runs the way back. Each component that ships gets a `release:` block:

```yaml
components:
  - id: api
    name: API server
    repo: org/app
    paths: ["server/**"]
    release:
      workflow: .github/workflows/deploy-api.yml # on: workflow_dispatch with an input `sha`
      post_checks: # jobs that must pass after the deploy, by workflow file
        - { workflow: .github/workflows/deploy-api.yml, job: smoke }
      migrations: ["server/migrations/**"]
      config: ["server/.env.example"] # files that declare configuration; only names reach the note
      rollback: { workflow: .github/workflows/rollback-api.yml } # or { text: "<one line>" }
      approvers: # third parties whose approval a release needs
        - {
            id: partner,
            who: "the partner's maintainer",
            for: "the partner integration",
            paths: ["server/partner/**"],
          }
      timeout_minutes: 60 # how long the release run and its checks may take; default 60
      guarded_paths: ["scripts/deploy/**"] # files outside .github the workflows run: list them
```

- **The release path.** Only `workflow`, a file below `.github/workflows/`, read from `studio.yaml` at the release commit on the default branch, never from the working tree. GitHub runs a dispatch on a branch or tag only, never on a commit, so Studio runs `gh workflow run <workflow id> --ref <default branch> -f sha=<release commit>`: the workflow must declare `on: workflow_dispatch` with an input `sha` and deploy exactly that commit. The announced record pins the blob of every workflow the release starts or names (release, post checks, rollback; each must exist at the release commit). Before it starts, Studio checks that the release commit is still on the default branch and that each workflow it starts is byte for byte the pinned one at the branch head; otherwise the lead cancels and drafts again. A block with `command`, `run`, `script`, `skill` or `steps` is refused: arbitrary commands are not supported (0.17 showed how hard it is to sandbox them). A deploy is never a crew's: an entry of `crew_allowed_workflows` that `gh workflow run` would resolve to the release, a post-check or the rollback workflow (by id, file or display name, ignoring case, against `gh workflow list`) refuses the trigger, and so does a display name in that list. A pull request that changes one of those workflow files, a component with a release (its whole entry), or `crew_allowed_workflows` while a release exists gets no approval from Studio: the owner reviews and merges it.
- **What the workflows run.** A release workflow runs more than itself: other workflows, actions and scripts. Once any component has a `release:` block, everything below `.github/` is the owner's, the scope the release pins, and so is all of `studio.yaml` except `stacks` (read camelized, so `crewAllowedWorkflows` beside `crew_allowed_workflows` changes it too; a key in two spellings is refused): a pull request that changes any of it gets no approval from Studio (approval only; merges by hand are branch protection's business). **The owner must list in `guarded_paths` every script the release, post-check and rollback workflows call outside `.github`** (deploy scripts, migration runners, infrastructure files); those are the owner's the same way, and Studio cannot find them by itself. The announced record pins the tree of `.github` and the files `guarded_paths` match at the release commit; the trigger refuses when either differs at the release commit or the branch head. A symbolic link or submodule points where the pin does not reach, and a wildcard glob may reach one anywhere: while a release is drafted or triggered the repository may hold none at all, and a pull request that adds one gets no approval. The rollback workflow is pinned like the workflows Studio starts: the trigger refuses another one, and before Studio shows the way back after a red release (`needsLead`, `release show`) it checks the pin again; a rollback workflow that changed since is no longer offered as the way back.
- **The note.** For the commits since production's (the last release of the component that deployed; the first release names it with `--since <commit or tag>`): the board items of the component merged in that range, grouped by epic; the migrations in order (numbers sorted as numbers), each with its kind and risk; the configuration names the `config` files gained or lost (never a value); the way back (the `rollback` text, or the rollback workflow with the commit production ran before); the post-deploy checks; the approvals it needs. `--dry-run` prints the draft and changes nothing.
- **Migration kinds.** Studio reads `.sql` files with the conservative SQL tokenizer of the evidence proofs (comments out, literals as one token) and an allow-list of exact statement shapes; there is no SQL parser. `additive`: every statement matches one shape from its first token to its last: `CREATE TABLE <name> (<columns>)` with plain columns (types, `NOT NULL`, a literal `DEFAULT`, keys and references), `CREATE [UNIQUE] INDEX CONCURRENTLY ... ON <table> (<columns>)` by column name, `ALTER TABLE ... ADD [COLUMN] <name> <type>` with a literal `DEFAULT` (a `NOT NULL` needs one), `CREATE TYPE ... AS ENUM (...)`, `CREATE SCHEMA <name>`, `CREATE SEQUENCE`, `ALTER TYPE ... ADD VALUE`, `COMMENT ON <object> IS '<text>'` and `SET lock_timeout` or `statement_timeout`. With a risk note (`lock` or `fails_on_data`, shown in the note and the announcement) and `unclear`: an index without `CONCURRENTLY`, a `NOT NULL` column without a default, a serial or identity column added to a table. A directive comment (`-- no-transaction`, `-- +goose ...`), a transaction statement (`BEGIN`, `COMMIT`), whitespace that is not ASCII, and a keyword where a column name belongs make the file `unclear`; `ALTER TYPE ... RENAME` is destructive. Files that look like a schema change (`schema.prisma`, `alembic/`, `*migrat*`, `.sql`) outside `release.migrations` get a warning in the note. A query (`AS`, `SELECT`, `WITH`), a copy (`LIKE`, `INHERITS`, `OF`), a partition, a computed (`GENERATED`) or non-literal default, a check, a cast, a call in parentheses, an index expression or predicate, triggers, rules, functions, `DO` blocks and every other statement are `unclear`. `destructive`: `DROP`, `DELETE`, `TRUNCATE`, and an `ALTER` with `DROP`, `RENAME` or `TYPE`. `backfill`: `UPDATE`, `INSERT`, `COPY`, `MERGE`. `unclear`: everything else, a file the tokenizer cannot read for sure, a file that is not SQL, an existing migration that changed or was deleted, and any other `.sql` file or file that looks like a migration (a path segment with `migrat`) below the component but outside `migrations`. Only `additive` is low risk; every other kind needs the owner. It errs that way: a column named `type` makes an `ALTER TABLE` destructive.
- **The announcement.** The first `studio release <component>` writes the release (`<component>-<n>`) with its note and logs one sentence for the owner: what is deployed, at which commit, through which workflow, and what cannot be undone (data a destructive migration or backfill changes, or simply that a deploy can only be followed by another). It prints the sentence as `announce`, and pushes a fixed phrase with the release id to the owner's phone itself, at once (no quiet hours, no throttle); the record keeps how it went (`notify: sent`, or `not_configured` when no notifications are set up). A push that did not go out is retried by the next tick. Nothing starts in that call, and the trigger waits until the announcement is recorded and a tick has run since, or 5 minutes have passed. The sentence also names a migration that locks a table or can fail on existing rows.
- **Approvals.** A migration that is not `additive` needs the owner: `studio release approve <id> owner --said "<words>"`, in a terminal only. A third party in `approvers` (always, or only when the release changes one of its `paths`, wherever in the repository) is asked through the lead: Studio contacts no one. The lead asks the owner, and records the answer with `studio release approve <id> <approver> --by "<who said it>" --said "<their words, verbatim>" --at <when>`; the time may not lie before the announcement or in the future, and text shaped like a credential is refused. Approvals belong to one release and never carry over. `tick` lists what waits in `needsLead` (`release approval: ...`), which is pushed to the owner.
- **The trigger.** The next `studio release <component>`, once the approvals are in, while Studio is not paused and CI is within the merge rule (`merge_max_busy`, read twice `check_twice_seconds` apart, as before a merge). The capacity read comes first; then the checks above; then the branch head is read once more, and a head that moved since the checks holds the trigger. Studio writes the trigger to the record and only then asks GitHub, so a crash in between never starts the workflow twice: a trigger without a known run is looked up (the one dispatch of that workflow on the branch since the trigger) and never repeated; none after 10 minutes, or several, goes to the lead, and the timeout fails it. Only a dispatch GitHub refuses with an HTTP 4xx fails the release as "nothing was deployed"; a timeout or any other exit may have started it, so it stays triggered and is looked up. The release run must be of the checked head; a run of another head fails the release before anything counts as deployed. Refused under `STUDIO_ROLE=crew`; the lead triggers as `lead`, the owner in a terminal as `owner`.
- **After the deploy.** `tick` (and `studio release <component>`) follows the release run, then the `post_checks`: a job of the release workflow from its run, a job of another workflow from a run Studio starts once after the release run passed (recorded first, `-f sha=` as well), only while Studio is not paused and CI is within the merge rule, only with the pinned workflow file at the branch head, and with its run held to that head. A passed release run counts as a deploy in the metrics (`deployed`, with the release). Every check must pass: a failed job, a job missing from a completed run, a run of another workflow or event, and no result within `timeout_minutes` all stop the release (`failed`), and `needsLead` gets `release failed: <id>: <why>; ...; Studio runs nothing back; the way back: ...` for a day, pushed to the owner. The way back is the lead's decision.
- **Runs that are not the release's.** The trigger records the newest run id of the release workflow before the dispatch; only a later run can be the release run (a run URL gh prints included), so a run another person or an earlier release started is never adopted. While a run of a workflow Studio would start is queued or running, the start waits.
- **An unknown outcome.** A release that failed after its trigger without a confirmed deploy (its run never found, never confirmed, or completed red, which may have deployed part) is "possibly deployed": its `release failed` line says "unknown whether <sha> is deployed", and no new release of the component can be drafted until the lead or the owner checks production and runs `studio release resolve <id> --deployed` or `--not-deployed --reason "<what was checked>"`. A resolved deploy counts as what production runs.
- **The workflow.** A workflow Studio starts (release, post checks) may run on `workflow_dispatch` only, never also on `push`, `schedule` or `workflow_call`, and must use `inputs.sha`; post-check starts go through the same checks as the trigger (pins, links, crew list, runs on their way, the head read again). `crew_allowed_workflows` counts from the release commit, the branch head and the owner's live config together.
- **States.** `announced` (ready to trigger), `approvals` (waiting), `triggered`, `checking` (deployed, checks running), `done`, `failed`, `stopped` (`studio release cancel <id> --reason "<line>"`, before the trigger only). `studio release list` and `studio release show <id>` read them; `studio board` lists the open ones, `state.json` and the pane's details view (`/studio more`) those of the last seven days.
- **Records.** `releases.json` in the state root, changed under `releases.lock` (one release command at a time; `recover` breaks a stale one), and `releases.jsonl`, an append-only log of announcements, approvals, triggers and outcomes. Crews cannot write either. A pull request that changes a component's `release:` block gets no approval from Studio, like one that changes `evidence:`: the owner reviews and merges it himself.
- **Not covered.** A release of several components at once, a release from another branch than the default, and a release skill: one named workflow per component.

## Migration numbers

When the lead hands database migration numbers to several sessions, a number promised only in chat can go out twice: main and the open pull requests show only what is pushed. Studio keeps a register of reserved numbers per project, in the lead's state root (never in git, out of every crew's reach).

```yaml
migrations:
  dir: server/migrations # the folder, relative to the repository root
  number_pattern: '^\d{8}(\d{6})_' # one capturing group: the number (default '^(\d+)_')
  # repo: <owner/name> # one of repos; default: primary_repo
```

Each file or folder directly in `dir` is one migration (`0042_x.sql`, or a folder such as `20240101120000_init/`); the pattern runs on its name, and its one capturing group must be digits (at most 15). `^(\d+)_` reads `0042_x.sql` as 42; `^\d{8}(\d{6})_` reads `20261027000039_some_name.sql` as 39; `^V(\d+)__` reads Flyway's `V7__x.sql` as 7. A pattern with no or several capturing groups, or one that repeats a group that repeats itself (`(\d+)+`), is refused.

- **`studio migration reserve --for <who> --purpose "<text>"`** reads the numbers on the default branch and those every open pull request adds (through `gh`), then, under the register's lock, gives one above the highest of those and of the numbers held (reserved or landed). `--number <n>` asks for one: given only when no file on main, no open pull request and no reservation holds it. `<who>` is the item id, crew or session the number is for. A read of GitHub that fails reserves nothing.
- **`studio migration list`** shows each number as `reserved`, `landed` (main holds it now; marked by itself whenever Studio reads main) or `released`, and the next free number. **`studio migration release <n>`** frees a reserved number.
- **The check.** When `collect` takes a crew's pull request, and again right before the queue merges one (an external pull request queued with `studio merge` too, whose `--by` may hold the reservation), every migration it adds is checked: a number already on main under another name, reserved for someone else, or used by another open pull request (unless this item holds its reservation) blocks it with the reason. At collect the item is `blocked` for the lead and the pull request gets no review; in the queue the merge fails with the reason. A number nobody reserved and nobody uses passes. When GitHub or the register cannot be read, collect waits and the queue does not merge. What a pull request adds is read from two listings of the folder alone (GitHub's trees API): the names at its head that are not there at its merge base, so a pull request of thousands of files elsewhere costs the same and blocks nothing. A listing GitHub reports as truncated, and 1000 or more open pull requests, count as unreadable. Leading zeros do not count (`0042` is 42); a number of more than 15 digits blocks the pull request that holds it and is left out of the next free number; on the default branch it refuses `reserve`. It is never taken for a file that is no migration.
- **The limits.** Two files with one number in the same pull request pass (an up and a down migration share one); the migration tool's own check stays in charge of that. The register coordinates the lead's sessions; it is no security boundary.

## Third-party sources

Nothing with an unknown or copyleft licence is copied into this repository; MIT and Apache-2.0 content only with its notice (`capabilities/NOTICE.md`). `capabilities/SOURCES.yaml` lists every source with its licence. `studio setup sources` fetches the referenced ones below the owner root with hooks and links off; nothing from them ever runs.

Vendored content is watched upstream: a vendored source lists the upstream files it adapts under `watch:` in `SOURCES.yaml` (the platform files of `ehmo`), and `setup sources` and `sources check` fetch and judge those files like the `reads` of a referenced source; nothing of them reaches a crew. A source whose licence is `unknown` (today `better-auth`) is not used until it is cleared: `setup sources` and `sources check` leave it out (`notUsed` in the JSON), and a brief never copies it; its row reads `skipped: licence unknown`.

`studio sources check` holds one rule. `setup sources` records a sha256 for every file the source's contract reads and for its licence files. `fits`: every one of those files is byte-identical to its recorded hash. `unclear`: one changed, is new or is missing, or something could not be read; the output names the files, and a person or the lead reads the diff. `conflict`: a licence file is missing or changed. Files outside the contract are not judged, because they never reach a crew. A brief copies a fetched file only when it still matches its hash; otherwise the row reads `skipped:`. It installs nothing, not even a `fits`. `studio sources apply <id>` judges the candidate again and adopts only a `fits`; there is no command that adopts a held update.

## Skills and updates

**Only the skills the matrix names.** A crew gets exactly the skills `capabilities/INDEX.yaml` and the role's `skills:` name for its item: required, offered and required-when-installed, plus `studio:studio-crew`. Every other skill installed in the crew's Claude config dir (user skills, plugin skills and commands, from the install paths in `installed_plugins.json` and from the plugin cache) is denied in its session settings as a `permissions.deny` rule `Skill(<name>)`, together with the denied list. A plugin skill is allowed only by its full `<plugin>:<name>`; a bare name in the matrix allows only a skill without a plugin, and the matrix writes every plugin skill with its plugin (a test holds it to that). An offered skill counts as installed only under that exact name. A skill is named by the `name` of its `SKILL.md` front matter, read with the YAML parser as a strict subset: exact `---` lines at the start, a map with plain string keys and unique keys, no anchors, aliases, tags or merge keys anywhere, and `name` a plain top-level string; other keys may hold nested blocks such as `metadata:`. Its directory name is denied as well. A command below `commands/` is named by its path with `:` (`commands/db/migrate.md` is `db:migrate`), and its bare file name is denied as well. It fails closed: an installed skill or command whose name no rule can hold (spaces, brackets, a leading dot), a `SKILL.md` that cannot be read for sure (two `name` keys, a list, no closing line, no YAML, blank lines before it, over 256 KiB), or a command entry Studio cannot map (another extension, a link, an unreadable folder) refuses the launch, naming where it sits. Claude Code has no skill allowlist that holds under `--permission-mode bypassPermissions`: allow rules have no effect there, deny rules hold in every mode (https://code.claude.com/docs/en/permission-modes), so the list is built from what is installed. Skills bundled with Claude Code itself are not on disk: they count as present, and each one the brief does not name gets a deny rule from a fixed list (the "Skill" entries of https://code.claude.com/docs/en/commands, plus `security-review`). The crew settings also set `syncClaudeAiSkills: false` and `syncClaudeAiPlugins: false`, so nothing synced from a claude.ai account reaches a crew. A missing required skill refuses the launch, as before. A missing offered skill does not: the brief names it under "Offered but not installed", and `collect` prints it under `skillsMissing`.

**Pinned plugin versions.** `plugins:` in `.studio/studio.yaml` pins each plugin crews need at one exact version, over the defaults (`superpowers@superpowers-marketplace` and `studio@studio-marketplace` at Studio's own version). studio.yaml is repository content, so it can only set versions: it cannot change the marketplace of a default (that refuses `setup-plugins`, the launch and the skills check), and it cannot add a plugin or marketplace of its own. Extra plugins come from `allowed_plugins` in the owner config, outside every repository, with their marketplace; one studio.yaml names without that is never installed, and `setup-plugins` and `doctor` say so. A change of `.studio/studio.yaml` in a pull request always gets the security analyzer.

```yaml
# .studio/studio.yaml
plugins:
  - { name: superpowers@superpowers-marketplace, version: 7.0.2 }
  - { name: pg@aiguide, version: 1.2.0 }
# owner config ($XDG_CONFIG_HOME/studio/config.yaml)
allowed_plugins:
  - { name: pg@aiguide, marketplace: "https://github.com/<owner>/<repo>" }
```

`claude plugin install` takes no version (https://code.claude.com/docs/en/plugins/cli-reference), so `studio account setup-plugins` adds the marketplaces, installs the plugins, reads `claude plugin list --json`, runs `claude plugin update` once for a plugin at another version, and fails naming both versions when it still differs. Claude Code records each install with its version in `<config dir>/plugins/installed_plugins.json` (https://code.claude.com/docs/en/plugins/loading); a launch reads it and refuses while a pinned plugin is installed at another version. `studio doctor` shows each pin with the installed version.

**`studio skills check`.** Compares each pin with what its marketplace offers (`claude plugin marketplace update` and `claude plugin list --json --available` in the crew config dir, nothing installed) and runs `sources check`, the watched upstream files of vendored content included. Versions from marketplaces and from the CLI are untrusted: one that is not a plain version (`^[0-9A-Za-z][0-9A-Za-z.+-]{0,63}$`) is dropped and named under `problems`, never written into a title, note or output, and table output has control characters replaced. Each update becomes one board item, a `chore` for a builder: `Update <name> to <version>` or `Review upstream change in <source>`, with a Definition of Done to compare the change, run the stored skill scenarios in `test/skills/` against it where they apply, propose the adaptation of Studio's own rules, and adopt only after a green review. An update already on the board (by its note `skills-update: ...`, in any status) gets no second item. A security update gets priority 0: one whose marketplace entry names an advisory (`security`, `CVE-`, `GHSA-`, `vulnerability`, `advisory`, or `security: true`), or one the lead names with `--security <name>`, which also raises an open item to 0. A source that cannot be judged (not fetched, upstream unreadable) is listed under `problems`, not as an item. `tick` runs the check at most once in 30 days per project (`skills-check.json` in the state root holds the last run) and lists what it added under `skillsCheck`; `skills check` alone says when it is due next, `--now` and `--security` run it at once.

## Role memory

`.studio/roles/<role>.md` holds the role's brief and a `## Lessons` section of at most 40 lines. `collect` stores a report's lessons as proposals in the state root (`lessons.json`), with the report and the pull request of that run as evidence; only `studio lessons accept <n>` moves one into the file, which the lead then commits. Lessons are crew text: `lessons list` says so and shows each with its age, source item and evidence, each is reduced to one plain line (control and format characters, escape sequences and leading markup removed), `accept` copies only that line into the file, never the evidence, and a brief shows them in a labelled data block apart from the role's instructions. Nothing in a proposal is ever run.

**Lessons review.** Once a week `tick` (or `studio lessons review --now` at once) bundles what is pending: proposals of one role whose text is the same once case and punctuation are ignored become one, the oldest, which keeps the others' items and evidence (`alsoFrom`). Then each role with pending proposals and no open review gets one board item, `Review crew lessons for <role> (<n>)` (`chore`, role `researcher`, notes `lessons-review: <role>` and the proposal numbers, never their text). Its Definition of Done: judge each proposal against the role file and its evidence, accept the ones that hold beyond their one run, drop the rest with `studio lessons drop <n> --reason "<one line>"`, keep the Lessons within 40 lines (`lessons prune` first when full) and commit the role file. `lessons accept` refuses a crew, so the item is the lead's: the planner never assigns it (`held` with `lead work: ...`) and it is not pushed to the phone. `tick` lists open ones under `lessonsReview` with how many proposals still wait, and closes an item, as `merged` with the note `judged: <a> accepted, <d> dropped`, once each of its proposals was accepted, dropped or folded into another; that tick prints it under `lessonsJudged`. Verdicts and reasons stay in `lessons.json` (`judged`, the last 500).

## Recovery after a crash or restart

After a crash of the lead session or a restart of the machine, the next `studio tick` picks up the thread without starting anything twice, and `studio recover` runs the same checks explicitly, with more of them, and prints what it found (`findings`, each with `check`, `subject`, `found` and, when it acted, `did`) and what needs the lead (`needsLead`). `studio recover --dry-run` only reads. Both are safe to run again: a second run finds nothing left to do. `recover` refuses under `STUDIO_ROLE=crew`.

- **Locks.** Every lock (`tick`, `queue.run`, `queue.json`, `board`, `ci-reruns`, `lessons`, `costs`, `crew` in the state root; `launch`, `limits`, `blocks`, `push`, `notify`, `migrate` in the owner root) records the holder's pid, its process start time and a heartbeat. A lock counts as stale when its pid is not running, or when the pid now belongs to another process (the start time differs, as after a reboot); the next taker breaks it with a note. A live holder whose start time matches is never broken, however long it has been silent; one whose start time cannot be read (or that recorded none) is taken over only after a very long silence (four times its usual limit, at least an hour). A lock without a pid goes by its heartbeat. A queue run whose lock was taken over anyway stops before its next step, and a launch beats its lock before and after the clone. `recover` lists every lock that is held (`silent <n> min, holder alive` when it has been quiet) or stale and breaks only the stale ones. `crew.json` is changed only under `crew.lock`, so a launch, a stop and a reconcile in different processes never lose each other's records. It also removes what a cut-short write or lock break left at the top of a state root: a `*.tmp` file whose writer is gone, a `*.stale` file older than a minute.
- **Launches.** The crew record with its pid is written right after the start, before anything else. A launch cut short before the start leaves the item `ready`, and the next tick launches it once (the clone is reused or made again). One cut short after the record leaves a `ready` item with a crew started for it: `tick` moves it to `assigned` with that crew, as the launch would have, and never starts a second one. This repair waits while any launch holds the launch lock, and while a record without its start time is younger than 2 minutes (a launch may still be writing it); a launch that finds its item already moved to its crew counts as done. A record whose start time was not read yet counts as unverified: no signal, the lead decides.
- **Crews.** A crew that ended while nobody watched is collected by the next tick when its report holds; without a report it goes to `needsLead` (`studio stop <id> --requeue`) and is never relaunched by itself. An `assigned` or `in_progress` item without any crew record goes to `needsLead` too: to drop it when its log is quiet, or to look by hand first when the log was written in the last 30 minutes. `collect` stores a report's lessons before it moves the item, so a failed move loses none.
- **Merges.** The queue records each step before it runs it. A run killed after GitHub merged but before the board moved resumes at that step; it reads the pull request first and books it as merged, never merging twice. A result recorded but not put on the board is applied by the next run. An item in review that the queue already holds (`queue add` stopped between the queue entry and the board) is moved to `queued` first. A `queued` item the queue holds neither as entry nor as result goes to `needsLead`.

## Workers on other machines

Some work cannot run on the lead's machine: real hardware, an installed program to analyse, a toolchain of another operating system. An item can name a worker label, and a machine that serves that label runs it. The lead's machine and the workers share nothing but GitHub.

```yaml
# .studio/board.yaml, an item
runs_on: windows
# .studio/studio.yaml: what crews of that label must never touch (optional)
workers:
  windows:
    deny: { paths: ['D:\data', 'C:\ProgramData\Backup'], ports: [5432] }
# owner config on the lead's machine: whose claims count, per label, by login and account id
workers:
  accept: { windows: [{ login: worker-login, id: 1234567 }] }
# owner config on the worker machine: whose offers it takes, its own deny list, places it opens
workers:
  self: {
      lead: lead-login,
      lead_id: 1234567, # the lead's numeric account id (gh api users/lead-login --jq .id)
      deny: { paths: [/srv/backup], ports: [5432] },
      allow_read: ['C:\analysis'],
      lease_minutes: 30,
    }
```

The account id is what counts: a login can be renamed and then taken by someone else. Read it with `gh api users/<login> --jq .id`.

- **Which items.** `runs_on` takes a label (`^[a-z][a-z0-9-]{0,31}$`) on a `feature`, `fix`, `chore`, `docs` or `research` item of a builder, designer or researcher. Reviews, acceptances and releases stay with the lead; `plan` blocks them otherwise. The review item `collect` adds for a worker's pull request has no `runs_on`: it runs on the lead's machine as always.
- **Offer.** `plan` lists such items under `offer`, never under `assign`; `launch` refuses them. `tick` offers each one: it opens an issue on `primary_repo`, `Studio offer <id> for <label>`, labelled `studio-offer`, and locks it at once, so only accounts with write access can comment. Its body holds the item's board fields as one JSON block (id, title, type, role, repo, size, priority, paths, touches, components, `runs_on`, Definition of Done, flag, plan, notes, risk, triggers, model, epic; never status, history, dependencies or anything of the state root) and a random nonce. The item moves to `assigned` with the crew `worker:<label>`, and the offer is recorded in `workers.json` in the state root. A tick cut short finds its open offer again instead of opening a second one. Without an entry under `workers.accept` for the label nothing is offered (`held`), and an accepted account that is the account of the lead's own crew token refuses the offer. An offer takes no role WIP, no credential slot and no host load, because no local crew runs; overlaps, dependencies, component WIP, a pause, an account block and the daily cost cap hold it like any item.
- **Claim.** `studio worker --label <label>` runs on the worker machine, in a clone of the project. Each pass (every 20 to 60 seconds; `--once` for one) first goes on with the item it holds; only without one does it check whether it may claim (see below) and look for an offer that the configured lead opened and nobody else edited (GitHub's author and editor, which no client can set), whose block parses and whose item passes the board schema. It claims by creating the ref `refs/studio/claims/<id>` on `primary_repo` through the GitHub API: a commit whose message holds the claim (item, label, worker login, offer, attempt, state, lease). Creating a ref that exists fails, so of two workers exactly one wins. A ref outside `refs/heads` and `refs/tags` is no branch: it starts no workflow and shows in no branch list. The ref is only the lock: right after winning it, the worker reads the offer again (closed: it removes its ref) and posts one comment on it, exactly `studio-claim <claim commit SHA> <offer nonce>`. GitHub sets that comment's author from the worker token, and that is what proves who claimed; each takeover posts a new one, and so does every later state change (`done`, `released`), naming its exact commit. Heartbeats change no state and stay unannounced. A worker that cannot post its comment, or whose crew does not start, removes its own ref and writes nothing else: the item stays offered. A launch that is only held back (another launch, a lock) tries again on a later pass; any other refusal stops the worker.
- **May it claim.** Before every claim the worker reads its platform again (WSL interop and mounts can change while it runs) and checks: a sandbox, `workers.self` in its owner config, a token that is not the lead's, a deny list the sandbox can hold, every pinned plugin installed at exactly its pin, no account block, a Claude credential that is neither parked nor at its limit, no other launch in progress, no pause. Whatever fails holds or refuses the claim, never a claim already held.
- **After a claim.** A refusal that only means "not now" (an account block, a pause, a parked or full label, a busy launch lock) holds the worker, which tries again later; a refusal for the item (a crew that cannot start) is final for this worker. Either way the claim is given up (a first attempt's ref is deleted; a takeover puts the ref back to the first attempt, so the attempt count is not used up), and the same offer is not claimed, nor commented, again for 5 minutes (held) or an hour (refused). The whole brief, the rules included, and the crew's start come from the one `origin/main` commit the worker pinned. A `done` or `released` commit is announced by a comment; if the comment fails, the worker keeps the commit in `worker.json` and tries again with backoff until it exists. Long git calls keep the claim beating. The lead gives a claim commit two minutes for its comment before it goes to `needsLead`. The worker tells the lead by `workers.self.lead_id`, not by login.
- **Lease and heartbeat.** While the crew runs, the worker moves the claim every third of the lease (default 30 minutes) to a new commit on top of the one it wrote last, as a fast-forward only (`force: false`). A claim that someone else moved meanwhile is lost: the worker stops its crew and lets go; heartbeats of its own on top of what it saved (a worker cut short after one) still count as its own. A claim without a heartbeat for longer than its lease (plus two minutes) is free. The lease runs from the moment the lead, or another worker, first saw that claim commit, on its own clock; the dates in a commit are the writer's and never count. Then another worker of the label, or the same one after a restart, takes it over with a fast-forward from the expired commit, so two takers can never both win. A takeover is attempt 2 and starts from the pushed `studio/<id>` branch when there is one; a second expiry goes to the lead (`needsLead`), never to a third attempt.
- **Two tokens.** The worker acts with its own token, `worker-token` (`studio secret set worker-token`), and calls GitHub with it in-process (HTTPS from Node, no `gh`), so the token is never in the environment of a child process while a crew runs; only the git push for a crew without a token gets it, in its own environment. A crew gets at most the machine's crew token (`studio secret set crew-token`), to push `studio/<id>`. The worker refuses a worker token equal to the crew token, and one whose account (`GET /user`) is the crew token's. Without a crew token the crew gets no GitHub token at all: its brief says to commit only, and after it ended the worker clones the repository blob-less and bare into a fresh directory, fetches `studio/<id>` from the crew's clone into it (git never runs inside the clone), checks it against the report's `head_sha` and pushes it with the worker token, never forced. The guard refuses crew pushes to `refs/studio/*`, also as a short name git would match there, and every `gh api`.
- **Crew.** The worker launches the crew exactly as `launch` does on the lead's machine. The brief is made of the offered item and of `origin/main` alone: the project rules, `studio.yaml`, and the role text, lessons and solutions of `.studio/roles` and `.studio/solutions`, each read at the commit the worker fetched, never from its working tree. Then the sandbox, the guard, the skill allowlist per role, the pinned plugins, its own Claude account, usage limits and account blocks, and on top the deny lists (see below). Studio opens the pull request there, never the crew, so the brief asks for `pr_title`.
- **Report.** When the crew has ended, the worker reads its report under the name only the brief knew. A report that looks like it holds a credential (token shapes of GitHub, Anthropic, AWS, Slack, npm, private keys, the worker token and the crew token) is not published: the claim is `released`. So is a crew that left no usable report, with Studio's own fixed reason, never crew text from a log; a crew that ended at a usage limit or with an account block parks the label or records the block in the worker's owner root, as on the lead's machine. Otherwise the worker checks once more that the claim and its offer are still its own, checks the pushed branch head against `head_sha`, and opens the pull request, or renews the open one of the branch when it is its own and from the repository itself (an open one of another account releases the claim). Then it moves the claim to `done` with `report.md` (the exact report) and `usage.json` (tokens and cost of the run from its log) in the commit, and announces that commit.
- **Collect.** `tick` reads each claim. A live one moves the item to `in_progress` and holds it (`worker: on <login> (<label>), heartbeat n min ago`). A `done` claim is collected by the same `collect` as a local crew's: the report is parsed with the same schema, and the pull request is the one the claim names. Then the review item, the queue and the merge go on as for any pull request. A `released` claim blocks the item with the worker's reason. The run's usage goes into the day's cost ledger (`costs.json`, key `<id>@<claim time>`) first and onto the item only once the ledger took it; while the ledger is busy or unreadable the item waits for the next tick. One run counts for at most the lowest daily cap, and the lead hears of a report above it. Then the offer closes and the claim goes.
- **What the lead checks.** Nothing in a claim commit says who wrote it: its content is the writer's, GitHub matches author and committer by e-mail, and commits made through the API with a user token are unsigned. So the lead walks back from the tip of the claim to the commit that started this attempt (state `claimed`; every commit on the way names the same worker, offer and attempt, and below the tip only heartbeats) and reads the claim comments of the offer, every page; with more pages than it reads it decides nothing and asks the lead. Of them only unedited comments (`updated_at` equals `created_at`) by accounts with write access (`author_association` OWNER, MEMBER or COLLABORATOR) whose numeric id is accepted for the label and that name the offer's nonce count; anyone else's are a warning for the lead and never decide or block a claim. The first counted comment naming the start commit must be the account the claim names; a tip in another state (`done`, `released`) counts only when that account named that exact commit too. A claim without its comments, one proven by another accepted account first, an unannounced state change and edited comments all go to the lead (`needsLead`). The walk ends at the tip the lead proved before. The claim must name this offer. The pull request must come from a branch `studio/<id>` of the item's repository, its head must equal the report's `head_sha`, and its author's id (set by GitHub) must be the claiming worker's, in a fix round too: a fix round another worker takes over goes to the lead. Anything else counts for nothing.
- **Withdraw.** `studio stop <id> --requeue` closes the offer and removes the claim; the worker sees that on its next pass and stops its crew. The item gets its one relaunch through `blocked` to `ready`, as for a local crew, and the next tick offers it again. `studio drop <id>` closes the offer too.
- **Where it shows.** `studio status` lists each offer as a row with the crew `worker:<label>` and the worker's login, no pid, `alive` while the claim is live, and with `--json` a `worker` object (label, offer, claim state, attempt, last heartbeat). The pane shows the item as building with a dimmed line `worker: ...`; `tick` prints `offered`.
- **Restart.** The worker keeps the item it holds in `worker.json` in its state root (`worker.lock` keeps a second worker process off the same clone), with the repository, so going on needs no fresh config. After a crash or reboot the next pass goes on: a crew still running gets its heartbeat, one that ended is finished as above, a claim lost meanwhile is let go. A worker cut short between the claim and its own record leaves a claim that nobody beats: it expires and is taken over.

**Deny lists.** `workers.<label>.deny` in `studio.yaml` and `workers.self.deny` in the worker's owner config are joined: the repository can only add to what the machine denies, and the other way round. Paths are absolute (`/srv/backup`) or Windows drive paths (`D:\data`); network paths are refused. Each path is denied in the sandbox for reads and writes (`denyRead`, `denyWrite`) and given to the guard as a secret path. Ports are ports on the worker machine. Before every claim the worker checks that it can enforce the list, and refuses to claim anything otherwise (exit 1, with the reason):

- On WSL2 every Windows file system is denied by default, for reads and writes: the automount root (`/mnt` unless `/etc/wsl.conf` says otherwise) and every `drvfs`, `9p` or `virtiofs` mount in `/proc/self/mountinfo`. `workers.self.allow_read` opens single places on them for reads (`C:\analysis` or `/mnt/c/analysis`); a place inside an explicitly denied path refuses, the deny list wins. A worker checkout, state root or toolchain on a Windows file system refuses.
- A Windows path holds inside WSL2, and on a native worker with the Windows crew sandbox (below), where the probe must find it unreadable. Under WSL2, Windows drives ignore case, so a rule for `/mnt/d/data` would not hold `/mnt/d/DATA`: a denied Windows path denies the whole drive, and the worker says so. A path that covers the worker's checkout, state root or toolchain paths is refused, and so is `/`.
- A crew command has no direct route out; the sandbox proxy reaches only allowed hosts and refuses names that resolve to local addresses. With ports denied, every `sandbox.network_allow` entry that could still reach this machine or its network refuses the claim, judged after the host is normalised as a resolver sees it (lowercased, one trailing dot dropped, parsed as a URL host; an entry that does not parse refuses, and so does a wildcard over an IP address such as `*.<address>`, already when `studio.yaml` is loaded): an IP address in any spelling (dotted, short `127.1`, integer, octal, hex, IPv6 and mapped forms) or `localhost` without a port or with a denied one, a bare `*`, a name without a dot or with a local suffix (`.local`, `.lan`, `.internal`, `.home.arpa`, ...). The guard refuses commands that name a denied port (`:5432`, `--port 5432`, `-p 5432`, `port=5432`), as a convenience.
- Third-party software on such a machine is never changed: deny its data and backup places. Analysis results are structure, never customer data; the report schema and the credential check above hold for workers as for every crew.

**Platforms.** Claude Code's sandbox runs on macOS, Linux and WSL2; on native Windows it runs commands unsandboxed. A worker never starts a crew without a sandbox. On a Windows machine there are two ways. One: run `studio worker` inside a WSL2 distribution. It refuses under WSL1 and when signs of WSL (the kernel name, the `WSLInterop` entries, `WSL_DISTRO_NAME`, `/run/WSL`) leave its version unclear. Under WSL2 a crew could start a Windows program through interop, which runs outside the Linux sandbox, so the worker refuses while interop is on or cannot be told off (`[interop] enabled=false` in `/etc/wsl.conf`, then `wsl --shutdown`), checked again before every claim. Two: run it natively with the **Windows crew sandbox**, described next. Without that a native worker refuses.

**The Windows crew sandbox (experimental).** Not yet piloted on a real native Windows worker: use WSL2 for work you rely on until it has been. On native Windows every crew, Claude Code included, runs as a local standard user made for its job and deleted after it. `crew_user` is the name prefix of these users (at most 13 characters); each job runs as `<prefix>-<6 hex>`:

```yaml
# owner config on the Windows worker
workers:
  self: { lead: lead-login, lead_id: 1234567, windows: { crew_user: studio-crew } }
```

`studio worker windows-setup` prints a PowerShell script. Save it and run it once in an elevated Windows PowerShell as the account that runs the worker. It needs Git for Windows 2.35.2 or later and makes the local group `<prefix>s`, which carries what every crew user gets:
- an outbound firewall rule that blocks its members from every address but loopback;
- read, never write, on Node.js, the Studio plugin, Claude Code, your `crew_toolchain_paths`, and the `skills` and `plugins` folders of the crew Claude config dir (a write grant an earlier version of the script left there is taken off first);
- no logon as a batch job (no scheduled task with a stored password), as a service, over the network or by remote desktop.

It also removes the one shared crew user of earlier versions (named the prefix), with its profile and its firewall rule. Run it again after an update of the plugin, because the plugin's folder changes.

**A user per job.** Before a job the worker makes a new standard user in Users and that group (never in Administrators) with a random password nobody sees, sealed for this machine in `windows-crew.bin` in the owner config dir (only SYSTEM, administrators and your account read it). The probe and the crew run as it. After the job, and at the latest before the next user is made, the worker ends every process of the crew users, takes their places back, and deletes them: each user is disabled with a new password nobody learns first; its profile moves into an admin-only quarantine in one rename and is deleted there a bounded number of entries per run, without ever following a link or junction in it, whatever ACL the crew set. A huge profile never holds up the next job. Nothing a crew leaves in its profile reaches a later job. Only users named `<prefix>-<6 hex>` with Studio's description are ever deleted.

**Run the worker elevated.** On a native worker, run `studio worker` in an elevated PowerShell (as administrator). Only an elevated account can make and delete users and see and end every process of another user. Without one, the worker refuses to grant and to claim, and says so. The crews themselves still run as standard crew users.

**One crew at a time.** A Windows machine runs one crew at a time, across all projects of the owner: the crew user of the job, the grants and the running crew are recorded in the owner's state root, under a lock, and a launch while a crew runs is held. Before each grant Studio ends every process of the crew users it finds (by owner SID); a process it cannot end refuses the launch.

**Grants per run.** For each crew Studio grants the crew user of the job, by SID, only that run's clone, `HOME`, tmp dir and log (modify) and its brief, settings and guard context (read). A writable folder also gets an inheritable OWNER RIGHTS entry, so the crew user keeps no owner's rights over what it created. Taking a place back runs in one fixed order: first Studio ends every process of the crew users; then it removes the grant on the place and makes your account (by SID) its owner. Next it walks the place without following links and removes every link or junction a crew planted there. Only when that worked does it reset every ACL below to what it inherits and make your account the owner of everything there; otherwise it reports the place and keeps it on record. Each `icacls` call is checked and runs with `/L`. Every grant is recorded in the state root and taken off when the crew ends, when it is stopped, and before the next grant. Each run gets its own writable Claude config dir in its `HOME`, with copies of the skills and plugin lists; the shared plugins stay read-only.

**Starting and stopping.** Claude Code's own sandbox is off for such a run (it does not exist there).
- **Network:** traffic goes through a proxy Studio runs on loopback. It tunnels only to the names of `sandbox.network_allow` and `api.anthropic.com`, resolves each name itself, refuses any answer that points to this machine or a private, link-local, multicast or reserved network (also inside an IPv6 address that carries an IPv4 one: mapped, compatible, NAT64, 6to4, Teredo), and connects to the address it checked. Claude Code's optional traffic is off.
- **The keeper:** the worker starts each crew through a keeper, `studio-crew-keeper.ps1`, a PowerShell of your account. The keeper unseals the password of the job's crew user and puts `bin/studio-crew-host.mjs`, started as that user with `Start-Process -Credential`, into a job object before the host gets anything. It hands the spec, with the crew's environment, to that very host over a named pipe, so the Claude token never lands on disk. When the host ends, it takes the grants off.
- **Identity and stop:** Studio records the keeper, never anything the crew can write. The identity is the keeper's creation time, read through CIM, and only for a process of your account running the keeper file. Stopping ends the keeper, which ends the job and the crew's whole tree. The output of keeper and host goes to files in the `logs` folder of the state root, which the crew user cannot reach; links there are removed, not followed.

Deny paths on a native worker are Windows drive paths (`D:\data`); a POSIX path refuses.

**The probe.** Before every claim the worker starts a probe as the crew user of the coming job: a fresh one, unless no crew ran as the one made for the last probe. It refuses unless the probe shows all of this:
- the process runs as that user, with the SID made for this job and a profile no older than that user, and not as an administrator;
- it cannot read your profile, the owner config or any deny path;
- it cannot write your home, nor the crew Claude config dir or its plugins;
- a direct connection to `github.com:443` fails;
- the proxy refuses a name that is not allowed;
- the environment Studio set arrived;
- no scheduled task runs as the crew user;
- a place taken back stays closed: a seed run as the crew user makes a file in a granted place, the place is taken back, and the probe must fail to change that file, its ACL, or add a file there.

A failed or missing check, or no answer, refuses (fail closed). A crew launch on native Windows outside such a worker refuses as well. What this sandbox does not cover is in SECURITY.md.

**Identity.** A worker uses its own GitHub identity: the worker token of the worker machine (`studio secret set worker-token` there, a fine-grained token of a separate account, stored only on that machine). As a fine-grained token on the repositories of the project it needs Contents: Read and write (write the claim ref, push `studio/<id>` for a crew without a token), Pull requests: Read and write (open its pull request), Issues: Read and write (read offers, post the claim comments) and Metadata: Read; nothing else, no administration, workflows or actions. Its account needs write access to the repository, or it cannot comment on the locked offers. With issue write a worker could open or edit an issue: workers take only offers the lead opened and nobody else edited, and the lead ignores edited claim comments. The worker refuses a token whose login is the lead's. Studio never merges for a worker and never counts a GitHub review: approvals come from the lead's own reviewer crews, merges from the lead's queue. Protect `main` server-side so that no worker account can push to it or merge; if branch protection requires approving reviews, a worker account with write access could give one, so require a review from code owners that do not include it.

**Not covered yet.** A worker serves one item at a time and one label per process. Usage of a run counts when the worker hands it back, so a day can end above the cap by what workers were running (as for local crews), and the cost is what the worker reports, capped per run at the daily cap. A crew token with contents write can write any ref, the claim refs too; the guard refuses that, but a program a crew runs is not held by the guard. Such a claim has no claim comment of the worker, so the lead ignores it, but a writer can still move or remove a claim; give crews a token of another account than the worker's, or none.

**Claim refs and rulesets (untested, not a control).** Any account with contents write can write `refs/studio/claims/*`. It cannot forge a claim or a report that counts (the lead decides by the comments above), but it can deny one: move it, block it or remove it, which delays the item or hands it to the lead. GitHub documents rulesets for branches and tags, and a ruleset with `"target": "branch"` probably does not cover `refs/studio/*` at all. Nothing in Studio relies on one. If you try, test it: push to `refs/studio/claims/test` with an account outside the bypass list and see whether GitHub refuses. The form, in the repository's Settings → Rules → Rulesets or with `gh api`:

```bash
gh api -X POST repos/OWNER/REPO/rulesets --input ruleset.json
# ruleset.json
# {
#   "name": "studio claims",
#   "target": "branch",
#   "enforcement": "active",
#   "conditions": { "ref_name": { "include": ["refs/studio/claims/**"], "exclude": [] } },
#   "rules": [{ "type": "creation" }, { "type": "update" }, { "type": "deletion" }],
#   "bypass_actors": [
#     { "actor_type": "Team", "actor_id": TEAM_ID, "bypass_mode": "always" },
#     { "actor_type": "RepositoryRole", "actor_id": 5, "bypass_mode": "always" }
#   ]
# }
```

`TEAM_ID` is the id of the team of worker accounts (`gh api orgs/OWNER/teams/TEAM --jq .id`); role 5 is the admin role, which the lead needs to remove claims. Studio writes no `refs/studio/briefs/*`.

## Relay workers

A relay worker is a worker machine without any GitHub access: no GitHub account, no token, no credential of the lead's machine. The lead connects to it over SSH and does everything on GitHub itself; the worker only runs crews. Use it for a machine that sits next to systems nobody else should reach through it. Experimental: not yet piloted on a real native Windows machine (see SECURITY.md, "Relay workers").

```yaml
# .studio/board.yaml, an item: nothing else changes for a project
runs_on: lab
# owner config on the lead's machine: the worker of the label
workers:
  relay:
    lab:
      host: worker.example
      user: studio-relay # the default
      port: 22 # the default
      host_key: "ssh-ed25519 AAAA..." # pinned: the worker's host key, as ssh-keyscan prints it
      identity_file: /home/owner/.ssh/studio-lab # the lead's private key for this worker
      grace_minutes: 30 # the default: unreachable longer goes to the lead
# owner config on the worker, optional (on Windows config\studio\config.yaml in the admin-only tree %ProgramFiles%\Studio\relay)
workers:
  serve:
    deny: { paths: ['D:\data'], ports: [5432], hosts: [local-subnets, tailnet-peers, nas.example] }
    windows: { crew_user: studio-crew, broker: Studio relay broker } # the defaults: crew users studio-crew-<6 hex>
    max_cpu_percent: 75 # the default: busier, nothing starts
    min_free_disk_gb: 20 # the default
    probe_unreachable: ["nas.example:445"] # addresses the crew user must not reach
```

A label is either under `workers.accept` (GitHub workers, above) or under `workers.relay`, never both. A new project needs nothing on the worker: the item's `runs_on` is enough, and `workers.<label>.deny` in `studio.yaml` stays optional.

- **Start.** The plan lists the item under `offer`, as for a GitHub worker; `tick` starts it on the worker instead. It first asks the worker whether it would start anything now (`hello`): a busy worker (one crew at a time), a CPU above `max_cpu_percent` or free disk below `min_free_disk_gb` holds the item, nothing is sent and no run is counted. Then the lead pins `origin/main`, makes a git bundle of `main` at that commit (and of `studio/<id>` as GitHub has it, for a fix round), picks the Claude credential by the usual rules (provider, active account, else the environment's token; parked and full labels never) and sends the job: the item's board fields (exactly what an offer carries), the commit, the bundle and the token. The run counts on that credential's label. The item moves to `assigned` with the crew `worker:<label>`.
- **On the worker.** `studio relay serve` takes the bundle into a mirror of the repository (exactly `main` at the pinned commit and the job's branch; any other ref refuses), refuses while the machine holds any credential, checks the pinned plugins, and hands the job to a runner, a process of its own that outlives the SSH session. The runner checks again (load, sandbox, deny list, on Windows every check below and the probe as the crew user) and launches the crew as a worker does: the brief from the pinned commit, the deny lists of `studio.yaml` and `workers.serve`, no GitHub token (the crew commits only, Studio opens the pull request). The token stays in memory.
- **Following.** Each `tick` asks for the job's state. The item moves to `in_progress` while its crew runs (`worker: relay lab, crew running`). A worker that does not answer holds the item (`unreachable for <n> min`); longer than `grace_minutes`, it goes to the lead, never to a second attempt elsewhere. A start the worker held (busy, load, a check that says "not now") goes back to `ready` without using up its relaunch; one it refused is blocked for the lead with the reason.
- **Result.** When the crew has ended, the lead collects the report and a bundle of `studio/<id>` and treats both as untrusted: size caps, a credential scan of the report, the bundle unpacked into a fresh bare directory with no hooks, exactly one ref `studio/<id>`, its head equal to the report's `head_sha`, descending from the pinned commit. Then the lead pushes `studio/<id>` with its crew token (never forced), and `collect`, the review item, the queue and the merge go on as for a local crew: the lead opens or renews the pull request. The usage the worker reports counts in the day's ledger (capped per run at the daily cap); a usage limit or an account block the crew hit parks or blocks the lead's credential label. The worker then cleans up.
- **Stop.** `studio stop <id>` sends `stop` and `cleanup` to the worker (`--requeue` gives the item its relaunch); `studio drop <id>` does the same. A worker out of reach is named and not waited for: it holds no credential, so a crew it still runs can push nothing.
- **Where it shows.** `studio status` lists the job with the crew `worker:<label>` and, with `--json`, a `relay` object (label, state, last answer). `studio doctor` names each relay label: reachable or not, the worker's Studio and plugin versions against the pins, its load, and every warning of its probe (loopback listeners, SMB candidates and where they came from).

### Set up a Windows relay worker in 10 minutes

A new owner, a new project or a new PC: the same five steps. Nothing is copied between the machines but one line; a new project needs nothing on the worker.

1. **Lead: pair.** `studio relay pair lab worker.example` makes the lead's key for the worker and prints one line: `studio relay install --pair "studio-pair-1 lab <secret> ssh-ed25519 AAAA..."`. The secret in it is used once and expires after an hour: paste the line on the worker only.
2. **Worker: Studio.** Install Node.js and Studio on the Windows PC (the rest comes in the next step).
3. **Worker: install.** At the PC itself (or over remote desktop), never over SSH: the install stops sshd while it runs, and refuses in an SSH session. In an elevated PowerShell, run the line from step 1. `studio relay install` checks and, where missing, installs Git and Claude Code (winget, for the whole machine) and the OpenSSH server, and refuses Git for Windows older than 2.35.2; creates the relay account `studio-relay` (a standard user; the lead logs in as it), the group `studio-crews` of the crew users (one user `studio-crew-<6 hex>` per job, made and deleted by the broker tasks) with its firewall rule, and the broker tasks; writes the `Match User studio-relay` block into `sshd_config` (checked with `sshd -t` first) and lets only the Tailscale interface reach sshd (without Tailscale it asks for an interface or a source range: `--interface <name>`, `--source <range>`); stops and disables WebClient (it says so first); installs the pinned plugins; records the pairing and rewrites the relay account's authorized keys from the recorded pairings alone (it names every lead it authorizes, and every unknown line it removes); and ends with a summary and the **host key fingerprint** of the PC. Run it again any time: it repairs and updates.
4. **Lead: connect.** Within the hour, `studio relay pair lab --connect` connects with the worker's host key and keeps it only when the worker proves it with the pairing's secret (an HMAC of its host key that only the machine you pasted the line on can compute); then it writes `workers.relay.lab` into the owner config. It shows the host key fingerprint, which you may compare with the one the worker printed; the proof does not depend on it.
5. **Lead: check.** `studio doctor` checks everything end to end and gives one line per problem with its fix. Then `runs_on: lab` on an item is all a project needs.

Site rules (a particular LAN, a database port next to the PC, the tailnet) are optional extras for your operations: add them as `deny.hosts`, `deny.ports` and `probe_unreachable` in the worker's config (`%ProgramFiles%\Studio\relay\config\studio\config.yaml`, admin-only, which the install writes with `deny.hosts: [local-subnets, tailnet-peers]`) or as the project's `workers.<label>.deny`. Without the install, `studio relay setup` prints the same script for you to run, and the `Match User studio-relay` block to add to `sshd_config` yourself; leads are authorized only through `relay install --pair`. `studio relay unpair <label>` on the worker takes a lead's key away.

**Before every start on Windows** the worker checks: the relay account is no administrator; the crew user of the job is made (a fresh one unless no crew ran as the last one) and its credential opens; WebClient is stopped and disabled; the load; the loopback listeners (a denied port listening on loopback holds the start; others are doctor warnings); the SMB check of `deny.hosts` (each candidate's `IPC$` as the crew user: a session refuses, access denied or not found pass, any other code holds); and the probe of the Windows crew sandbox as the crew user, with no stored credential of the crew user and no direct connection to `probe_unreachable` or to neighbors. `deny.hosts` takes host names, addresses, IPv4 ranges up to /22 and two keywords: `local-subnets` (the private subnets this machine sits in, capped at /22 each) and `tailnet-peers` (the peers of `tailscale status --json`). Candidates come from the neighbor table inside the ranges, the explicit entries and the Tailscale peers; a range without any candidate refuses.

On Linux, macOS or WSL2 a relay worker uses Claude Code's sandbox as a worker does; its SSH server and forced command are yours to set up (`studio relay serve --home <dir>`). Not covered yet: one crew at a time per worker and one worker per label; a label's parallel limit does not count relay crews; a start bundle carries the whole history of `main` each time.


## Reverse engineering for the researcher

Some questions can only be answered from a shipped program or package: how does a vendor's file format work, what does an installed client store, how do two versions differ. The role `researcher` (and only it) can answer them with [REA](https://github.com/morluto/rea), an MCP server for reverse engineering, and its skill `reverse-engineer-anything`. The result is always structure, never content.

**Who gets what.** A crew starts with an empty MCP list and every MCP tool denied. A researcher whose project sets `research.artifacts` in `.studio/studio.yaml` gets exactly one server, `rea-agents` at one exact version, and the allowlist below. The skill is offered to the researcher alone; every other role is denied it by name, also when its `skills:` in `studio.yaml` or a matrix row names it. A researcher of a project without `research.artifacts` runs as before, without the skill, unless its item names its own folder: `studio add "<title>" --dod "<line>" --artifacts ~/analysis/vendor-x` files a research item for the researcher with `artifacts:` on the item, which wins over the project's. It must lie below a granted `research_roots` entry by its real path, at `add` and again at launch, or it is refused; a sub-folder of a granted root needs no new step from the owner.

```yaml
# .studio/studio.yaml
research:
  artifacts: /absolute/path/to/the/analysis/directory # the one place the tools may read
```

```yaml
# owner config (outside every repository)
research_roots: [/absolute/path/to/the/parent] # artifacts must lie below one of these, or the launch refuses
# rea_version: 6.7.0 # optional: another exact version (x.y.z) of the npm package; default pinned in Studio
rea_env: # where the analysis engines are; only GHIDRA_INSTALL_DIR, JAVA_HOME and REA_* are passed on
  GHIDRA_INSTALL_DIR: /absolute/path/to/ghidra
```

studio.yaml points, the owner config grants and pins: a pull request that changes `research.artifacts` cannot open a directory the owner has not allowed, and the whole `research:` block is the owner's for Studio's approval (a pull request that adds, changes or removes it gets none, like `evidence:`). The version of the code that runs with the owner's privileges is set only in the owner config, and only as an exact `x.y.z`. The path also goes through the checks of `crew_toolchain_paths` (not the home or a parent of it, no credential store, not the project or the state root), on its real path.

**Trust mode, the default.** The owner config says how much REA may do:

```yaml
# owner config
research: { trust: true } # the default; false: strict mode
```

In trust mode a researcher crew may use every tool class below (`annotate`, `debug`, `observe`, `device`, `export`) without `studio research allow`, and REA is installed in full, with its optional dependencies and install scripts, which the debug and observe tools need. The first launch that uses it prints one line, once per owner: REA tools run as you, outside the sandbox. `research: { trust: false }` is strict mode: the static install and the classes the owner opens per item, as described below. What holds in both modes: no `npx` and nothing installed in a clone; the server starts through Studio's wrapper with a clean environment and no token; its per-run home and temp folders are denied to the crew; every path argument is confined to the analysis folder, which lies below a granted root; research items push nothing; the privacy check runs before any pull request; artifacts never enter git; no secret goes into a report.

**Installed on first use.** When a researcher item is about to launch and the pinned `rea-agents` is not installed in the mode the owner config asks for, Studio installs it, after one confirmation per version. In a terminal (`studio launch`) it asks: `REA is not installed yet. Install rea-agents <version> now? It runs with your user rights outside the sandbox. [Y/n]`, and, when the owner config grants no folder yet, `Analysis folder for reverse engineering [~/analysis]:`, which it creates and adds to `research_roots` (comments in the file are kept). Without a terminal (`tick`, the lead) nothing is asked and nothing installed: the lead gets one decision, `REA install needed for <id>: the owner confirms once, with the button in the Studio pane or with studio research install in their own terminal` (with `(analysis folder ~/analysis)` when no folder is granted). The pane shows `REA install – confirm once, here` with a button, `Confirm REA install (rea-agents <version>, folder ~/analysis)`; a press (a click, or Enter on it, by the person: no command and no model can press it) writes the confirmation for that version and mode, with `<home>/analysis` when no folder is granted, as its own file `rea-confirm.json` in the owner state (never through a link). The next Studio command that needs REA takes it in only when it is a plain file of the owner, writable by nobody else, one whole JSON object, naming no other folder than `<home>/analysis`; it folds it into `rea-consent.json` (temporary file and rename, mode 0600), removes it, installs and grants the folder. Every new research root, from the terminal or the pane, gets the checks of `crew_toolchain_paths` (not the home or a parent of it, no credential store, not the Claude config, not around or inside Studio's state), must be the owner's own folder and not a link, and is stored by its real path. The lead cannot confirm: `studio research install` counts `--yes` and `--folder` only in a real terminal and refuses without one. The answer, yes or no, is kept in the owner state (`rea-consent.json`) per version and mode, so it is never asked again; a no refuses until `studio research install` in the owner's terminal. A new pinned version, or a switch between trust and strict mode, asks again. A crew can never install or confirm: under `STUDIO_ROLE=crew` both refuse, and the guard keeps crews from running `studio` at all. `studio research install` and `studio setup research` (and the optional sixth step of `studio setup`, asked once; a skip is kept) are manual paths to the same thing.

**Installing it.** `studio research install` installs the pinned `rea-agents` once into the owner state (`<state base>/owner/rea/<version>/`), never with `npx` and never in a crew's clone: it asks the npm registry for the version's `dist.integrity`, installs with npm's user and global config set to two distinct empty files of the staging folder (mode 0600; npm refuses one file as both), no token in the environment, in strict mode no install scripts (`--ignore-scripts`) and no optional dependencies (`--omit=optional`), and uses the result only when npm's lockfile names the registry tarball with that same integrity; it records the integrity beside the package. The earlier install is moved aside, the new one verified as a launch would, and the earlier one deleted only then (restored if the check fails). In strict mode there is no Frida and no prebuilt pseudo-terminal binary: the static tools need neither (both are loaded lazily, by debug and process-capture tools only), and the `debug` and `observe` tools that need them fail. In trust mode they come along and the record says `full`; a launch takes only an install of its own mode. A launch refuses unless that record, the lockfile and the installed package agree with the pin, and nothing on the way to the package's command is a link or writable by anyone but the owner. Crews can neither read nor write the owner state. Then the skill: `studio doctor` shows the pin and where it comes from, the mode (in trust mode all known tools are allowed; in strict mode only the static ones plus what an item was allowed), whether it is installed, how many `research_roots` the owner config grants (counted, never named), whether the optional `research.artifacts` of `studio.yaml` lies below one, whether the skill is in the crew config dir and what is registered there, and prints `CLAUDE_CONFIG_DIR=<crew config dir> node <installed command> setup --client claude_code --dry-run` (read the plan), then the same with `--yes`. A launch refuses while the skill is missing.

**How the server starts.** Claude Code starts a stdio MCP server in the session's working directory, which for a crew is its clone, and with the session's environment, which holds the crew's tokens. So the launch never names the package: the server entry is Node by its absolute path running `bin/studio-rea-server.mjs`, shipped with Studio, on a spec file in the state root. The wrapper changes to an empty directory Studio owns, and starts the installed package's command with a clean environment: `PATH`, `HOME`, `TMPDIR` and the `XDG_*` directories in the run's own folder (`<state root>/rea/<id>/`), npm's user and global config `/dev/null`, and the `rea_env` variables; no `GH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` or any other variable of the crew. REA copies what it analyses into that folder (an APK into `$TMPDIR`, for example): it is in the crew sandbox's `denyRead` and `denyWrite` and in the guard's denied paths, and `collect` and `stop` remove it when the run is over (a launch starts with a fresh one). The server runs outside the sandbox, as every MCP server does; that is why its tools are an allowlist.

**The tool allowlist.** Claude Code has no allowlist that holds in `bypassPermissions`, so it has two layers: the guard hook allows an MCP tool only if its exact name is on the crew's list (`mcpAllow` in the guard context; everything else, known or not, is denied), and the settings deny every known REA tool that is not on it. The default list is the static, read-only tools: inspecting and decompiling (`open_binary`, `inspect_artifact`, `inspect_macho`, `procedure_pseudo_code`, `batch_decompile`, `read_bytes`), searching (`search_strings`, `search_procedures`, `search_bytes`, `list_strings`, `list_procedures`, `xrefs`), call graphs and comparisons (`get_call_graph`, `compare_functions`, `compare_artifacts`, `compare_application_versions`), the platform inspectors for APK, managed code, Electron fuses, Go, Rust, WASM, PE resources and so on. Their arguments are checked too: only the argument names a tool's schema lists are accepted (`src/rea-schemas.ts`, generated from the pinned server's tool list), every string under an argument the schema declares as a path, and any string elsewhere that looks like a place (a slash or backslash, a drive letter, `.` or `..`, `~`, `file:`), must be absolute and lie in the analysis directory both as written and on its real path, through links; never the clone, which the crew can change between the check and the server's read, and never a relative path, which the guard and the server would resolve against different directories (the exception is a handful of free-text arguments such as `pattern`, at the top level of the tools that have them; Windows paths are refused for now). The crew cannot write the analysis directory, so a link in it stays as it was checked; one that leads out is refused. Schema arguments are classified by type: only strings name a place, so a number such as `max_entries` never does. A nested argument named like a place (`left.subject.local_path`, `reference.entries[].path`) is confined the same way whatever its value looks like: REA resolves a bare name against its own working directory. A write argument, judged by the words of its name (`snapshot_path`, `output_directory`, `overwrite`, ...; not `left_export_name`), with any value but unset, null, false or empty is refused; only a limit (`max_*`, `min_*`, `limit_*`) takes a number, `inspect_recorded_crash` with `include_debugger_context` needs the `debug` class, and `inspect_sqlite_database` reads schemas, not rows (`table`, `columns`, `row_limit` and `schema_scope: selected_table` are refused).

In strict mode everything else is denied unless the owner opens its class for the item: `studio research allow <id> <class>...` (in a terminal; refused for crews and without one, like `pause`), `studio research revoke <id> [<class>...]` closes it again and `studio research list` shows what is open. The grant lives in the project's state root (`rea-allow.json`), outside the repository and the board, and counts from the item's next launch; a note on the board opens nothing.

| Class      | Tools                                                                                                                                                                                                                                                                                                             |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `annotate` | writes into the analysis session or the target project's database: `set_comment`, `set_inline_comment`, `comment`, `inline_comment`, `set_address_name`, `set_addresses_names`, `annotate_native_function`, `set_bookmark`, `unset_bookmark`, `record_unknown`, `update_unknown`, `import_managed_reconstruction` |
| `debug`    | debuggers and instrumentation: all `*_frida_*`, `instrument_with_frida`, `start_gdb_session`, `gdb_console`, `start_rizin_debug_session`, `rizin_debug_command`, `execute_rizin_command`, `cutter_command` and their status and close tools                                                                       |
| `observe`  | watching a running program, page, window or the network: `capture_*`, `observe_*`, `inspect_web_page`, `inspect_electron_page`, `inspect_pcap_capture`, `inspect_packet_capture`, `analyze_web_bundle`, `correlate_static_and_runtime` and the comparisons of captures                                            |
| `device`   | every `*_adb_*` tool: listing, reading logs and settings, `install_adb_package`, `start_adb_app`, `push_adb_file`, `pull_adb_file`, `uninstall_adb_package`                                                                                                                                                       |
| `export`   | tools that write files of their own outside the sandbox: `extract_artifact`, `extract_firmware`, `export_evidence_bundle`, `export_web_scripts`, `recover_javascript_sources`                                                                                                                                     |

The shell follows the same classes: without `debug`, `observe` or `device` the guard refuses `gdb`, `lldb`, `frida`, `strace`, `tcpdump`, `tshark`, `adb` and the like.

**The analysis directory.** Bash never touches it. It is in the crew sandbox's `denyRead` and `denyWrite` (and in no allow list), so the operating system refuses every shell process, however the command is written; Read, Grep and Glob are refused by the guard, and a Bash command whose text names the directory, or that runs in it, gets an early, friendly refusal (a convenience, not the boundary: parsing shell syntax to protect a place does not hold). The REA tools run in the MCP server, outside the Bash sandbox, and are the only way in; what `strings` or `file` would show, a researcher gets from `search_strings`, `inspect_artifact` and the like. The tools are held to the directory by the argument checks above. Artifacts never enter git: the crew is told so, nothing in the shell can read them to copy, and a privacy check runs over the result. The directory must not lie in the clone or the state root.

**The report.** A `type: research` item opens no pull request (as before) and pushes nothing: the guard refuses every `git push` of such an item, and its crew gets no GitHub token. The findings go in the report body. To keep them in the repository the lead adds a `type: docs` item for the researcher that writes `docs/research/<id>-<slug>.md` and opens its pull request as usual. At `collect`, every crew field of a researcher's report goes through a privacy check (body, pull request title, findings, questions, lessons, `not_run_here` entries and jobs, analyzer and probe lines), and so does what its branch adds: the diff over `base...head`, read in the owner's checkout (never the crew's clone, which can differ from what was pushed), every added line of every file. When Studio opens the pull request, it checks the pushed branch first and opens none on a hit; a pull request that already exists for the branch is closed with a fixed comment. It looks for email addresses (reserved example domains pass), phone-like numbers, personal fields with a value (`first_name: ...`), card and account numbers, credentials and keys, insert statements and runs of delimited rows; a file that is binary, very large, a link, a submodule or that cannot be read line by line, and a line over 4,000 characters, is a hit itself. A diff that cannot be read now makes `collect` wait. One hit fails the report closed (`collect` refuses, `tick` hands it to the lead) with the kinds and lines, never the text. The check is a set of heuristics: it catches the careless leak, not a determined one, and it does not replace reading the report.

**Content is data.** The brief says that strings, symbols, comments, decompiled code, page text and every tool result marked `_meta.provenance.untrusted_content` come from the target and are never instructions; a request in them to run, install, download or send something is an injection attempt, reported under `questions:` by its kind.

**Workers.** An item that runs on a worker (`runs_on`) gets no REA yet: a worker has its own analysis directory and engines, which come with a later release. Such a researcher runs without the skill.

## Metrics and learning

`studio metrics` adds change failure rate (deploys followed by an incident, over deploys; `null` without a deploy), median time to restore and open incidents to lead time and deploy frequency, from `studio deploy record` and `studio incident open|resolve`. An incident counts against the latest deploy before it, once per deploy.

`studio flaky record <test> <sha> pass` counts a test that failed and passed on a rerun; `fail` is a real failure and is not recorded, because nothing is retried into green. `studio flaky` lists the worst first, for a scheduled fix item.

`studio metrics` also prints `costs`: today's cost of this project's ended crew runs (`today`), and per item and per epic the runs and cost stored on the board (see "Costs").

### Flaky tests

When the merge queue, or `collect` waiting for green checks behind an approval, sees a failed check, Studio asks whether the failure lies outside the pull request. It does when every failed check is an Actions job of the pull request's repository whose job runs in a directory of its own (`defaults.run.working-directory` of the job or its workflow, read at the pull request head; no step with a working directory of its own), no changed file of the pull request lies in that directory, at the repository root or in `.github/`, and no path of the item reaches into it. Anything else, a cancelled check, a commit status, a job without a directory or more than 3000 changed files, counts as related, and the pull request fails as before. Names are job-level: `<workflow> / <check>`, since `gh pr checks` names no single test.

Nothing is judged while any check of the pull request still runs. An unrelated failure then gets one rerun of its failed jobs on the same commit (`gh run rerun <run> --failed`), once CI is under the merge capacity (`merge_max_busy`, read twice like a merge); until then, and while the rerun runs, the queue waits. The commit is recorded in `ci-reruns.json` in the state root before the rerun starts, so it never gets a second one, also after a crash; a rerun GitHub refuses for now (the run still runs, HTTP 403 or 422) gives that allowance back and is tried again on the next poll. Rerun passed: the job goes into the flaky ledger (`studio flaky`, as `<repo>: <workflow> / <check>`) and the queue goes on. Failed again: a real failure, which never counts as flaky. A failure of the same job in the same repository on any pull request within 14 days of one whose rerun passed adds one board item, `Find the cause of flaky <job>` (`fix`, builder, with the run ids in its notes; its Definition of Done: find the cause, make it deterministic under load, never raise a timeout without a measured cause), unless one for that job is still open. `tick` lists both under `reruns` and `flakyItems`, `queue run` too when there are any.

`.studio/solutions/*.md` is a store of earlier solutions, one file per topic with a `# Title`. `studio solutions search`, `studio plan` and builder and designer briefs answer with paths and titles.

## Costs

Each crew run writes a stream-json log (`<state root>/logs/<id>.jsonl`). Claude Code ends a run with one `result` event; Studio reads `total_cost_usd` from it (else the sum of `costUSD` in `modelUsage`) and the tokens from `modelUsage` (`inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, over every model of the run), else from `usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`). A run is a `system`/`init` event. A run without a `result` (stopped at a limit, killed, crashed) is estimated from its `assistant` events: the last `usage` of each message, priced by model family (Haiku, Sonnet, Opus) at the first-party API prices of November 2026, cache writes at 1.25 times input, an unknown model at the highest rates so that an estimate errs high under a cap; such a run is marked `estimated` on the item and in the ledger, and its estimate counts toward the cap like a reported cost. Lines that do not parse or values that are not numbers are skipped. The cost is what Claude Code reports; on a subscription it is an estimate, not a bill.

- **Per item.** `collect` sums every run in the item's log and in the logs of the reviews of its pull request, and stores it on the board item as `usage: { runs, tokens_in, tokens_out, tokens_cache, cost_usd }`. A review counts for the builder item it reviews, not for itself. The sum is computed from the logs each time, so collecting again never counts twice. `studio metrics` lists it per item and epic, `studio epic list` adds a `COST` column (`costUsd` with `--json`), and the pane's footer shows `today $n` once today's runs cost anything.
- **Daily cap.** `limits: { daily_cost_usd: 25 }` in `studio.yaml` caps one project, the same key in the owner config caps all projects of the owner together. Both are optional. Before each plan (with an owner cap, in every project of the owner, also one that had no plan since), before a launch replaces an item's crew record and before `accounts-clear` moves the log start of crews, Studio enters every crew run that has ended into `costs.json` in the state root, on the local day it saw the result (`crew_label_limits.timezone`, default the system zone), so a run across midnight counts for the day it ended; runs are kept for eight days. A run has ended when its process is gone or its pid belongs to another process now (the start time stored at launch); a live process Studio cannot verify counts as running. Writers take `costs.lock` and merge with the file as it is then. Once today's sum reaches a cap, nothing new is planned or launched: every ready item is deferred with `daily cost cap reached ($x of $y)` (`owner daily cost cap reached …` for the owner cap), `tick` lists it under `held`, and `state.json` shows one `usage-limit` line. Running crews finish; their cost counts once they have ended, so a day can end above the cap by what was running. The next day starts from zero. While a cap is set, an unreadable `costs.json` holds every launch.

## Build cache

Crews start from a fresh clone and a fresh `HOME`, so each one downloads its crates and packages and builds from scratch. A project can keep a shared build cache instead. It is off by default:

```yaml
# .studio/studio.yaml
roles:
  cache: { model: haiku, wip: 1 } # the role that builds it
cache:
  enabled: true
  every_days: 7 # rebuild once the cache is this old (1 to 90)
  timeout_min: 60 # per build command (5 to 240)
```

- **Filled from main only, by its own crew.** When the cache is on and missing or older than `every_days`, and the root of `origin/main` in your checkout has a `Cargo.toml`, `pnpm-lock.yaml` or `package-lock.json`, `tick` adds one item of the role `cache` (type `research`: no pull request, no push, no GitHub token) and launches it like any other item. The lead never builds it itself. The crew gets a fresh clone at the `origin/main` commit Studio read the project rules at (never a clone an earlier run left, never a pull request branch) and a fresh `HOME`, both unseeded, and runs in the usual sandbox. Its brief lists the commands, read from the manifests at the root of that checkout: `cargo fetch` and `cargo build --workspace --all-targets` (each with `--locked` when `Cargo.lock` exists), `pnpm install --frozen-lockfile --ignore-scripts`, else `npm ci --ignore-scripts`. The guard lets it run exactly these commands, write only its report, edit nothing and start no subagent; Claude Code's Bash limit is raised to `timeout_min` for this crew (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`). Downloads go through the sandbox's `network_allow` like every crew's, so the registries the build needs (for Rust `index.crates.io`, `static.crates.io`; for Node `registry.npmjs.org`) must be listed there, or the step fails and the item is blocked.
- **Published by Studio.** When `collect` reads a `done` report of a cache item, Studio copies what the build left into `<state root>/cache/seeds/`: the clone's `target/`, `$HOME/.cargo/registry` and `.cargo/git`, the pnpm store (`$HOME/.pnpm-store`) and the npm cache (`$HOME/.npm`), each only as a real directory reached without a link, then swaps the new seeds in under the launch lock. Only the run Studio launched publishes: the launch writes a run record with the commit and a nonce, the crew record of that launch carries the same nonce, and any other launch of the id removes the record; collect also reads the clone's HEAD from its files (no git runs in a crew clone) and refuses unless it is that commit. `cache.json` beside the seeds records when, from which commit and by which item. A failed copy, a build that left nothing or a cache over `cache.max_gb` publishes nothing: the old cache stays and the item is blocked with `build cache not published: <why>`. A blocked cache item stays open, so no second one is added until the lead drops it.
- **Read by every other crew through its own copy.** At launch every other local crew (not one on a worker) gets copy-on-write copies of the seeds: the target dir only into a fresh clone, the rest into its fresh `HOME`, and `PNPM_CONFIG_STORE_DIR` points pnpm at that store. A crew never sees the cache itself (it lies in the state base, which its sandbox denies) and what it writes stays in its copy. Copy-on-write (`cp -c` on APFS, `cp --reflink=always` on btrfs or XFS) costs no disk until a file changes; where the state root's file system cannot do it, nothing is published, so there is no cache. Hard links are never used. Cargo reuses the compiled dependencies; crates whose build scripts watch files by absolute path, and the workspace's own crates, build again.
- **Disk.** `cache: { max_gb: 20 }` in the owner config caps the caches of all projects together (default 20). Once a day `tick` removes the caches used longest ago while all together exceed it. `studio doctor` prints `build cache: on|off, built <date> from <commit> (<seeds>), <size> of <cap> for all projects`. Clone cleanup never touches the cache: it lives outside `clones/`.

## Using your own runners

`studio setup ci` reads the runners GitHub shows for your repository and proposes the `ci:` block of `.studio/studio.yaml`. It needs `primary_repo` (`owner/name`) in that file and a logged-in `gh`.

- **Detection.** It lists the organisation's runners first and the repository's runners as a fallback. Runners with the `self-hosted` label are grouped by their exact label set; the largest group becomes `runner_labels`, `ci.capacity.total` is its size, and a name prefix shared by the group becomes an anchored `runner_name_pattern`. If a read fails, the result is "unknown" and nothing is proposed. Without any self-hosted runner it proposes `github-hosted`, and so it does when self-hosted runners exist but all workflows use GitHub-hosted labels (a job whose runner cannot be classified, such as an expression, a group alone or a reusable workflow, keeps the runners in the proposal); a note then names how many runners stay unused. Workflows that use both kinds of runner give `runners: both`. Organisation runners restricted to other repositories by runner groups are counted, because the API call does not show those restrictions. Capacity supports organisation runners only: with repository-level runners, or when a read finds no runner matching `runner_name_pattern`, it reports fully busy with an error instead of idle.
- **Labels.** The command also lints `.github/workflows/*.yml` and `*.yaml`: every job whose `runs-on` names self-hosted labels needs an online runner that carries all of them, otherwise the job would wait forever instead of failing. A `runs-on` map with `group` and `labels` is checked by its labels, with a warning that group membership cannot be verified; `group` alone only warns. Workflows triggered by both `push` and `pull_request` must use a concurrency group of the form `<prefix>-${{ github.head_ref || github.ref_name }}`, for example `ci-…`, with `cancel-in-progress: true`. The prefix may hold letters, digits, `.`, `_` and `-`. Concurrency groups are repo-wide, so two workflows sharing a group is an error naming both files when a sharer is a `push` and `pull_request` workflow with `cancel-in-progress: true`: give each its own prefix. Sharers that only deploy, with `cancel-in-progress: false`, pass.
- **Merge rule.** `merge_max_busy` is about 62% of `total` (at least 1). Studio opens pull requests and merges only while the busy self-hosted runners stay at or below it. With `runners: both`, only self-hosted runners count toward `ci_busy`; GitHub-hosted runs (in progress plus queued) are counted separately and compared with `github_hosted_limit`. `githubHostedBusy` counts all runs of the repository, including runs whose jobs use self-hosted runners. Until you set that limit the check is skipped, and Studio says so in a warning.
- **Public repositories.** A self-hosted runner on a public repository would run code from fork pull requests, so the command reports an error and `--write` refuses to write. There is no override, even when fork pull request workflows are blocked: use GitHub-hosted runners, or edit the `ci:` block by hand at your own risk. When the visibility cannot be read, the repository counts as public.
- **Shared host.** Set `ci.shared_host: true` when the runners share their machine with other work. Capacity then also requires the 1-minute load average of the machine Studio runs on to stay at or below `ci.capacity.host_load_max`, or at the number of CPU cores when that is unset. An explicit `host_load_max` applies with or without `shared_host`.
- **Where capacity applies.** Studio gates CI load where it causes it. A launch does not wait for CI runners: a crew builds and tests in its own clone and puts no load on CI until a pull request exists. A launch of a fix, feature or chore waits only for the host load above (reason `host load` in `studio plan`), besides role WIP, credentials, overlaps, dependencies and a pause. The load average is one reading that lags behind new work, so a plan assigns at most one build; the other ready builds show `host load: one build start per plan`, and each `studio launch` reads the host again and may start one of them. When `collect` opens the pull request for a crew, it first checks the merge rule twice, `check_twice_seconds` apart, like the merge queue; a read error counts as busy. If CI has no room, nothing is opened: the item keeps its status and branch, gets the note `pr held: ci capacity (busy N of M, limit L)`, and `collect` exits 1; run `studio collect <id>` again later, and it opens the pull request once and removes the note. An item that changed during the capacity wait gets no pull request. An open pull request of the branch is taken without waiting. The merge queue keeps its own check before every merge.
- **A review waits for CI.** A review item is deferred with the reason `ci pending` while any check of its pull request head still runs, or while the checks cannot be read; a launch refuses then too. Red checks do not hold it: the reviewer sees them. A repository that reports no checks at all does not wait. The routine tells the reviewer to approve code that is fine with green checks, and to ask for changes only where the code needs one, never because checks still run.
- **Crew pushes.** Studio assumes a crew's `git push` of `studio/<id>` starts no CI and does not block that push. A workflow whose `push` trigger matches crew branches (no branch filter, `**`, `studio/*` and the like) would start CI on every crew push that no capacity check sees, so `setup ci` warns about it. Limit `on.push.branches` to the default branch and let `pull_request` run the checks.

Without `--write` nothing changes. With `--write` the command changes only the `ci:` block (other keys and comments stay, but comments inside a replaced list are lost), validates the whole file first, and writes it atomically. Any error, from the proposal or from the workflow lint, makes it write nothing and exit 1. `--json` prints one object with `detection`, `proposal` (`ci`, `notes`), `errors`, `warnings` and `written`.

## Claude accounts

Studio can keep the Claude login of crews apart from your own. You store a long-lived token per account; crews then use it with their own Claude config dir, so logging in or switching accounts in your own sessions never changes theirs. You are responsible for using your accounts within the terms that apply to them.

1. `claude setup-token`: creates a token valid for one year and prints it. It needs a Pro, Max, Ultra, Team or Enterprise plan.
2. `studio account add <label>`: asks for the token with hidden input and stores it. The first account becomes the active one and sets up the crew config dir.
3. `studio doctor`: shows the accounts, which one is active and how crews log in.

`studio account list` shows each label with the day it was added, whether it is free, parked until a reset, blocked or at its limit, and its runs today; never a token. `studio account use <label>` makes another account the active one. `studio account remove <label>` removes one, and refuses while a crew runs on it. `add`, `use` and `remove` are for the owner and need a terminal; `setup-plugins` handles no secret and also runs for the lead without one (never for a crew), since every Studio update moves the pins; `remove` refuses while a launch is in progress, and warns when the last account goes, since launches then use the environment or your main login again. Crews use the active account only: while it is parked, blocked or at its limit, nothing starts until it is free again.

Studio checks only that a token has a plausible form (no spaces or control characters, 20 to 4096 characters). The Claude Code documentation names no way to check a token without a model call, so a wrong token shows up only when a crew starts. `account list` and `doctor` warn from 30 days before one year has passed since a token was added; after that a launch refuses and names `claude setup-token`.

**Crew config dir.** Crews of stored accounts use `$XDG_CONFIG_HOME/studio/claude` (default `~/.config/studio/claude`, mode 0700) as `CLAUDE_CONFIG_DIR`, never `~/.claude`. The first `account add` installs the pinned plugins there (by default `superpowers` and `studio`, see "Skills and updates"); `studio account setup-plugins` does it again and checks the installed versions. It runs `claude plugin marketplace add` with the HTTPS addresses of both marketplaces and `claude plugin install` with only `CLAUDE_CONFIG_DIR`, `HOME` and `PATH` in the environment, no token. A launch refuses while this directory is missing, and a role whose required skill is missing there, as for any config dir.

**Which way a launch takes.** A configured `crew_credential_command` comes first and is unchanged. Without one, stored accounts come next, with the active label. Without accounts, the environment and your normal Claude login are used, as before, under the label `default`.

## Crew credentials and usage limits

**GitHub token.** `studio secret set crew-token` asks for the token with hidden input (it refuses without a terminal), strips whitespace, checks the token once against the GitHub API for `primary_repo`, and only then writes `$XDG_CONFIG_HOME/studio/crew-token` (default `~/.config/studio/crew-token`) with mode 0600. It prints `valid for <repo>` or the failing permission and nothing from `gh`; after a failed check nothing changes. The check shows the token can use the repository; it does not prove the token's scope, so check yourself that it is least-privilege. At launch a `crew_token.env` variable that is set comes first, then this file. A file with a mode wider than 0600 or another owner makes the launch refuse.

**`studio doctor`** shows how crews log in to Claude (credential provider, the active stored account, a token in the environment, or your main login), the stored accounts with their state and expiry, and lists the crew token and its source, the credential provider, `allow_api_billing`, the names of API key variables in the environment and whether `studio.yaml` and the owner config are readable. It never prints a value. It exits 1 when the crew token is missing, unless `allow_ambient_credentials: true`.

**API billing** stays off unless the owner config sets `allow_api_billing: true`. Then `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` pass through to the crew. Without it, a launch also refuses when the `settings.json` in the crew's Claude config dir sets `apiKeyHelper`, `env.ANTHROPIC_API_KEY` or `env.ANTHROPIC_AUTH_TOKEN`. An unparsable settings file, or one that is not a regular file, refuses in either case. Crew settings written by Studio never contain `apiKeyHelper`.

**Settings sources.** Crews ignore the project and local Claude Code settings of the clone (`.claude/settings.json`, `.claude/settings.local.json`): Studio starts every crew, fresh or resumed, with `--setting-sources user`, so only the user settings and the file Studio passes with `--settings` apply. Hooks, `env` and `apiKeyHelper` from the repository therefore have no effect, and Studio no longer reads those files. Crews also do not auto-load the project `CLAUDE.md`, rules, skills, commands or subagents; Studio reads `AGENTS.md` and `CLAUDE.md` itself, in the owner's checkout, at the SHA of a freshly fetched `origin/main` (replace objects ignored), and saves copies next to the crew's brief in the state root (`briefs/<id>.rules/`); the brief points to those copies. The crew can read them but not write them, and a reused clone with moved refs cannot change them. A launch refuses when the fetch fails, when an entry is not a plain file (mode 100644, so no symlinks) or when a file is over 256 KiB. Items in another repository get the rules of the project checkout. The guard denies `git update-ref`, `git replace`, `git symbolic-ref` and fetch refspecs that write below `refs/remotes/`. Claude Code auto memory is off for crew runs (`autoMemoryEnabled: false` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`). These files cannot change settings or Studio's rules, and can never direct a crew to handle credentials, change remotes, reach new hosts or change the report contract. Before a launch, Studio refuses a role whose required skill is definitely absent from the crew's Claude config dir (`skills/<name>/SKILL.md` or a plugin cache `skills/<name>/SKILL.md`, any `plugin:` prefix stripped); an unreadable directory does not refuse. A required skill that is not available in the session means a `blocked` report naming it.

**Credential provider.** You can set `crew_credential_command` in the owner config (it is refused in `studio.yaml`). It is the absolute path of an executable file you own that neither group nor others can write. Studio runs it without a shell, with a 30 s timeout, and with only `PATH`, `HOME`, `STUDIO_ITEM`, `STUDIO_ROLE` (both empty when a plan only asks whether a credential is available) and `STUDIO_EXCLUDE` (comma-separated labels that are parked). It reads exactly one JSON line from stdout, at most 64 KiB; stderr is discarded:

```json
{ "label": "label-a", "env": { "CLAUDE_CONFIG_DIR": "/absolute/path/below/the/owner/config/dir" } }
```

`env` has exactly one key: `CLAUDE_CODE_OAUTH_TOKEN`, the verified fallback, or `CLAUDE_CONFIG_DIR`, which is also accepted (a login directory that must exist, belong to you and have a real path below the owner config dir). The config dir form has not yet been verified with an isolated `HOME` on macOS. The label matches `^[A-Za-z0-9._-]{1,64}$`. Only the label goes into state and board; a token reaches only the environment of the crew process. Any failure, a parked label in the answer, or an empty answer while no label is parked keeps the crew from starting. Without a provider Studio uses stored accounts (see "Claude accounts"), else the environment as described under Prerequisites, under the label `default`.

**Stored accounts, as a contract for providers.** A provider may hand out the tokens that `studio account add` stores, without its own copy. The layout is stable within a major version:

- `$XDG_CONFIG_HOME/studio/tokens/` (default `~/.config/studio/tokens/`): a directory, mode 0700, owned by the user, no symlink.
- `tokens/<label>.json`: one per account, mode 0600, owned by the user, no symlink, holding one JSON object `{"label": "<label>", "token": "<token>", "addedAt": "<ISO 8601 time>"}`. `label` equals the file name without `.json` and matches `^[A-Za-z0-9._-]{1,64}$`, not starting with a dot.
- `tokens/active`: mode 0600, the active label and a newline.
- `$XDG_CONFIG_HOME/studio/claude/`: the crew config dir with the plugins. For these tokens a provider returns `CLAUDE_CODE_OAUTH_TOKEN`.

Whenever a provider answers in the `CLAUDE_CODE_OAUTH_TOKEN` form, for a stored account or any other token, the crew gets this crew config dir as `CLAUDE_CONFIG_DIR`, as on the built-in way, never `~/.claude`; a launch refuses while it is missing (`studio account setup-plugins`). The `CLAUDE_CONFIG_DIR` form keeps the directory the provider names.

Studio reads these files only when no provider is configured. A provider reading them must apply the same checks (owner, mode, no link) and must never print a token except in its one JSON line.

**Usage limits.** At the start of `status`, `plan`, `launch`, `state`, `collect` and of every `tick` (before it collects), Studio reads the end of each active crew's log. Only events Claude Code itself emits count; tool output that quotes a limit message does not. A failed `result` or an assistant API error message counts by its fields (`api_error: "usage_limit_reached"`, or status 429 with a rejected `rate_limit_info`) or by the limit text; the rejected window gives the reset as an absolute time (`seven_day` windows are the weekly limit). The owner and the lead see `usage limit on <label> until <time>; nothing launches on it`; the item goes back to `ready` without using up its one relaunch, and a credential provider is asked for another label on the next launch. A `rate_limit` retry alone never stops a running crew; it counts only when the crew exited without a report and no later successful event shows it recovered. On a limit it stops the run, parks the label in `limits.json` in the owner root, for all projects, and returns the item to `ready` with a note; clone and branch stay. A label is parked until the reset when the event gives an absolute time, otherwise for one hour, and clears by itself afterwards. The next launch resumes the session when the clone is still there and the session is usable with the new credential (same label, or the token form with the same config dir), otherwise it starts fresh. A crew that left a report is not treated as limited, and a clone that left its branch is not replaced: the launch refuses and names it.

When no credential is available (without a provider: `default` is parked; with one: it answers empty while labels are parked), nothing is planned or started, and `state.json` shows one `forOwner` line with the earliest reset. Work continues by itself once a label is free. An unreadable `limits.json` counts as all parked and is reported.

**Usage limits per credential.** Each credential label has a ceiling set in the owner config under `crew_label_limits`: `max_parallel` (default 2) crews running at once, and optionally `max_runs_per_day` crew launches per day; `timezone` (an IANA name such as `Europe/Berlin`, default the system zone) decides where the day ends. A crew counts as running while its process is alive, whatever the board says. A launch counts when the crew is started, also when the start fails. Counts per day and label are kept in `usage.json` in the owner root and shown in `state.json` as `labelUsage` (labels only). A label at its limit is added to `STUDIO_EXCLUDE` like a parked one; a provider that returns it anyway makes the launch refuse. `plan` asks the provider with a growing exclude list (at most 16 calls, token never kept) and plans only as many items as the free labels allow; the rest wait with the reason `credential limit`, and with no free label `state.json` shows one `usage-limit` line. A provider must honour `STUDIO_EXCLUDE`: one that returns an excluded label makes the launch refuse and also holds `plan` (nothing is planned), even when no label is full. A live crew counts whatever the board says about its item. The counts are owner-wide, like account blocks and parks: two projects using the same credential share its limits. A crew stays running when another project parks its label; it hits the limit itself. An unreadable `usage.json` counts as all labels full, and an unreadable `crew.json` in any project refuses launches, since its crews cannot be counted. Launches of all projects are serialised with a `launch.lock` in the owner root, and the checks run again under the lock, after the clone is prepared and just before the run is counted and started; a launch that lost the lock refuses.

**Account blocks.** When an account looks blocked, Studio stops, so automation never makes it worse. At the start of `status`, `plan`, `launch` and `state`, it looks in the current run of every crew not yet stopped on an `assigned` or `in_progress` item, and of every running crew it can verify in another unfinished status, for events Claude Code itself emits: a failed authentication (also with no earlier success), an account on hold, disabled, suspended or banned, a disabled organization, a usage policy refusal. Tool output that quotes such a message does not count, and neither do billing errors or usage limits. A retry with a block category counts at once, also for a running crew, unless a later successful event shows the run recovered; a crew that left a report still counts.

Studio records the label and a reason code in `blocks.json` in the owner root (`<state base>/owner`), then stops every running crew of all your projects, of all labels, except on `merged` and `dropped` items, also when a board cannot be read. Another project's board is only read; its items move back the next time Studio runs there. It signals a crew only when the process start time stored at launch still matches; a running crew it cannot verify is not signalled but reported with item and pid, so check it by hand. `assigned` and `in_progress` items return to `ready` with a note; clone and branch stay. An item whose crew left a report stays where it is, so `collect` still works. Nothing starts and no credential provider is called while any block exists, under any label. `state.json` shows one `forOwner` line (`account-block`) and one entry per block under `notifications`. An unreadable `blocks.json` (malformed, a symlink, not a file) counts as blocked in the same way; a missing file means no block.

Nothing clears by itself. `studio accounts-clear <label>` removes that label's entries, moves the scan start of that label's crews in all projects to the end of their logs so an old event does not return, restarts nothing, and needs a terminal. Crews cannot write the owner root, because the sandbox lets them write only their own clone, tmp dir and `HOME`; those lie below the state base, but not in the owner root. On an unreadable file it refuses: inspect or remove the file.

**Upgrading.** Older versions kept `blocks.json`, `limits.json` and `usage.json` per project. The first command that needs them merges them into the owner root and removes the old files: blocks by label and reason with the earliest time, per label the later park, usage summed. A file that cannot be read is not interpreted. It is kept as `<owner root>/<name>.legacy-<project root>` (for a symlink, only a note), and until you inspect and remove that entry the file counts as unreadable, so nothing starts.

## Security model

The crew guard is a convenience layer, not a security boundary. The boundary is the sandbox, a least-privilege token and server-side branch protection. The guard does not contain a malicious crew: `package.json` scripts, and any program a crew writes, can run anything, so no list of denied commands can stop one. Owner-only commands (`pause`, `resume`, `accounts-clear`) need a terminal, which a crew does not have; that is the real barrier for them.

Layers, outermost first:

1. Sandbox: crew shell commands run sandboxed. Each item gets its own blob-less clone (no `git worktree` on the owner's repository) and an isolated, freshly recreated `HOME` that holds only a git identity and a credential helper reading the crew token. The clone is made from the project's origin, then its `origin` is set to `https://github.com/<item repo>.git`, so the crew pushes over HTTPS with the crew token even when the owner's origin is an ssh URL. An item's `repo` must be `primary_repo` or listed in `repos`; launch refuses anything else. Writes are limited to that clone, a per-item tmp dir and that `HOME`. Reads deny the whole real home directory (plus explicit credential locations such as `gh`, ssh, netrc, gnupg, aws, docker and keychain paths, and `GH_CONFIG_DIR` / `XDG_CONFIG_HOME` entries when set); only the clone, the tmp dir, the crew `HOME` and the real paths of the owner's `crew_toolchain_paths` (see below; nothing is derived from `PATH`) are allowed back in. Studio never runs git inside a crew clone after the crew started.
2. Least-privilege token: the crew token cannot merge, release or administer.
3. Server-side branch protection: `main` and every ref listed in `crew_allowed_workflow_refs` must be protected on the server. `loadConfig` callers can read `configWarnings(config)` for a reminder.
4. Guard hook: allows only the tools a crew needs (Bash, Read, Edit, Write, MultiEdit, NotebookEdit, Grep, Glob, Skill, TodoWrite, Task, Agent) and denies every other tool, including WebFetch, WebSearch and all MCP tools (crew settings deny these too, and crew sessions start with `--strict-mcp-config` and an empty MCP config), except the REA tools of a researcher (see "Reverse engineering for the researcher"): there the allowlist is the guard's own, default deny. It denies risky constructs outright (force pushes, tag pushes, merges, deploys, writes outside the worktree, secret files, `eval`, shells with command strings, `xargs`, command substitution inside `git` and `gh`, running `studio` directly, `node` except `--version`, `--help`, `--test` with relative paths or plain patterns, or a literal relative script path, unquoted arithmetic and `${VAR:=x}`, `npx`, `pnpx`, `bunx`, `bun x`, `corepack`, `dlx`, `create` and `init` of npm, pnpm, yarn and bun, `npm x` and `npm exec`, `--shell*` and `--script-shell`, setting or unsetting `STUDIO_*`, `NODE_PATH`, `PATH`, `HOME` and package manager variables). These are conveniences that catch mistakes, not a wall. The hook blocks the call when node or the guard script is missing. Crew sessions write commit messages with `git commit -F <file>` and pull request bodies with `gh pr create --body-file <file>`. The guard allows listed forms, not a model of gh's or git's option grammar: `gh pr view|checks|diff|list|status` with an exact list of flags each (no clusters, no `--web`) and exactly `gh pr create --head studio/<id> --base <item base> --title <text> --body-file <file>` from the clone root (each option once, the file a relative path inside the clone), `gh workflow run <listed> --ref <listed>` when `crew_allowed_workflows` is set, no other gh; git global options from a short list; `git fetch` and `git pull` with listed options from `origin` only, `git ls-remote origin [<ref>...]`, `git push` to `origin` only, all from the clone root; no `git clone`, `init`, `fetch-pack` or `archive --remote`/`--output`; `git remote` and `git submodule` only to read; no writes below any `.git`.

npm, pnpm, yarn and bun pass with any command and any option (`--filter`, `-C`, `-r`), except the denylist above; a crew runs an installed tool with `pnpm exec <tool>`. `node` takes `--version`, `--help`, `--test [<relative paths or patterns>]` or a plain relative script path. A pattern after `--test` follows the same allowlist as Glob patterns (letters, digits, `_ - . / * ? , { }`, flat braces, no `..`), and one that could name the studio binary is refused. Variable names are matched case-sensitively, except `npm_config_*`.

## State root and owner config

Runtime state never lives in the repository. Per project it goes to `$XDG_STATE_HOME/studio/<hash>-<name>` (default `~/.local/state/studio/<hash>-<name>`; `<hash>` is the first 16 hex digits of the SHA-256 of the project directory's real path, `<name>` its sanitised base name): clones, crew homes, tmp dirs, settings, briefs, logs, guard contexts, `crew.json` and `marker.json`. The marker binds the root to the project's real path and origin URL; origins count as the same repository however they are spelled: host lower-cased, login and port dropped, a trailing slash and `.git` stripped, ssh (`git@github.com:org/repo.git`, `ssh://...`) and https the same, and on GitHub owner and repository case-insensitive. A launch with a mismatching marker, or into a non-empty root without one, is refused, and so is a state root that equals, lies inside or contains the project directory. A reused clone must still name the project's origin in its `.git/config` (read as a file), otherwise it is cloned again. Directories are created with mode 0700; Studio refuses to write or delete through a symlink below that root. Crew shell commands cannot read the state base `…/studio` except their own clone, tmp dir and home. The project's `.studio/` keeps `studio.yaml` and `roles/` (committed), `board.yaml` (the lead machine's, not committed, see [The board lives on the lead machine](#the-board-lives-on-the-lead-machine)) and `reports/` (crew reports, written untracked in the crew clone as the last step).

### Clean-up of finished items

A clone grows with its build output: a Rust `target/` reaches gigabytes, `node_modules` hundreds of megabytes, while the blob-less git objects stay at tens of megabytes. Each tick removes the clone, crew home and tmp dir of an item that is finished and needs none of them any more; `studio gc` lists every item's folders with their sizes and verdict (a dry run), `studio gc --apply` does what the tick does, and `studio doctor` shows the total and how many can go. Nothing else of the state root is touched: briefs, logs, settings and the crew records stay.

An item's folders go when all of this holds, and stay otherwise, with the reason:

- the item is on the board and `merged`, or `dropped` at least 7 days ago (its history must say when; uncommitted work in a clone cannot be seen without git, so a dropped item gets that time to be looked at);
- no crew of the item runs or may run (one that cannot be verified counts as running), and no launch holds the launch lock while the folders are removed;
- every local branch tip and a detached `HEAD` of the clone, read from `.git` as files (`HEAD`, `refs/heads/`, `packed-refs`), is on GitHub: the head of the item's pull request or contained in `main` (GitHub's compare API). A stash, a ref that is a link or no plain commit id, an unusual `HEAD`, more than 20 branches, or a GitHub that cannot be asked keep the clone;
- `crew.json`, the board and `lessons.json` can be read.

A clone whose report a pending lesson proposal cites (see "Role memory") is trimmed to `.studio/reports/`, and removed once the lesson is judged. A merged piece of an epic goes as soon as it is merged: the acceptance checks a pinned `main` commit in a clone of its own. The tick asks GitHub about at most 10 clones each time; `doctor` asks GitHub nothing and counts such clones apart. Git never runs in a clone for this (rule D4).

### Moving a project

The state root is named after the project folder's real path, so a project that moved (another folder, another machine path, a new clone) starts with a fresh, empty state root and the old one keeps the history. `studio adopt --from <old state root>` brings that history over: the owner's, in a terminal (refused for crews and without one). It reads the old root's `marker.json` and refuses unless it names the same repository as this project's `origin` (spelled as above), and it refuses while a crew of either root is alive (or cannot be verified), a queue run or a tick holds its lock, or a queue has a merge in progress. Without `--apply` it is a dry run: it lists each file with what it would do and writes nothing. With `--apply` it binds this project's state root and, under its tick lock:

- copies the small history files this root does not have yet: `metrics.jsonl`, `costs.json`, `lessons.json`, `lessons-review.json`, `skills-check.json`, `exceptions.jsonl`, `releases.json`, `releases.jsonl`, `rea-allow.json`, `flaky.json`, `ci-reruns.json`, `acceptance-runs.json`, `group-contracts.json`;
- merges the append-only logs (`*.jsonl`) line by line, the old lines first, each line once, and the queue's merge history (`done` of `queue.json`) entry by entry; pending queue entries stay behind and are named (queue them again here);
- keeps a JSON file both roots hold and that differs (`conflict`, exit 1: compare them by hand);
- never copies clones, crew homes, logs, briefs, settings, guard records, crew records, locks, markers, `state.json`, `tick.json`, `pause.json`, worker records or per-run folders (`rea/`, `reference/`, `contract-changes/`); they are listed as left behind.

It is idempotent: a second run finds every file the same and changes nothing. It never deletes the old root: it prints `rm -rf -- <old root>` for you to run once `studio metrics`, `studio lessons` and `studio release list` look right.

Settings that open reads on the owner's machine are not the repository's call. They live in the owner config `$XDG_CONFIG_HOME/studio/config.yaml` (default `~/.config/studio/config.yaml`; schema `schema/owner.schema.json`; a missing file means defaults):

```yaml
crew_toolchain_paths: [] # absolute directories a crew may read, e.g. a version manager's install dir
crew_allow_macos_trust_service: false # true lets crew shells on macOS reach the TLS trust service so gh works; weakens the network boundary, see SECURITY.md
crew_credential_command: /absolute/path/to/provider # optional, see "Crew credentials and usage limits"
allow_api_billing: false # true lets crew runs bill the API
allow_proof_commands: false # true lets proof: command rules run here, in the proof sandbox (see "Exceptions by evidence")
# research_roots: [/absolute/path] # optional, see "Reverse engineering for the researcher": where a project's research.artifacts may lie
# rea_version: 6.7.0 # optional: the exact rea-agents version researcher crews run (studio research install)
# rea_env: { GHIDRA_INSTALL_DIR: /absolute/path } # optional: engine variables for the REA server
# research: { trust: true } # the default: every REA tool class, full install; false: strict mode
# groups: [...] # optional: groups of related projects, see "Groups of related projects"
# notify: # optional, see below
#   quiet: "22:00-07:00" # local hours in which pushes that are not urgent wait
#   timezone: Europe/Berlin # the zone of the quiet hours; default the system zone
#   language: de # a shipped language code or auto (the default: Claude Code's language setting, else LC_ALL, LC_MESSAGES, LANG)
#   ntfy_server: https://ntfy.example.org # self-hosted ntfy; default https://ntfy.sh
#   channel: my-channel # with command: hand state's owner lines to your own executable
#   command: /absolute/path/to/notify
crew_label_limits: # usage limits per credential label, see "Usage limits per credential"
  max_parallel: 2 # crews running at once per label
  # max_runs_per_day: 20 # optional launches per label and day
  # timezone: Europe/Berlin # optional, where the day ends; default the system zone
# limits: { daily_cost_usd: 50 } # optional, all projects together, see "Costs"
# cache: { max_gb: 20 } # optional: the build caches of all projects together, see "Build cache"
# pane: { nested_worktrees: show } # or hide: sessions in a git worktree nested under a Studio project start with the board off, see "The Studio board"
# workers: # optional, see "Workers on other machines"
#   accept: { windows: [{ login: worker-login, id: 1234567 }] } # on the lead's machine: whose claims count, per label, by login and account id
#   self: { lead: lead-login, lead_id: 1234567, deny: { paths: [], ports: [] }, lease_minutes: 30 } # on a worker machine
#   relay: { lab: { host: worker.example, host_key: "ssh-ed25519 AAAA...", identity_file: /home/owner/.ssh/studio-lab } } # on the lead's machine, see "Relay workers"
#   serve: { deny: { paths: [], ports: [], hosts: [local-subnets] } } # on a relay worker
```

Tools installed below your home, such as `cargo` from rustup or `node` from a version manager, run in a crew only when their directories are listed here; `studio doctor` names any it finds on `PATH` that are not. For Rust list `~/.cargo/bin` and `~/.rustup`, never `~/.cargo` itself, which holds the registry credentials and is refused. Crews then get `RUSTUP_HOME` pointing to the rustup dir (read-only) and `CARGO_HOME` in their own `HOME`, so crates are fetched again per run and `~/.cargo/credentials*` stay denied.

A `studio.yaml` that still contains `crew_toolchain_paths` is refused. At launch every toolchain path must exist; Studio resolves it to its real path (which goes into the sandbox) and refuses it, comparing literal and real spellings and case-insensitively on macOS, when it is the home or a parent of it, equals, contains or lies inside a credential store, `~/.claude` or `CLAUDE_CONFIG_DIR`, or equals, contains or lies inside the project directory or the state root.

### Push notifications

**To your phone (ntfy).** `studio setup` (or `studio setup --notifications`) sets it up: ntfy needs no account. Studio makes a random topic (`studio-` and 24 url-safe characters, 144 bits) and stores it in `notify-secret` in the owner config dir (`$XDG_CONFIG_HOME/studio`, mode 0600, never readable by crews). Whoever knows the topic reads your pushes, so the setup prints the subscribe link once in your terminal and nothing else ever shows it: not `doctor` (it says `notifications: ntfy`, `none` or `invalid`), not `tick`, not any state file. Pushes go out as a plain HTTPS POST to `<server>/<topic>` (the topic is never in a command line), title `Studio`.

`tick` pushes each new entry of its `needsLead` and each account block. A push is one line in your language (`notify.language` when it is a code, else as the pane: Claude Code's `language` setting in the project or your user settings, else the locale, else English), a fixed phrase, the item id and the project name (the repository name of `primary_repo`; `primary_repo` and `repos` must be `owner/repo`), never a note, question or other crew text: `Fix limit reached: APP-3 in app`, `Merge failed`, `Changes requested`, `Crew has a question`, `Blocked`, `Account blocked`, `Decision needed`. A decision is the item, its kind and the time the item entered its status; it is pushed once (`pushed.json` in the owner state root holds what was sent, no secret). At most one push per project in 10 minutes: what comes up meanwhile waits and goes out bundled (`3 decisions needed in app`). During `notify.quiet` (in `notify.timezone`, else the system zone) pushes wait too, unless urgent: an account block passes quiet hours and the throttle, with high priority. A failed push is listed under `errors` as `notify: <reason>` and tried again on the next tick; it never fails the tick.

**To your own command.** With `notify: { channel, command }` in the owner config (a `notify` block in `studio.yaml` stays parsed, has no effect, and `studio` warns), `studio state` hands each line for you and each account block to `command` once. `channel` matches `[A-Za-z0-9._-]{1,64}`; `command` is checked like the credential provider (absolute, a regular file you own, not group- or world-writable) and runs without a shell, with a 30 s timeout, output ignored. Its environment is exactly `PATH`, `HOME`, `STUDIO_NOTIFY_CHANNEL`, `STUDIO_NOTIFY_KIND` (`owner-item`, `usage-limit` or `account-block`), `STUDIO_NOTIFY_ID`, `STUDIO_NOTIFY_PROJECT`, `STUDIO_NOTIFY_TEXT` (in the push language: an item's own title as it is, Studio's lines and account blocks in words; control characters replaced by spaces, at most 500 characters) and `STUDIO_NOTIFY_LANG` (that language's code). Sent messages are remembered in `notified.json` in the owner state root; a failing command is retried on the next run, a line that vanishes and returns is sent again, at most 20 are sent per run, and an unreadable `notified.json` sends nothing. `studio doctor` shows only whether notify is set.
