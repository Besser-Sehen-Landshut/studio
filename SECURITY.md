# Security policy

Please report vulnerabilities through GitHub private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for security problems.

## Security model

The crew guard is a convenience layer, not a security boundary. The boundary is the sandbox, a least-privilege token and server-side branch protection. The guard does not contain a malicious crew: `package.json` scripts, and any program a crew writes, can run anything, so no list of denied commands can stop one. Owner-only commands (`pause`, `resume`, `accounts-clear`) need a terminal, which a crew does not have; that is the real barrier for them. Crews cannot run `studio` directly (the guard denies it), but the guard does not contain a malicious crew; the parser differences between the guard and a real shell that we accept are tracked in issue #10. `main` and any ref listed in `crew_allowed_workflow_refs` must be protected server-side.

## Crew credentials

Studio itself writes no crew credential to state, board, brief, settings, logs or errors, and never prints it. Output of crew commands is logged as is, so a crew printing its environment would put its credentials in the crew log, which lies in a state directory with mode 0700. A provider's token reaches only the environment of the crew process, as does the crew's GitHub token. That means crew shell commands can see both tokens in their environment: keep the GitHub token least-privilege, and treat a crew as able to use its model credential while it runs.

Crews ignore the project and local Claude Code settings of their clone: every launch, fresh or resumed, passes `--setting-sources user`, so only the user settings and the settings file Studio passes with `--settings` apply. Hooks, `env` and `apiKeyHelper` committed to a repository cannot redirect the Claude process, which runs outside the sandbox, or capture a newly issued token. Crews do not auto-load the project `CLAUDE.md`, rules, skills, commands or subagents; Studio itself reads `AGENTS.md` and `CLAUDE.md` from the owner's checkout at a verified `origin/main` SHA (after `git fetch origin main`, ignoring replace objects) and saves copies in the state root beside the brief, a place the crew can read but not write. The brief points to those copies, so a reused clone whose refs or replace objects an earlier run changed cannot alter them. A launch refuses when a fetch fails, when an entry is not a plain file (mode 100644, a blob) or when a file is over 256 KiB. The guard also denies `git update-ref`, `git replace`, `git symbolic-ref` and fetch refspecs (and `--refmap`) that write below `refs/remotes/`; plain `git fetch origin` stays allowed. Like the rest of the guard that is a convenience layer; the copies' safety rests on the sandbox, which allows writes only to the clone, the tmp dir and the crew `HOME`. Crew runs also have Claude Code auto memory off (`autoMemoryEnabled: false` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in the settings file), so nothing a run writes there reaches the next run. The pinned files are ordinary project content: they cannot change settings or Studio's rules and can never direct a crew to handle credentials, change remotes, reach new hosts or change the report contract. A launch refuses when a role's required skill is definitely absent from the crew's config dir. Studio checks only the owner's own `settings.json` for API billing keys.

Stored Claude accounts (`studio account add`) lie in `tokens/` in the owner config directory: the directory mode 0700, each `<label>.json` mode 0600, both owned by the user and never a symlink; anything else makes a launch refuse rather than fall back to another login. Only processes of that user can read them, which includes anything else running as that user. Studio reads a token only at launch and passes it only as `CLAUDE_CODE_OAUTH_TOKEN` in the crew process's environment; it never writes it to state, board, brief, settings, logs or output, and the plugin setup runs without it. The crew's Claude config dir (`claude/` in the owner config directory) holds no token, and of it only the plugin and skill folders are open to crew reads; `tokens/` stays denied to crew shell commands and file tools. A crew process can see its own token in its environment, as with a provider. Not yet checked, and due in the first real run: whether a crew shell can see the environment of other crews' processes, which holds their tokens (for example with `ps eww` or `ps -E`), and what Claude Code writes into shell snapshots in the config dir.

The owner config directory, including the `crew-token` and `notify-secret` files, is denied to crew shell commands and file tools, also when `XDG_CONFIG_HOME` lies outside the home. Of the Claude config dir a crew gets, a provider's `CLAUDE_CONFIG_DIR` or the crew config dir `claude/`, crew shell commands may read only `skills/`, `plugins/cache/` and `plugins/marketplaces/`, which skills need. The rest of it, with the transcripts of all crews using it (`projects/`), `.claude.json`, shell snapshots and any stored login, stays denied to them. Claude Code itself runs outside the sandbox and uses the whole directory; the sandbox covers only the shell commands it starts. The crew's file tools reach the same three places and its own saved tool outputs (`projects/<this clone>/*/tool-results/`), see below. Other logins below the owner config directory stay denied.

The provider is a program the owner configured: it is accepted only from the owner config, as an absolute path to a regular file owned by the current user that neither group nor others can write. It gets a minimal environment, and its output is parsed strictly and never echoed. API billing is off by default, see the README.

Limit and account block detection read crew logs, which contain untrusted tool output, so they match only top-level events from Claude Code. A forged limit event could at worst stop that run and park its label for at most 8 days. A forged block event could stop all crews of all the owner's projects, because they share the account, until the owner clears it with `studio accounts-clear`, which needs a terminal; that is the safe direction, since it only stops work. In the same way, content that provokes a Usage Policy refusal, for example in a repository a crew reads, can stop all crews of all projects until the owner clears it. The block state lies in the owner root below the state base, and the barrier that keeps crews from changing it is the sandbox: it allows writes only to the clone, the tmp dir and the crew `HOME`, so a crew cannot clear a block. The guard's denial of the owner root, `blocks.json` and the `studio` command is only a second net; a program a crew writes itself, or a `package.json` script, can still start the CLI. `accounts-clear`, `pause` and `resume` also need a terminal, which a crew does not have. Detection runs whenever a `studio` command runs in any project: with a block recorded, each run also stops the verified live crews of every other project root, and it does so for stops only, never moving another project's board. A project with no lead running is therefore swept only when another project reconciles. A forged block now stops all projects on the machine, not just one. Crews cannot read the state base, except their own clone, tmp dir and `HOME`, and can write only those three; the owner root is not among them. Push notifications (`notify` in the owner config) are trusted like the credential provider: an absolute path to a regular file you own, not group- or world-writable, run without a shell and with a minimal environment; the message text is passed in the environment with control characters replaced by spaces, and the same stripping applies to titles in the Studio board pane and toasts. Phone pushes (ntfy) carry only fixed phrases, item ids and the project name, never crew text; the topic is their only secret, sent only in the URL path of an HTTPS POST (never in argv), printed once by `studio setup`, and redirects are not followed. A block stops every live crew except on `merged` and `dropped` items, and also when the board cannot be read. Because a recorded pid may by now belong to another process, Studio stores the process start time at launch and compares it before each signal on a block: a mismatch means the crew is gone and nothing is signalled. A live crew with no stored or readable identity is not signalled either; it is reported with item and pid for the owner to check, its block event still counts, and launches stay refused. A launch whose new process has no readable identity is stopped and refused; that child, just spawned by Studio, is the one process signalled without a stored identity. The comparison and the signal are separate steps, so a very small window remains.

## TLS for Go tools on macOS

Go tools such as `gh` verify TLS certificates on macOS only through the system trust service `com.apple.trustd.agent`, which the sandbox blocks. Blocked, `gh` fails with `x509: OSStatus -26276`; `SSL_CERT_FILE` does not help on macOS. Checked locally with `sandbox-exec`: denying that one service reproduces the error, and allowing it fixes it.

By default this service stays shut, and a crew on macOS runs no `gh` at all. It pushes its branch and names the pull request title in its report, with the pull request text as the report body. `collect` then opens the pull request outside the sandbox, with the crew token: title and body are crew text, so control characters are removed, the body is cut to 20,000 characters and passed as a file, and a line says that the crew wrote it. An open pull request of that branch is taken instead of a second one. Without the trust service a crew cannot read CI checks, view workflow runs, start an allowed workflow or call `gh api`; `git` over HTTPS works.

The owner can opt in with `crew_allow_macos_trust_service: true` in the owner config. Crew settings then set `sandbox.network.allowMachLookup` to exactly this service, and crews open their own pull requests. This weakens the network boundary: the sandbox does not confine what the trust service does, and a crew can hand it a certificate it built itself whose issuer (AIA) or revocation (OCSP, CRL) address points to any host. The trust service then fetches that address outside the network allowlist, which is a real channel out of the sandbox. Opt in only when you accept that.

## What a review binds

A reviewer's time is held by the guard, which runs inside subagents too: each analyzer subagent has its minutes from its start, after which every tool call of it is refused and the refusal is appended to a per-run file, so `collect` refuses an approval after any timeout unless every mandatory analyzer reads `skipped: timeout` and as many analyzers read it as subagents were stopped (subagent types are the model's choice and are not trusted to map to analyzers), and after the session's deadline only the report may be written. A timed-out mandatory analyzer reads `skipped: timeout` and refuses the approval; `tick` stops a reviewer still alive well past its deadline. Like the rest of the guard this is a convenience against a hung step, not a boundary: a subagent stuck in one long model turn makes no tool call to refuse until it returns, and the hard stop is the tick's.

A launch refuses a pull request from a fork, or one it cannot read, because a reviewer loads that head and runs its tests with the crew token and network. Launch records the head its tier and analyzers were chosen for; an approval of any other head needs a relaunch. A launch also refuses a pull request whose base is neither the repository's default branch nor listed in `review_bases` (empty by default), so a crew cannot get its work approved against a branch of its own. The reviewer's brief names that base for its fetch and its diff, so the verdict is about the diff against the base it is bound to; a base name that is not safe to write into a command refuses. A launch writes its record with its start, then clears any earlier approval of that pull request under the board lock, so a review that fails or never finishes leaves none, and a collect running at that moment sees the newer review. While a review is open, `queue add` and the merge refuse as a second net. `collect` stores the approved head and the base branch from the launch record on the builder item, and a request for changes clears both. Only one review of a pull request runs at a time, and only the verdict of the review started last counts; a superseded verdict changes nothing and is not counted as a round. A review counts as running unless its record says it was stopped, its item is merged or dropped, its process is gone or the pid has another start time; one that cannot be verified counts as running. `studio stop` signals only a process with the start time stored at launch. When something lives on the pid that cannot be shown to be that crew, for example a process group whose leader ended, it gets no signal from any command: `studio stop <id> --release` closes the record for the owner, and it and `collect` print the pid and what to check by hand. A pid another process holds now blocks nothing, because that crew is gone. `queue add` and the last step before the merge require that base and that head, and `--match-head-commit` pins the merge to the head.

Merging the base into a branch changes the head without changing what was reviewed, so one more commit counts as approved, whoever made it, if it passes all of this: two parents, the approved head first, the other already on the approved base, committed by `web-flow` with a verified signature, and a tree identical to what `git merge-tree --write-tree` gives for those two parents in the owner's checkout. The signature alone would prove little; the tree comparison is what shows that nothing else came in. A conflict makes that merge fail, so a conflict resolved by hand needs a new review, and so does a merge result where GitHub and the local Git differ. A second update on top of the first has another first parent and needs a new review too. Limit: `gh pr merge` cannot pin the base, so a pull request moved to another base between the last check and the merge is merged there; branch protection remains the boundary. The pause and block check is the last step before the merge, and the same small window applies.

## Merging a pull request without a review (`studio merge`)

`studio merge` lets the lead hand the queue a pull request that no Studio reviewer has seen: it bypasses the review requirement above on purpose, for work reviewed elsewhere. What stands in for the approval is GitHub's branch protection (required reviews and checks) and nothing else, so protect the base branch server-side before relying on it. The command refuses `STUDIO_ROLE=crew`, and the crew guard denies crews the studio CLI. It only queues pull requests of repositories in `repos`, and refuses one that a board item holds, at queue time and again right before the merge, so a builder's work cannot skip its review this way; an open Studio review of the pull request refuses it too. Studio does not update the branch, and every failed or cancelled check stops it (no rerun, no exception by evidence). The head the pull request had when the lead ran `studio merge` is recorded with the entry, and only that head is merged (`--match-head-commit`): a push after the enqueue fails the entry, so code the lead did not see is never merged. `--follow-head` is the explicit opt-out: then a later head, once its own checks pass, is merged as well, and whoever can push to the branch decides what merges. Who asked (`--by`) is a label for the record, not an identity: anyone who can run Studio as the owner can name anyone.

## Exceptions by evidence

An exception waives failed checks of a guard job for one pull request at one base and one head commit. A built-in proof runs no command: Studio computes it (`comments_only`, `paths_only`) itself, in TypeScript, over blobs and paths that git gives it with pinned options, so nothing of the pull request is executed. Both proofs cover every changed file of the pull request, with case-sensitive paths. `comments_only` reads SQL as PostgreSQL does, over the exact bytes, and accepts only plain comment text edited or added: invalid UTF-8, a backslash, a lone carriage return, form feeds, vertical tabs and changed line endings prove nothing, a line comment always ends a line, and the tokenizer is linear and errs towards "not proven": comments with a meaning (migration and query directives, tool names) count as code, executable comments and hints prove nothing, what it cannot classify for sure proves nothing, and so does an added, deleted or renamed file, a mode change, a symlink, a submodule, a binary or very large file, or a path with a control character. Rust, TypeScript and JavaScript (with JSX), YAML and TOML are read by tokenizers of their own, chosen by file extension, under the same rules. Shell and Python are not, on purpose: a script in them can read its own source and line numbers in too many ways (`$0`, `LINENO`, `caller`, `eval`, `set -v`, `__file__`, `inspect`, frames, `logging`, encoding lines) for a deny list to be complete, so a comment-only diff may change what it does; for those files the proof does not apply. The threat is code hidden in what the tokenizer takes for a comment, so each one refuses every construct whose extent depends on context it does not track instead of guessing (a `/` that may be a regular expression or a division, a `<` that may start JSX, a plain scalar over several lines); markers inside strings, raw strings, templates, regular expressions, JSX text and block scalars are content. Separators that some readers take for line ends (U+2028, U+2029, NEL), bidirectional controls (code that reads otherwise than it shows) and a byte order mark prove nothing; indentation is code in YAML; YAML must also load to the same data in a second reader. Rust doc comments count as code: they become `#[doc]` attributes, run as doctests and reach the program through derive macros. Comments that tools read (pragmas, type and lint directives, shebangs, bundler hints, JSDoc tags) count as code, and Rust `line!` or `column!` proves nothing. The rules are read from `.studio/studio.yaml` at the pull request's base commit on the default branch, never from the working tree or the pull request, so a pull request cannot bring the rule that waives its own hit, and one that changes the `evidence:` block gets no approval from Studio (checked for every approval from the base; the approval waits when that cannot be read). The merge queue judges the waiver again right before the merge and reads the base commit once more immediately before it merges, so a base that moved is judged on its own. The log `exceptions.jsonl` lies in the state root, which crews cannot write; `studio exceptions grant` refuses `STUDIO_ROLE=crew`, and the crew guard denies crews the studio CLI. Proof commands are below.

The lead is trusted here: it runs as the owner and can grant an exception. `owner_only` tells the owner's grant from the lead's by a terminal, not by authentication, so it guards against a lead's mistake, not against a compromised lead session. A guard that branch protection requires still blocks the merge on GitHub: waiving is Studio's gate only, never the server's.

### Proof commands

A `proof: command` rule runs a command of the project on the owner's machine to prove a property of a pull request. The command is trusted as far as the owner trusts the default branch: it comes from `studio.yaml` and the base tree at the pull request's base commit, never from the pull request, and a pull request that changes `evidence:` gets no approval. What is not trusted is everything the command reads from the head (the tree in `STUDIO_PROOF_HEAD_TREE`, the diff, the changed paths). A command that runs code or loads configuration from there (a linter's config, a plugin, a build) lets the pull request decide its own verdict. The sandbox contains the side effects of that, not the verdict. **A proof command must never execute head content** (run a script, load a config or plugin, build or import anything from the head tree): it reads the head as data only.

The threat model, and what holds against it:

- **A hostile head reaches the command's process** (an exploit in a parser, a config the command loads). The sandbox limits what that process can do:
  - No network: on macOS every socket, Unix domain sockets included; on Linux an empty network namespace.
  - Writes only in the run's `tmp` dir, never in the base or head tree.
  - No reads of the home or other homes, the state root, the owner and Claude config, credential stores, the shared temp dirs or removable volumes; on Linux nothing of the host is mounted but the system dirs, the toolchain paths and the run dir.
  - On macOS every Mach service is shut except logging, notifications and user lookup, and so are LaunchServices and AppleEvents. That keeps the process from handing work to a program outside the sandbox (an `open`, a keychain lookup). It registers no Mach service, uses no POSIX or System V IPC, and can neither signal nor inspect a process outside its own sandbox. On Linux new namespaces of every kind, no capabilities and a new session (no terminal input injection).
  - The environment is an allow-list, so no token, proxy or PATH of Studio's reaches it.
- **It shapes what the command sees.** Base and head are written out blob by blob from `git ls-tree` and `git cat-file`, never with `git archive`, so `.gitattributes` (`export-ignore`, `export-subst`, filters) cannot make a tree differ from what git stores. A tree with a symbolic link, a submodule, another mode, a path that leaves it or names `.git`, two paths that differ only in case, more than 128 MiB of blobs or more than 50,000 files is refused before anything is written.
- **It tries to outlast or exhaust the machine.** CPU time and file size are capped by `ulimit` in the process and every child. The wall-clock timeout kills the process group (on Linux the PID namespace dies with bubblewrap). Stdout beyond 1 MiB kills the run.
- **It tries to fake a proof.** Only exit 0 together with the line `proven <nonce>` proves, and the nonce is drawn per run and handed to the top-level command on fd 3 only, never in the environment or a file: a child the command starts after reading fd 3 to the end (head content it should not run, but might) finds the pipe empty and the nonce nowhere, and a command that echoes the diff cannot prove by accident. A command that starts children before reading fd 3 hands them the nonce; that is the command's bug.
- **No sandbox.** On a platform without one (native Windows, a Linux without bubblewrap or without unprivileged user namespaces) or when the tool refuses the profile, no command runs and the rule proves nothing. A probe runs the real profile once per process.

Limits:

- On macOS the profile allows by default and denies the places above. Files outside them stay readable: system dirs, `/Library/Developer`, `/Library/Frameworks`, `/opt/homebrew`, `/opt/local`, `/private/etc`. Process information and signals are limited to the sandbox itself (`same-sandbox`), and POSIX and System V IPC and Mach service registration are denied. A profile that denies by default would be stronger; it breaks too many tools to be the first step and is an open item.
- Memory and process counts have no limit of their own beyond the wall clock and CPU time.
- Disk use in `tmp` is limited per file only.
- The extracts carry no installed dependencies, so tools must be on the system or in `crew_toolchain_paths`; those paths are readable by the command.
- Seatbelt (`sandbox-exec`) is deprecated by Apple, though still shipped and used by Claude Code's own sandbox.

## Releases

A release starts one workflow file named in the component's `release:` block of `studio.yaml` at the release commit on the default branch; Studio runs no command of its own and never the way back. A block with commands is refused for the reason 0.17 gave for evidence: a command would need a real sandbox. GitHub dispatches on a branch only, so the commit travels as the input `sha`, and the workflow must deploy exactly that input: Studio cannot check what a workflow does with it, only that the file is byte for byte the one at the release commit and declares the input. An entry of `crew_allowed_workflows` that `gh workflow run` would resolve to the release, a post-check or the rollback workflow (by id, file or display name, ignoring case, against `gh workflow list`) refuses the trigger, and `studio release` refuses `STUDIO_ROLE=crew`; the guard also denies crews the `studio` CLI, but as everywhere the sandbox and a least-privilege crew token without `actions: write` on the deploy are the boundary, not the guard. Branch protection on the default branch matters here too: whoever can push to it can change the release workflow for the next release. A pull request that changes a component with a release (its whole entry), a workflow such a release starts or names, or `crew_allowed_workflows` while a release exists gets no approval from Studio. Once a release exists, everything below `.github/` (the scope of the pin), and every file a component's `guarded_paths` match, is the owner's as well for Studio's approval; a link or submodule added there, or on the way there, too. Links and submodules inside the pinned scope refuse a draft or trigger, because the pin cannot follow them: what a release workflow runs is part of the release. The owner must list the scripts the workflows call outside `.github`; Studio does not read workflows to find them, so an unlisted script is a gap. The announced record pins each workflow's blob, the tree of `.github` and the guarded files; the trigger refuses another one at the release commit or the branch head, reads the head again right before the dispatch, and holds the release run to that head. A small window remains between that last read and GitHub's dispatch; a run of another head is then failed closed, but it ran. The rollback workflow is pinned the same way, and its pin is checked again whenever Studio shows the way back; one that changed is not offered.

While a release exists, all of `studio.yaml` but `stacks` is the owner's for Studio's approval, compared camelized, and a key written in two spellings is refused. A run is the release's only when its id lies above the newest run of the workflow before the dispatch, and nothing starts while a run of the workflow is on its way. A release whose deploy Studio could not confirm blocks the next one until the lead or the owner resolves it after checking production; that check is theirs, not Studio's. The announcement is pushed by the release command itself, recorded, and the trigger waits a tick or 5 minutes after it.

The owner's approval for a migration that is not clearly additive needs a terminal, as `pause` does: that tells the owner from the lead by the terminal, not by authentication, so it guards against a lead's mistake, not against a compromised lead session. The lead is trusted: it runs as the owner, records third parties' approvals, and could record one nobody gave. The record states who said it, when and the words, and the log `releases.jsonl` keeps it, but nothing proves the words were said. Studio sends nothing to anyone but the owner's phone (fixed phrases and ids). Notes, the log and the board carry Studio's own text, board titles, paths and configuration names, never file contents or values; an approval text shaped like a credential is refused, which catches common token formats only.

The migration kinds come from an allow-list of exact statement shapes over a tokenizer, not a SQL parser: a statement that does not match a shape from its first token to its last is `unclear` and needs the owner, so a mistake lands on the side of asking; queries, copies, partitions, computed or non-literal defaults, call shapes, triggers, rules, functions and `DO` blocks are never additive. It reads only `.sql` files; a migration in another language is `unclear` by definition, and one outside the configured `migrations` paths is caught when it is a `.sql` file of the component or a path segment contains `migrat`.

## Workers on other machines

A worker (`studio worker`, see the README) runs crews on a machine other than the lead's. The boundary there is the same as on the lead's machine: Claude Code's sandbox, a least-privilege token and server-side branch protection. The guard is a convenience on a worker too. What crosses between the machines is public: offers and claim comments are issues and comments, claims and reports are commits on `refs/studio/claims/<id>` of the primary repository. Treat all of it as visible to everyone who can read the repository, even when it is private: an offer carries only board fields and a nonce (no secret, it only ties a comment to one offer), a claim only Studio's own lines and numbers, and a report the crew's report as the pull request body carries it anyway. A report that matches a credential pattern, or holds the worker token or the crew token, is never published; the pattern check catches common token formats only.

**Sandbox and platform.** A worker never starts a crew without a sandbox: Claude Code's (`failIfUnavailable`), which runs on macOS, Linux and WSL2 only, or on native Windows the crew sandbox user below. On native Windows Claude Code runs commands unsandboxed, so without that user `studio worker` refuses there, under WSL1, and when signs of WSL leave its version unclear. Under WSL2 a sandboxed command can hand a Windows program to the host through interop; that program runs as the Windows user, outside every Linux rule, so the worker refuses while interop is on or its state cannot be read, checked again before every claim. The consequence is plain: a worker can analyse files of a Windows machine (read-only, only the places the owner opens with `allow_read`) and run Linux tools there, but it cannot run Windows programs, builds or device tools. Those stay on the CI's Windows runner or with a person, as 0.17 decided for commands Studio cannot sandbox.

**Native Windows: a crew user per job (experimental, not yet piloted on a real worker).** With `workers.self.windows.crew_user` (a name prefix of at most 13 characters) a native Windows worker runs each crew, Claude Code included, as a local standard user instead of in Claude Code's sandbox (which does not exist there). Every job gets a user of its own:
- **Fresh per job.** The setup makes a local group of Studio's (`<prefix>s`) that carries what every crew user must have: the outbound firewall rule, the denied logons (batch job, service, network, remote desktop) and read on Node.js, Studio, Claude Code and the toolchains. Before a job the worker makes a new standard user `<prefix>-<6 hex>` in Users and that group, never in Administrators, with a random password sealed for this machine (LocalMachine DPAPI) in a file only SYSTEM, administrators and the account Studio runs as may read. The probe and the crew run as it; once a crew was granted places as it, the next job never runs as it again. After the job, and before the next user is made, every crew user is retired, and retiring never waits for a profile to be deleted. Per user, each step runs only when the one before it held, while the other users go on: the user is locked (disabled, with a new random password nobody learns: the relay account, which could unseal the old one, can no longer start a process as it); none of its processes may be left after the sweep; its profile leaves the profiles folder in one rename into the quarantine (`<profiles folder>\Studio crew quarantine`, owned by administrators, its DACL protected: SYSTEM and administrators only) and Windows forgets it; none of its processes may be left after a second sweep; its SID goes on the list of retired SIDs (in the quarantine, admin-only); only then is the account deleted. A user whose step failed is kept, locked, so the next sweep still finds it and the next retire tries again; each failure is reported by user. Every sweep also looks for the processes of the listed retired SIDs (a SID leaves the list once none is left), and a fresh user is refused while any process of a crew user or a listed SID runs. A process whose owner cannot be read could be a crew user's: it is never ended, and it holds every crew user (the minimal processes of the kernel, pid 0 and 4 and those pid 4 started, have no owner and are left out). Each run then deletes up to 20,000 entries of the quarantine (`bin/studio-tree.cs`), so a huge tree goes away over several runs and never holds up a fresh user; doctor names how many profiles wait there, and the free-disk check of a relay worker holds starts if space runs low. Only a local user named `<prefix>-<6 hex>` with Studio's description counts as a crew user; nothing else is ever deleted, and a member of the group that is anything else refuses every sweep, retire and fresh user. A profile is moved only when it is a folder right below the machine's profiles folder and not itself a reparse point. The tree deleter opens every entry as itself: a link or junction is deleted as the link and never followed, also one that appears after a folder was listed (the folder is then not empty and is listed again). With the backup and restore privileges an entry is listed, moved and deleted whatever its DACL says, so a Deny entry of the crew's cannot stop it and no ACL is changed or handed down anywhere; paths go to Windows with the `\\?\` prefix, so length is no limit; the walk keeps only the current path, so memory grows with the depth, never with the number of entries. An entry that cannot be deleted is skipped for the rest of a run; one that failed three runs in a row is left alone from then on and named to doctor with its path, so pruning goes on past it. The tree deleter is compiled only from a copy in an admin-only folder (a relay worker's admin-only copy of Studio; on a native worker `%ProgramFiles%\Studio crew`, which the setup fills), never from the plugin cache, and its compiler writes its temporary files into an admin-only folder of its own, never SYSTEM's shared TEMP. The setup also removes the one shared crew user of earlier versions with its profile and firewall rule. What a crew leaves in its profile (Run keys, Startup, PowerShell profiles and modules, COM classes, environment values) goes with the user; no later job runs as it.
- **The boundary is the account.** Windows' default profile ACL keeps the owner's profile closed to it, with gh, git and SSH logins, Studio's owner config and state.
- **One run's places only.** Studio grants the user of the job only the places of one run, by SID, records every grant owner-side under a lock across processes, and takes them off when the crew ends, when it is stopped, and before the next grant. One crew runs at a time on the machine, across all projects. Before each grant Studio ends every process of every crew user it finds by owner SID (a scheduled task or a WMI start could outlive a job); one it cannot end refuses the grant. The probe refuses while a scheduled task runs as the user. Files a crew creates are owned by the crew user, and an owner may by default change their ACL. So taking a place back runs in one fixed order:

1. The sweep ends every process of every crew user (the keeper has ended its job already).
2. The grant on the place's root is removed, and the root's owner becomes Studio's account. This happens even when a later step fails, so the crew user loses its access at once.
3. The place is walked with lstat, and every link or junction in it is removed, so no ACL work as the owner can reach outside the place.

If the sweep or the walk fails, the place stays on record and is reported, and the recursive steps do not run. Otherwise Studio resets every ACL below the place to what it inherits (dropping CREATOR OWNER entries and any the crew set) and gives the owner of everything there back to the account Studio runs as, named by its SID. Every `icacls` call runs with `/L` and is checked; a failure refuses the next grant. The folder keeps an inheritable OWNER RIGHTS entry that leaves an owner nothing of its own. The probe checks this each time: a seed run makes a file in a granted place, the place is taken back, and the probe must fail to change that file, its ACL, or add a file. Each run gets its own Claude config dir; the shared skills and plugins are read-only to it.
- **Network.** A firewall rule blocks its outbound connections to everything but loopback. A proxy on loopback lets it reach only allowed names; the proxy resolves each name itself, refuses answers that point inside (loopback, private, link-local, carrier-grade NAT, multicast, unspecified, reserved, documentation, discard-only; an IPv6 address is judged by the IPv4 address it carries as mapped, compatible, NAT64, 6to4 or Teredo) and connects to the checked address.
- **The keeper.** It unseals the job's crew user password itself; Studio's own process never handles it. A keeper (a PowerShell of the owner) starts the host as the crew user, puts it into a kill-on-close job object before the host has its spec, and hands the spec (the crew's environment, the Claude token included) over a named pipe that only the owner and the crew user may open, after checking that the pipe's client is that host. Nothing of it is written to disk. Studio identifies and stops the keeper, an owner process, by its creation time and owner SID; ending it ends the job and the crew's whole tree. Host and keeper output goes to owner-only files, so no crew-planted link is followed with the owner's rights.
- **Proof before trust.** The worker does not trust the setup. Before every claim it proves the isolation with a probe running as the user of the coming job: the user, the SID made for this job and a profile no older than that user (never one an earlier crew ran as), not an administrator, owner profile, owner config and deny paths unreadable, owner home and shared crew Claude config dir unwritable (a write grant an earlier setup left there is taken off by the current one), no direct connection out, the proxy refusing other names, the environment arrived, no scheduled task running as the user. It refuses on any failure or silence.

This is weaker than the Linux and macOS sandboxes in ways the probe cannot cover:
- The Windows firewall does not filter loopback. The crew can reach every service listening on loopback of the worker machine; denied ports are refused only by the guard, a convenience.
- Places outside the owner profile that grant Users, Authenticated Users or Everyone access (folders created at a drive root, shared data folders) are open to the crew user unless they are deny paths; the probe checks only the deny paths, the owner profile and the owner config.
- The crew can append anything to its own log, which the worker reads for usage, limits and session ids, as on the other platforms.
- The process sweep finds the crew users' processes through CIM and ends them, and making and deleting users needs an administrator too. A worker that does not run elevated therefore refuses every grant and every claim ("nothing visible" never counts as "nothing running"). Run the worker in an elevated session; the crews still run as standard crew users. A scheduled task that runs only while the crew user is logged on interactively is not prevented by the denied logons; the probe refuses while one exists, and the user is deleted after its job.
- What a crew writes outside its profile, into places of the machine that every user may write (shared data folders, a folder created at a drive root), outlives the job's user; a later crew, as another user, can read it where those places allow. Deny paths and the guard cover what the owner names.
- The identity check reads another process's owner through CIM; it was tested on an elevated runner. On an account without administrator rights an unreadable owner leaves the crew unverified, which holds it rather than signalling it.

The windows-latest CI job runs these, all on a GitHub-hosted runner:
- the setup script, with the crew users' group;
- the probe as a crew user made for the coming job, twice as the same user before any crew ran;
- a crew started through the keeper as the user of its job, which gets its spec by pipe with no trace of the token on disk and is identified by the keeper; stopping the keeper ends it and a grandchild, its grants are gone, and its user and profile are deleted without following a junction the crew planted in the profile;
- a second crew, as a fresh user, which cannot read a file the first one created; after it, the next probe runs as yet another user and the earlier one is gone;
- a junction a crew planted to a place of the owner's: taking the clone back removes it and leaves that place's ACL as it was;
- a write grant on the crew Claude config dir as an earlier setup left it: the probe refuses, and the setup takes it off;
- every probe there seeds and takes back a place, so the check of a place taken back runs on Windows too.

It does not run a real Claude Code session, a real build, or a worker against GitHub.

**The other way round.** Windows processes of the same Windows user can read and write the whole Linux file system of the distribution through `\\wsl$` (`\\wsl.localhost`), the worker's state root with its clones, logs and briefs included, and the worker token file. The Linux sandbox does not stand between the two. Run the worker in a distribution of a Windows account that runs nothing else, or accept that every program of that Windows user can see and change what the worker holds.

**Deny lists.** Each denied path goes into the sandbox's `denyRead` and `denyWrite` (literal and real spelling) and into the guard's secret paths. On WSL2 the automount root and every `drvfs`, `9p` or `virtiofs` mount of `/proc/self/mountinfo` are denied by default; `allow_read` reopens single places for reads, never inside an explicitly denied path. Windows drives under WSL2 ignore case, and a sandbox rule names one spelling, so a denied Windows path denies the whole drive it lies on, and an opened place opens only the spelling written (the safe side). A mount that appears after a claim is not denied until the next claim. The rules are checked against the paths and the settings, not with a crew on a real Windows machine. Ports are enforced by the sandbox's network rules: a command has no direct route, and the proxy refuses names that resolve to local addresses. What could reach a port of the worker machine is an allowed host that is local, judged after normalising it as a resolver does (case, a trailing dot, URL host parsing): an IP address in any spelling a resolver takes, `localhost`, a bare `*`, a single-label or local-suffix name; with ports denied, such an entry refuses the claim. Not covered: a public DNS name that points to a private address of the network (Claude Code's proxy checks local addresses, not private ranges; on native Windows Studio's own proxy refuses private ranges too), and a port on another host that an allowed name without a port leads to. Name ports in `sandbox.network_allow` on workers whose network holds such services. The guard's check of port numbers in commands is a convenience: a script can compute a port.

**Identity and trust.** A worker acts with its own GitHub token (`worker-token`), never the owner's login and never a token a crew holds. It refuses a token whose login is the lead's, one equal to the crew token, and one whose account (`GET /user`) is the crew token's. It calls GitHub in-process (HTTPS from Node, no redirect followed), so the token is not in the environment of a child process while a crew runs; the git push for a crew without a token is the one exception, a short-lived git process with the token in its own environment, visible to processes of the same user for that moment. A crew gets at most the crew token, or none; then the worker pushes the crew's branch after it ended, from a fresh blob-less clone of the repository that only fetches from the crew's clone (git reads a repository it fetches from as a remote, without its hooks). On the lead's machine, an accepted worker account that is the account of the lead's crew token refuses: any crew of the lead could act as that worker.

The claim ref is only the lock. Nothing in a claim commit identifies its writer: the content is the writer's, GitHub matches author and committer by e-mail, and API commits of a user token are unsigned (checked on GitHub). Identity comes from an authenticated action instead: the worker posts one-line comments on the offer naming each claim commit that matters and the offer's nonce, and GitHub sets the comment's author from the token. The offer is locked when it is opened, so only accounts with write access can comment, and the lead reads only comments whose `author_association` is OWNER, MEMBER or COLLABORATOR, unedited, by an account whose numeric id is accepted for the label under `workers.accept` in the owner config (outside every repository; ids, because a login can be renamed and reused). Everything else is a warning for the lead and never decides or blocks a claim. The first counted comment for the commit that started the attempt must come from the account the claim names; every later state change (`done`, `released`) must be announced the same way by that account, naming its exact commit; below the tip a chain may hold heartbeats only. An offer with more comment pages than Studio reads decides nothing. Leases run from the time the lead (or a worker) first saw a claim commit, on its own clock, never from the commit's dates. The lead takes the pull request the claim names only when it comes from `studio/<id>` of the item's own repository, its head equals the report's `head_sha`, and its author's id (set by GitHub) is the claiming worker's; a worker never renews a pull request of another account or a fork. The role text, lessons and solutions in a worker's brief come from the pinned `origin/main`, never from the worker's working tree.

Offers are taken only from the configured lead login and only when nobody else edited them; the worker token needs issue write for its comments, so it could open or edit an issue, but a worker ignores offers others opened or edited, and the lead ignores edited claim comments. A worker that deletes another worker's comment can at most leave that claim unproven, which goes to the lead; it cannot take it over. Any account with contents write, a crew token included, can write or remove claim refs: it cannot forge a claim or a report that counts, but it can deny one (move, block or remove it), which delays the item or goes to the lead. A ruleset that restricts `refs/studio/*` is untested and probably not possible (GitHub documents rulesets for branches and tags); Studio relies on none (README, "Claim refs and rulesets"). The guard refuses crew pushes to `refs/studio/*` (also short names git would match there) and every `gh api`, as a convenience. Usage figures are what the worker reports, capped per run at the daily cap; a worker could report less than it spent. Accept only machines you control. A worker cannot approve or merge anything for Studio: approvals come from the lead's reviewer crews, merges from the lead's queue with the owner's login. It can still do on GitHub what its token allows, so protect `main` server-side against pushes and merges by worker accounts, and do not let their GitHub reviews count toward required approvals.

## Relay workers

A relay worker (README, "Relay workers") is a worker machine that holds no GitHub credential and no credential of the lead's machine. The lead connects to it over SSH, never the other way round, and does everything on GitHub itself. Experimental: not yet piloted on a real native Windows machine.

**What crosses.** One SSH session per request, in a small versioned JSON-lines protocol (hello, probe, start, status, collect, stop, cleanup). The worker's side is `studio relay serve`, forced for the lead's key; it never runs a command it is sent. A start carries the item's board fields (exactly what an offer carries), the pinned `origin/main` commit with a git bundle of `main` (and of `studio/<id>` for a fix round), and the crew's Claude token. A collect brings back the report and a bundle of `studio/<id>`.

**The lead's side.** The system ssh client runs with no config file (`-F none`), the host key pinned in a known_hosts file Studio writes with exactly the configured key under an alias of the label (`StrictHostKeyChecking=yes`, no global known_hosts, no key updates), `BatchMode=yes`, only the configured key (`IdentitiesOnly=yes`, no agent), no agent, X11 or port forwarding, no connection sharing, no proxy command, no password. Each result is crew output: size caps on the report and the bundle, a credential scan of the report (token patterns, the lead's crew token), and the bundle unpacked into a fresh bare directory with no hooks (`--template=` and a hooks path that does not exist), objects checked as they come in (`fetch.fsckObjects`); it must hold exactly one ref, `refs/heads/studio/<id>`, at the report's `head_sha`, descending from the pinned commit (and from the head a fix round started from). Only then does the lead push it with its crew token, never forced, and open or renew the pull request; review, queue and merge are the lead's as for a local crew. The Claude token goes to the worker in the start request only, from the credential the owner's rules pick (provider, active account, or the environment's token); it is never in a command line, a log or a file on the lead.

**The worker's side.** The worker refuses to start anything while it holds a credential (a crew token, a worker token, Claude accounts, a credential provider). The token of a start stays in memory: `relay serve` hands the job to a runner over its stdin. On Windows the runner must be created through CIM to outlive the session, so a PowerShell child of `relay serve` gets the spec on its stdin and writes it into a named pipe whose DACL allows the relay account alone, and only after checking that the pipe's client is the runner it created (GetNamedPipeClientProcessId); `relay serve` itself listens on nothing. The keeper's pipe to the crew host works the same way: an explicit DACL (the owner and the crew user) and the client checked before a byte. The runner gives it to the crew's environment through the launch, and on Windows the keeper hands it to the crew host over its pipe, as for every Windows crew. One crew at a time.

**Threat model: a compromised worker machine.** It holds no GitHub credential, so it cannot push, comment or open anything on GitHub. What it can do: read the code of the projects it got (the bundle of `main` and the job's branch), see the Claude token of the crews it runs (use that account until the token is revoked; give relay crews an account of their own and rotate it), lie in its answers (the lead's checks above hold for any answer: a result counts only as a branch on top of the pinned commit, pushed by the lead, reviewed by the lead's reviewer crews, merged by the lead's queue), report wrong usage (capped per run at the daily cap), and withhold or delay results. It cannot reach the lead: the lead's key works only towards the worker, and the protocol carries no command.

**Threat model: a compromised lead key.** Whoever holds the lead's private key for a worker can do what the lead does there: start jobs (with a Claude token of their own), read states and results, stop and clean up. The key is forced to `studio relay serve` by sshd (`ForceCommand` in a `Match User` block, with no terminal and no forwarding of any kind); the `restrict` option in the authorized keys file is only an extra, because its support in Windows OpenSSH is unverified. The relay account is a standard user, never an administrator, so the key gives no administrator rights on the worker. Keep the key on the lead's machine only (`identity_file`, absolute); `studio relay unpair <label>` on the worker cuts the lead off. The relay account's authorized keys file holds exactly the keys of the pairings the worker records (written by SYSTEM-or-administrator only, readable by the relay account, replaced whole); `relay install` removes every other line and says so.

**What runs elevated on a Windows relay worker.** Only two things, both created by the setup script an administrator runs (`studio relay setup`):
- the setup script itself (Git for Windows 2.35.2 or later, the relay account, ACLs, the admin-only copies of Node.js and Studio, the crew users' group with its firewall rule, denied logon rights and read grants for toolchains, the broker tasks, WebClient stopped and disabled, the pinned plugins of the relay home, run with the admin-only copies), run by `studio relay install` together with the winget installs of Git and Claude Code, the OpenSSH server capability, the sshd block in `sshd_config` (checked with `sshd -t`, put back when it fails) and an inbound rule that lets only the Tailscale interface (or the interface or source range given) reach sshd, with the rule OpenSSH adds for every address turned off. It refuses while any process of the relay account or a crew user runs (before sshd stops, and again after), so no runner or crew can plant a link between its walk of a folder and the ACL it sets; `--force-stop` stops them instead;
- the broker tasks, which run as SYSTEM with no argument and no script file: each script is its task's action itself (`-EncodedCommand`), with the prefix, the answer file and the relay account's SID written in; the functions they share come from `broker\crew-accounts.ps1` of the admin-only tree, read once and run only when their SHA-256 is the one baked into the action. `<broker>` ends every process of the crew users (by SID); `<broker> retire` also deletes them with their profiles as above; `<broker> fresh` retires them and makes the crew user of the coming job, its password sealed for the relay account. Each writes what it did to a file of the admin-only tree the relay account can only read. SYSTEM moves a crew user's profile into the quarantine and deletes it there in bounded steps with the tree deleter above, loaded from the admin-only copy of Studio, never following a link. Only SYSTEM, administrators and the relay account may run them (the tasks' security descriptor).

**Two trees, and who may write what.**
- The admin-only tree (`%ProgramFiles%\Studio\relay`) holds the copies of Node.js and Studio the forced command runs, the worker's config (`workers.serve`) with the crews' Claude config dir and its pinned plugins, the sealed password of the current crew user, the brokers' answer folder and the authorized keys; owned by administrators, written only by SYSTEM and administrators, read by the relay account (Node.js, Studio, skills and plugins also by the crew users' group). The elevated plugin setup writes only here.
- The relay home (`%ProgramData%\Studio\relay`) and `%ProgramData%\Studio` are owned by administrators; the relay account may only read them, and may fill the `state` folder (an ACE on the folder that adds files and folders, and an inherit-only ACE that gives it modify on what is below), never rename or remove it or anything above.
- Every folder of Studio's gets a protected DACL built from scratch (no entry added before survives, also on folders created before the setup ran); an existing one must be a plain folder owned by administrators (or the administrator running the setup), else the setup refuses. A reparse point anywhere on the path, or just below the relay home, refuses. Setting a DACL hands its inheritable entries down the whole subtree, through any junction in it: a folder that already has the right DACL is left alone, and one that gets a new DACL may hold no reparse point anywhere below (found without following one), else the setup refuses. Every `icacls` runs with `/L`, and the copy of Studio leaves junctions out (`robocopy /XJ`). The elevated steps set the ACLs of the home's folders themselves only and write nothing into the relay-writable `state`.
- `relay serve` and `relay run` refuse to run unless they run from the admin-only copies, and unless the tree (with `config`), the relay home and `state` hold: no reparse point (none anywhere in `config`, none just below `state`), owned by administrators, SYSTEM or TrustedInstaller, the DACL protected, and nobody else able to write (in `state`, the relay account only to add files and folders, and below it).

**Uninstall.** `studio relay uninstall` (elevated, refused in an SSH session) removes in an order that never leaves the machine more open than before: first every authorized key and pairing, so no lead can log in; then it refuses while any process of the relay account or a crew user runs (`--force-stop` ends them); then the broker tasks and the sealed crew credential; then the crew users through the same retire path as after every job (a user it cannot retire stops the uninstall before anything else goes); then the group's firewall rule, logon rights and read grants and the group; then the relay account, locked first, its processes ended, its profile moved into the quarantine and deleted there without following a link (only a user with Studio's description); then Studio's lines in `sshd_config` (checked with `sshd -t`, put back byte for byte when sshd refuses) and the inbound rule; then the two trees, deleted without following a link. The first install records in the admin-only tree what it found (WebClient, the spooler, sshd, the OpenSSH server capability and OpenSSH's own inbound rule); uninstall turns a service back on only when that record says it was on, and without a record (an install of an earlier version) nothing, with sshd left stopped and disabled.

**Pairing.** `studio relay pair` makes a key for one worker on the lead and prints one line with the lead's public key, the label and a pairing secret (32 random bytes), which travels only in that line, is used once and expires after an hour. The worker's install records the pairing and authorizes the key. On the first connection the lead reads the worker's host key, connects with it pinned (so the other end holds that key's private part), and keeps it only when the worker answers HMAC-SHA256(secret, its host key), checked in constant time: a machine in the path that presents its own host key cannot compute it without the secret. The full SHA256 fingerprint is shown on both sides for a comparison by eye, which the check does not rely on. Whoever sees the line within the hour and can reach the lead's connection first could take the pairing over: paste it on the worker only.

**The crew user's credential.** An SSH key logon has no password, so Windows cannot open the relay account's own DPAPI keys: the password of each job's crew user is sealed for the machine (LocalMachine DPAPI) in a file of the admin-only tree whose ACL lets only SYSTEM, administrators and the relay account read it. Any process of those accounts on the machine can unseal it; the crew user cannot read the file. The probe refuses with a clear line when it cannot be opened under the current logon.

**Checks before every start (Windows).** The relay account is not an administrator; the crew user of the job is made (a fresh one unless no crew ran as the last one yet) and its credential opens; WebClient is stopped and disabled; the load is below `max_cpu_percent` and free disk above `min_free_disk_gb` (else "not now"); the loopback listeners; the SMB check below; then the probe as that crew user (as for every Windows crew, plus: no stored credential of the crew user, no direct connection to configured addresses and to neighbors of the network, no connection to a denied port on loopback, and the SMB sessions).

**Gaps the probe covers, and how.**
- _Loopback._ The Windows firewall does not filter loopback, and the crew user's rule leaves it open for the egress proxy; Windows counts this machine's own addresses as loopback too. So a crew could connect to any local service. Before every start the relay worker lists the TCP and UDP listeners on loopback and the wildcard addresses (v4 and v6): a denied port listening there holds the start when the crew user can connect to it (TCP), or always (UDP); every other listener is a warning line for doctor. A per-user loopback block in the Windows Filtering Platform would close this; Studio does not build it.
- _SMB and WebDAV._ A UNC path (`\\host\share`) goes through the kernel redirector in the System process, and WebDAV (`\\host@80\`) through the WebClient service: the crew user's firewall rule holds neither, and port 445 cannot be closed for one user. So WebClient must be stopped and disabled, and before every start the crew user opens `\\<host>\IPC$` without credentials against every candidate of `deny.hosts` (a host, an address, an IPv4 range up to /22, `local-subnets`, `tailnet-peers`). Candidates are the explicit entries, the neighbor table inside the ranges and the Tailscale peers, never found by connecting (a firewall that blocks the worker's accounts would make a sweep find nothing). Access denied (5, 86, 1326, 1327, 1331, 1909) and not found (53, 64, 67, 1231) pass; a session that opened refuses the start and is closed at once; every other code holds the start, naming it; a configured range with no candidate refuses (an empty set never passes). A file server that lets the crew user in as a guest or with an account of the same name and password is what this finds; one that is not in the neighbor table when the probe runs is not checked. The guard also refuses network paths in tool paths and commands of Windows crews, as a convenience.
- _Other machines of the network._ Studio does not lock down the crew user's network beyond its own firewall rule; site rules (a LAN, a database next to the machine, the tailnet) are the operator's. The probe checks what it can see: no direct connection to configured addresses (`probe_unreachable`) and to neighbors found above.

**Several leads.** A pairing's label is its lead on the worker (pairing again under a label replaces that lead's key, and `relay install` names every lead it authorizes). Each lead's key carries its lead in its comment (`studio-relay-<lead>`) and in its forced command (`--lead <lead>`); sshd (`ExposeAuthInfo yes`) tells `relay serve` which key logged in, and on Windows that key alone decides the lead (a `--lead` must agree; without either nothing is served). Each lead has its own jobs, mirrors and project checkouts (`leads/<lead>` in the relay state), and every job records its lead: one lead cannot see, stop, collect or clean up another's job. Only "one crew at a time" spans the leads, and a busy machine tells another lead no more than that. Outside Windows the keys are the owner's own: with more than one key forced to `relay serve` in the relay account's `authorized_keys`, each must name its `--lead`, or nothing is served.

**The crew's clone, at collect.** Git never runs inside the crew's clone, not even as a remote (rule D4). Right before the clone is read, the broker must prove that no process of a crew user is left; otherwise the collect waits. Then the worker copies the clone's loose objects and packs (never their index files) as plain files into a fresh repository of its own: `.git` must be a real folder (no link, no gitdir file), with no alternates; each file is opened once without following a link (`O_NOFOLLOW` where the system has it), checked on the open handle to be the same regular file, and copied from that handle, up to a cap; the branch head is read from its ref file or packed-refs. Every pack's index is built anew with `git index-pack --strict`, and `git fsck --strict` must pass before anything is bundled. Git runs only in that fresh repository (no hooks, no replace objects), which borrows the objects of the pinned `main` from the worker's own mirror.

**The lead's answer reading.** Every answer is capped as a whole (the header line, the payload in base64 lines, and a margin), not only per line; once the one answer is read, the lead reads nothing more and ends ssh.

**What a worker reports about accounts.** A usage limit or an account block the crew hit is the worker's word only. It parks the one credential label the lead handed over: for an account block an hour, for a usage limit until the reported reset but at most six hours. It never records an account block that stops every crew of the owner; the lead hears of a reported block and checks the account.

**The lead's result repository.** A result is checked in a repository that holds exactly the pinned `main` (and the head a fix round started from), fetched from the lead's relay repository as a bundle, with no alternates: a result bundle that leans on any other object of the owner's (an unpushed branch, say) does not apply and is refused, so nothing else of the owner's can be pushed with it.

**Network lockdown.** A crew user's own rule blocks everything but loopback, but the relay account runs the crews' egress proxy, and its own connections were open to the local network. `relay install` (and `worker windows-setup` for the group of a native worker) adds outbound Windows Firewall block rules, bound by SID to the relay account and the crew users' group (`LocalUser`), for 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16, fc00::/7 and fe80::/10; the machine's DNS resolvers inside them are carved out and blocked on every TCP and UDP port but 53; `deny.hosts` (addresses, IPv4 ranges, names as resolved at install time, recorded with their addresses; every relay start warns, and doctor shows it, when a name now resolves outside the local ranges to an address no rule holds, or was added after the install; running the install again resolves them anew) and `deny.ports` become rules too. The proxy already refuses names that resolve to these ranges; the rules hold the account itself. The install proves them before sshd starts: a throwaway user outside the group is bound into the rules for one probe and must get the firewall's own refusal (WSAEACCES, 10013) for every local target (each private range, the default gateways, the resolvers off port 53, up to three neighbors); a timeout, a refused or an open connection fails the install closed. It then reads the rules back from the active policy and requires every firewall profile on and taking local rules. Before every relay start the relay account itself must get 10013 from one address in each private IPv4 range, else the start is refused. `--no-firewall` leaves the rules out (and removes earlier ones), is recorded, and doctor says so. Only Windows Firewall is supported: another firewall product that replaces it fails the probe. The install also sets `RestrictDriverInstallationToAdministrators=1` (Point and Print), so no crew user brings a printer driver in through the spooler; the spooler stays on unless `--disable-spooler`. Uninstall removes the rules and puts the policy value back as recorded.

**Gaps Studio does not close.**
- _DNS._ Name lookups of the crew user go to the DNS Client service (Dnscache), which resolves for every process: a crew can encode data in names it looks up, past the firewall rule and the proxy. The print spooler and BITS act for a user in a service as well. For a machine next to sensitive systems, put it in a network of its own (a VLAN, or a host firewall that lets it reach only what it needs) and let the network be the boundary. `studio relay install --disable-spooler` stops and disables the spooler where the machine needs no printing.
- _A crew user per job._ Each job runs as a user made for it and deleted after it with its profile (above), so nothing a crew leaves in its profile reaches a later job. Every PowerShell the crew user runs for Studio (the probe's SMB, stored-credential and fresh-user checks) is the system's `powershell.exe` by full path with `PSModulePath` pinned to `$PSHOME\Modules`, in the environment and as its first statement. The job's user is deleted when its runner sees the crew end, when the lead stops it, and at the latest before the next job's user is made; a crash in between leaves it until then. What a crew writes outside its profile into places every user may write stays.

**Not verified.** No part of the Windows relay mode has run on a real Windows machine yet: the SSH session as a standard account, the runner outliving the session (created through `Win32_Process.Create` because sshd ends the processes of a session's job object), the broker tasks' security descriptor and their encoded actions, making and deleting crew users through them (profile deletion included), `ExposeAuthInfo` on Windows OpenSSH, the ACL checks of the two trees, the machine-sealed credential under a key logon, `Start-Process -Credential` from such a logon, the SMB codes. The CI tests the protocol, the lead's checks, the transport's arguments and the Windows pieces with fakes.

## Reverse engineering (REA)

The researcher role can use the REA MCP server (`rea-agents`, pinned like a plugin) on one analysis directory. What that does and does not protect:

- **Trust mode is the default.** With `research: { trust: true }` in the owner config (the default), REA is installed in full, with its optional dependencies and their install scripts (the native Frida binary and the prebuilt pseudo-terminal binaries, which nothing but npm's lockfile pins), and a researcher crew may use every tool class (`annotate`, `debug`, `observe`, `device`, `export`) without a per-item grant: it can start and instrument programs, capture windows and traffic and drive devices, with the owner's privileges, outside the sandbox. The first launch that uses it prints one notice, once per owner: REA tools run as the owner, outside the sandbox. Choose it on a machine and for targets meant for that. `research: { trust: false }` is strict mode: the static install without optional dependencies or scripts, and the classes the owner opens per item (below). What trust mode does not change: the install is never `npx` and never in a clone; the server starts through Studio's wrapper with a clean environment and no token; its per-run folders are denied to the crew; every path argument is confined to the analysis folder below a granted root; a research item pushes nothing; the privacy check runs before any pull request; artifacts never enter git; reports carry no secrets.
- **The install needs the owner's yes, once per version.** A launch that needs REA and finds it missing installs it only after a confirmation kept in the owner state per pinned version and mode: asked in the owner's terminal (`studio research install` counts `--yes` and `--folder` only there, like the other owner commands), or, with no terminal (a tick), put to the lead as a decision that only the owner can answer: a button in the Studio pane, whose press (a click or a key by the person; a command or the model cannot raise it) writes the confirmation for that version and mode as its own file in the owner state. The engine's file calls offer no rename and no mode, so the pane never rewrites the shared record: Studio takes the file in only when it is a plain file of this user, writable by nobody else, one whole JSON object naming at most `<home>/analysis`, folds it in with a temporary file and a rename (0600) and removes it; a torn or foreign file counts for nothing. New research roots get the toolchain-path checks (never the home or a parent, a credential store or Studio's state), must be the owner's own real folder, not a link, and are stored by real path. The lead's line never offers a command it could run itself. A new pinned version or another mode asks again; a no is kept too. Under `STUDIO_ROLE=crew` installing and confirming refuse, crews have no pane, cannot run `studio` (guard) and cannot write the owner state (sandbox). Limit: the lead session runs as the owner outside any sandbox, so a lead that ignores Studio's rules could write that file itself; the gate keeps an honest or misled lead from confirming through Studio, it is not a boundary against the owner's own account.

- **The server is not sandboxed.** Claude Code starts an MCP server itself, outside the crew sandbox, with the privileges of the owner's account. The boundary for a researcher is therefore not the sandbox but what the crew can ask the server: the guard hook allows only exact, static, read-only tool names and checks their arguments against the tool's schema and every path-like value (default deny, so a tool added by a later REA version is denied until Studio lists it). That makes the guard, a convenience layer elsewhere, the enforcing layer for these tools; a bug in it or in REA's own path handling is a way out. The analysis directory is out of reach of every shell process by the sandbox itself (`denyRead`, `denyWrite`), not by the guard; the MCP server, outside that sandbox, is the only way in, so the guard's argument checks are what confine it. A path argument, and any nested argument named like a place whatever its value, must be absolute and lie in the analysis directory both as written and on its real path; REA resolves a bare name against its own working directory (rea-agents 6.7.0 uses no MCP client roots). A write argument refuses every value but unset, null, false or empty; only limits take numbers. The clone is not an allowed place, and relative paths are refused: the crew writes the clone and could swap a link between the guard's check and the server's read, and a relative path resolves against different directories in the guard and in the server. The crew cannot write the analysis directory, so its links stay as checked.
- **Where the server starts, and with what.** Claude Code starts a stdio server in the session's working directory, the crew's clone, and with the session's environment, which holds the crew's tokens; the MCP configuration has `env` but no working directory of its own (as of Claude Code's MCP documentation in November 2026). So the configured command is Node by its absolute path running Studio's wrapper (`bin/studio-rea-server.mjs`) on a spec file in the state root. The wrapper checks that the spec and every directory it names are the owner's plain files and directories, writable by nobody else, changes to an empty directory Studio owns, and starts the installed package with a new environment built from nothing: `PATH`, a `HOME`, `TMPDIR` and `XDG_*` directories in the run's own folder, npm's user and global config `/dev/null`, and the `rea_env` names the owner config allows. No `GH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, API key or other crew variable reaches the server, and nothing of the clone (`node_modules`, `.npmrc`) is consulted. `NODE_OPTIONS` and `NODE_PATH` are emptied for the wrapper itself.
- **The server's own files.** REA writes copies of what it analyses into its `TMPDIR` and `HOME` (an APK, for example). Those point to the run's folder below the project state root, which is in the crew sandbox's `denyRead` and `denyWrite` and in the guard's denied paths; `collect` and `stop` remove it, and each launch starts with an empty one.
- **Pin and supply chain.** (Strict mode; trust mode differs as said above.) The version is the owner's: `rea_version` in the owner config, an exact `x.y.z` only (no range, tag or prerelease), or Studio's default. A repository cannot pin it, and the whole `research:` block of `studio.yaml` is the owner's for Studio's approval: a pull request that adds, changes or removes it gets none. `studio research install`, the owner's in a terminal, installs the package once into the owner state, which crews can neither read nor write, never with `npx` and never in a clone. It takes the tarball's `dist.integrity` from the npm registry, runs npm with no user or global config, no token, no install scripts and no optional dependencies, and uses the install only when the lockfile names the registry tarball with that integrity; the integrity is recorded beside the install. The earlier install stays until the new one passes the launch check, and comes back if it does not. Every launch checks the record against the pin, the lockfile against the record, the installed version, and that nothing on the way to the package's command is a link or writable by anyone but the owner. No native binary comes in that nothing pins: in rea-agents 6.7.0 only the optional `frida` has an install script (it downloads a native binary), and the prebuilt pseudo-terminal binaries are optional packages too; both are left out, so the `debug` tools that use Frida and the process captures of `observe` fail. Opening them needs a later, separate opt-in that installs those parts with a pinned binary hash. Limits: the registry is trusted for the integrity it reports (the first install is trust on first use, like a lockfile), native code shipped inside the package tarball itself is covered by that integrity only, and the dependencies are held by npm's lockfile integrity, not re-checked by Studio at launch.
- **The owner grants the directory.** `research.artifacts` lies in the repository, and an item's own `artifacts:` (from `studio add --artifacts`) on the board, so alone either could point at any place. Each is accepted only below an entry of `research_roots` in the owner config, outside every repository (by its real path, at `add` and again at launch), and not at a credential store, the home or its parents, the project or the state root. The first-use question adds the folder the owner names (default `~/analysis`) to `research_roots`; nothing else writes it.
- **Target content is hostile.** A program or file under analysis may carry text meant for the model. The brief says it is data; REA marks such results `untrusted_content`. A crew that follows it anyway still has no network beyond the sandbox's list, no token beyond the crew token and no tool beyond the allowlist; the harm it could do is bounded by those, not by the brief.
- **Content does not leave as findings.** A `type: research` item pushes nothing: the guard refuses every `git push` of it and its crew gets no GitHub token. For a researcher's item with a pull request, the privacy check reads what was pushed, the diff over `base...head` in the owner's checkout, every added line, not the crew's clone; a file it cannot read line by line (binary, very large, a link, a submodule, a path git quotes) and a line over 4,000 characters fail it. Every crew field of the report is checked, the pull request title and `not_run_here` lines included. When Studio opens the pull request it checks the pushed branch first and opens none on a hit; an existing one is closed. The check is heuristic. It catches the careless leak, not a determined or encoded one; it does not stop the push itself (the branch is on GitHub before `collect` looks), and it cannot see what the model puts into a commit message or a branch name. Reports of such a researcher still deserve a read before they are merged or published.
- **In strict mode, dynamic work is opt-in per item, by the owner.** `studio research allow <item> <class>` opens a class for that item; it needs a terminal and refuses crews, like `pause`, and the grant lives in the project's state root, out of the repository and the board, so neither a crew's note nor a lead's board edit opens one. Then the crew can start programs, devices or captures with the owner's privileges through REA (and `inspect_recorded_crash` may attach its debugger context with `debug`). Allow it only for a target and a machine meant for that. As elsewhere, the terminal tells the owner from the lead, not by authentication.

## Groups of related projects

- **Membership is the owner's.** A group is listed in the owner config only, by each project's folder and repository; a project's `studio.yaml` cannot name a group, the main project or the paths its crews read (it refuses a `groups` key). A folder whose `studio.yaml` names another repository than the owner config refuses, so a swapped checkout does not inherit a membership.
- **The excerpt is read, not run, and only what the owner listed.** A member crew gets copies of the main project's files under the owner's `reference` globs, read by Studio from the main project's freshly fetched `origin/main` at one commit (never uncommitted work), plain files only, no path with a secret-like segment, nothing below `.git/` or `.studio/`, no binary, no two paths that differ only in case (neither is copied: on a case-insensitive disk one would overwrite the other), capped in count and size, beside the brief, which the crew can read and not write. The brief marks them as reference and data. They are repository content of the owner's own main project, so text in them meant for the model is the same risk as the member's own `AGENTS.md`; Studio's rules win. A main project that cannot be read refuses the member's launch.
- **Other boards are read, never written.** Cross-project dependencies, member items of epics and the group view read the other projects' `board.yaml` and `state.json` (plain files only, no links), and fail closed: what cannot be read holds the item or the epic. A contract change adds an item to the member's own board, under its own lock, never to another project's; the changed main-repository paths reach the crew only in the reference index, as data, never in the item's title or Definition of Done. A crew's pull request that changes `.studio/board.yaml` gets no approval and goes to the owner: the board's dependencies and member items reach into other projects. The group view shows other projects' decisions as item ids and codes only, never their text.

## Build cache

The cache is a way for one crew's output to reach other crews, so it is filled under narrower rules than a normal item (see "Build cache" in the README).

- **Only main, only Studio writes.** The only writer of `<state root>/cache/` is Studio itself, at `collect` of a `done` cache item. A cache crew gets a fresh clone at the `origin/main` commit Studio pinned for its rules, a fresh unseeded `HOME`, no GitHub token, and no access to the cache. No pull request branch, no reused clone and no earlier cache reaches a build that is published. Crews of every other item, a pull request's builder and reviewer included, cannot read or write the cache: it lies in the state base their sandbox denies; they get copy-on-write copies in their own clone and `HOME`, and what they change stays there.
- **A narrow lane, enforced as a convenience.** The guard lets a cache crew run only the commands its brief lists, each exactly as written, write only its report, edit nothing and start no subagent. Like the rest of the guard this is not the boundary: the build itself runs main's code (cargo build scripts and proc macros; pnpm and npm run with `--ignore-scripts`), inside the same sandbox and `network_allow` as every crew. So the cache is exactly as trustworthy as main: code that reached main through review and branch protection can put anything into the target dir that later crews then run, as it could by being built by them directly.
- **Taking the result.** Studio copies only real directories reached without a link (`target/`, `.cargo/registry`, `.cargo/git`, `.pnpm-store`, `.npm`); links inside are copied as links, not followed, and are confined by each later crew's sandbox. It publishes only for the run it launched: the run record (commit and a nonce, out of the crew's reach) must match the nonce on the crew record collect handles, any other launch of that id removes the record, and the clone's HEAD, read from its files without running git in it, must be that commit. Hard links are never used, so a crew holding a copy cannot change the shared file.
- **Disk.** All caches together stay below the owner's `cache.max_gb`: a publish over it is refused, and a daily cleanup removes the least recently used caches.
- Not verified in a live run: a real cargo or pnpm build under the crew sandbox with the raised Bash time limit; the tests use a stand-in copy and a fake crew.

## Clean-up of finished items

The tick and `studio gc --apply` remove the clone, crew home and tmp dir of a finished item (see the README, "Clean-up of finished items"). Git never runs in a clone for this: the decision reads `.git/HEAD`, `.git/refs/heads/` and `.git/packed-refs` as plain files with `lstat` (a link or an odd file keeps the clone) and asks GitHub whether each branch tip is in the item's pull request head or in `main`. The crew wrote those files, so a crew can make its own clone look pushed and lose its own unpushed work; it cannot reach anything outside its item's three folders, because only `clones/<id>`, `homes/<id>` and `tmp/<id>` are ever removed, every path is checked against the state root first, and a link is unlinked, never followed. Removal happens under the owner's launch lock and only after the item's crew is checked once more, so a crew that starts in between keeps its folders. A crew cannot run the clean-up for another item: the command refuses crew sessions, and the state root lies outside the sandbox's writable places. Uncommitted changes cannot be seen without git: a merged item's clone goes regardless, a dropped one stays 7 days after the drop.

## What a crew can read

Two rules cover two kinds of reads. Crew shell commands are limited by the sandbox: `denyRead` covers the real home and the state base, and `allowRead` lets back in the clone, the crew's tmp dir and `HOME`, the owner's `crew_toolchain_paths` and the plugin and skill folders of the crew's Claude config dir. The sandbox does not apply to Claude Code's own file tools, so the guard has one plain rule for `Read`, `Glob` and `Grep`, on the real path: allowed are the clone, the crew's own brief with `briefs/<id>.caps/`, `briefs/<id>.rules/` and, for a member of a group, `briefs/<id>.reference/`, its `HOME` and tmp dir, and in its config dir `skills/`, `plugins/cache/`, `plugins/marketplaces/` and `projects/<this clone>/*/tool-results/`, where Claude Code saves a tool output too long to show; the transcripts beside it stay out. Everything else is denied. Paths a tool might read differently from the guard are refused: leading or trailing whitespace, control characters, a leading `~`, and any `..` segment in a read path, a search path or a Glob pattern, because a tool may drop it before or after following a link. A crew writes the path without `..`; the real path then decides. The Glob check is deliberately an allowlist, not a model of glob syntax, and the outer boundary remains the sandbox: a pattern may hold only letters, digits and `_ - . / * ? , { }`, its braces must close and not nest, no brace may remain after expansion, neither the text nor an expansion may hold `..`, and a segment may not be `.?`, `?.` or `??`. Anything else is refused with a message; a crew uses a narrower pattern or Bash in the sandbox. The `glob` field of `Grep` only filters the files below the search path and is not held to this rule. The working directory a tool reports must be absolute, with no `..`. Limit: `*`, `.*` and longer wildcards stay allowed, though a matcher that lets them match `..` would leave the area; the tools are not known to do so, but this was not tested. A symbolic link that a Glob wildcard matches is not resolved by this rule. Inside these locations only a secret rule over a whole directory holding the login gives way; the default secret names and the rules for a single file still apply. A crew's file tools therefore cannot reach other briefs, other clones, a login's credentials or the rest of the home. `CLAUDE_CODE_TMPDIR` points to the crew's tmp dir, so Claude Code's temp files of the run do not land in a directory crews share. Limits: the guard is not a boundary against a malicious crew (see above), so a program a crew runs is limited only by the sandbox, and that still lets it read a provider's whole login dir. This has been checked against the rule and the settings, not in a live run.

## Third-party sources, lessons and review results

Studio fetches a referenced source with `core.hooksPath=/dev/null` and `core.symlinks=false` and only reads it as text: it runs no install step, script or hook of a source. A candidate update stays beside the active copy until `studio sources apply` judges it `fits`, which means every file the contract reads is byte-identical to its recorded hash. Studio does not try to judge changed text: any change is `unclear` for a person or the lead to read. The first fetch is taken on trust, so a copied source file is labelled as data in the brief.

Files a crew reads are copied to `briefs/<id>.caps/`, out of its write reach: only what a matching row names, regular files of at most 256 KiB, with no link on the way. A source file failing this reads `skipped:`.

Lessons are crew output and can carry an injection to every later crew of a role. They are stored as proposals, cleaned to one plain line, need the lead's `lessons accept` and are shown in a labelled data block. The role file is reached with no link on any segment.

Title and text of the pull request reach the reviewer only as a file written by Studio at launch, marked as crew text to read as data, with control characters removed and the text cut to 20,000 characters; the brief names the file, never its content. A builder's `not_run_here` list (commands a missing service kept from running in its sandbox) is crew text as well: each field is one plain line by the report schema, format characters (bidi overrides, zero-width) are stripped, and it reaches the pull request body in a fenced block below Studio's own lines and the reviewer as `pull-request/not-run-here.txt`, labelled as data. `collect` prints only the count and the missing services. It never weakens a gate: an approval still needs green checks, and a skipped check that is not required counts as green there, so the reviewer names for each command the job at the base that runs it and states why that job covers the command (`covers`, one plain line, format characters stripped, at most 300 characters), and `collect` refuses the approval unless that job's check passed on the pull request. The reviewer reads workflows at the base, not in the head the crew wrote, and `collect` checks each named job in the owner's checkout at the pull request's base commit (`baseRefOid`) and at its head: the job is in the named file with no `if:` or `continue-on-error`; the file either runs on `pull_request`, or is a reusable workflow (`workflow_call`) that a job of a `pull_request` workflow calls with `uses: ./.github/workflows/<file>`, that calling job also without `if:` or `continue-on-error`; the workflow whose name the checks carry (the caller's, for a reusable workflow) has a name no other workflow file shares; the check names are the same at the base and at the head; the job's definition, with its calling jobs, is the same at both unless the item is a CI item; and every check of that job passed, `<job>` or `<caller job> / <job>`, each matrix leg ` (<leg>)` included (the leg is everything inside the outer parentheses), skipped, cancelled and missing counting as not passed. A check of that workflow whose name starts with the expected name and a space but does not parse as it (`<job> (1) / x`, `<job> / x`, `<job> (1`) refuses the gate, at collect and before the merge, rather than being dropped from "every check passed". The jobs are stored with the approval and checked again before the merge. What the gate proves is that the named job ran unchanged on the pull request and passed. Whether it covers the command is the reviewer's judgement, recorded in `covers` and shown to the lead by `collect` as reviewer text; no test of the job's steps backs it, because task runners (`turbo`, `nextest`, `make`) hide the command from any text check, and an earlier run-step test gave false assurance. Limits: one level of reusable workflows only; a job that calls a further reusable workflow, a file called only through another reusable workflow, and a remote `uses: <owner>/<repo>/...@<ref>` are refused rather than followed; a calling job with a matrix reports checks the gate does not match, so it is refused as missing; checks are matched by workflow name, which is why a name two workflow files share is refused. A change under `.github/` blocks the approval unless the item holding the pull request declares the changed path in its `paths` or `touches` (a symbolic link at `.github` or below always counts); launch reads the change in the owner's checkout with `git diff --name-only --no-renames <base>...<head>`, counts a symbolic link at `.github` or below, and counts a change it cannot read as one. Limit: the base workflows run the pull request's own code, so `package.json` scripts, test configuration and build files from the pull request still decide what a named job actually does; the gate shows that a base job ran and passed, not what it ran or that it tested what it should. That part stays with the reviewer and with branch protection. The checks the reviewer sees are a snapshot at launch, so `collect` reads them again and refuses an approval unless they pass. A review report is untrusted too. A reviewer loads the pull request into its clone, so a pull request could carry a report file: each launch draws a random 128-bit report name, known only to that crew's brief, and `collect` reads only that name. The report stays inside the clone, because the guard allows crew writes nowhere else. A verdict must name the pull request's head (`head_sha`). `collect` takes the pull request a verdict acts on from the record written at launch, not from the report, and prints analyzer ids, never reasons. Paths from a pull request are matched but never written into a brief. Limit: GitHub reports a renamed file under its new name, so a rename out of a sensitive folder alone does not turn the security analyzer on; the diff review still sees it.
