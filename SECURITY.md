# Security policy

Please report vulnerabilities through GitHub private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**. Do not open a public issue for security problems.

## Security model

The crew guard is a convenience layer, not a security boundary. The boundary is the sandbox, a least-privilege token and server-side branch protection. The guard does not contain a malicious crew: `package.json` scripts, and any program a crew writes, can run anything, so no list of denied commands can stop one. Owner-only commands (`pause`, `resume`, `accounts-clear`) need a terminal, which a crew does not have; that is the real barrier for them. Crews cannot run `studio` directly (the guard denies it), but the guard does not contain a malicious crew; the parser differences between the guard and a real shell that we accept are tracked in issue #10. `main` and any ref listed in `crew_allowed_workflow_refs` must be protected server-side.

## Crew credentials

Studio itself writes no crew credential to state, board, brief, settings, logs or errors, and never prints it. Output of crew commands is logged as is, so a crew printing its environment would put its credentials in the crew log, which lies in a state directory with mode 0700. A provider's token reaches only the environment of the crew process, as does the crew's GitHub token. That means crew shell commands can see both tokens in their environment: keep the GitHub token least-privilege, and treat a crew as able to use its model credential while it runs.

Crews ignore the project and local Claude Code settings of their clone: every launch, fresh or resumed, passes `--setting-sources user`, so only the user settings and the settings file Studio passes with `--settings` apply. Hooks, `env` and `apiKeyHelper` committed to a repository cannot redirect the Claude process, which runs outside the sandbox, or capture a newly issued token. Crews do not auto-load the project `CLAUDE.md`, rules, skills, commands or subagents; Studio itself reads `AGENTS.md` and `CLAUDE.md` from the owner's checkout at a verified `origin/main` SHA (after `git fetch origin main`, ignoring replace objects) and saves copies in the state root beside the brief, a place the crew can read but not write. The brief points to those copies, so a reused clone whose refs or replace objects an earlier run changed cannot alter them. A launch refuses when a fetch fails, when an entry is not a plain file (mode 100644, a blob) or when a file is over 256 KiB. The guard also denies `git update-ref`, `git replace`, `git symbolic-ref` and fetch refspecs (and `--refmap`) that write below `refs/remotes/`; plain `git fetch origin` stays allowed. Like the rest of the guard that is a convenience layer; the copies' safety rests on the sandbox, which allows writes only to the clone, the tmp dir and the crew `HOME`. Crew runs also have Claude Code auto memory off (`autoMemoryEnabled: false` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in the settings file), so nothing a run writes there reaches the next run. The pinned files are ordinary project content: they cannot change settings or Studio's rules and can never direct a crew to handle credentials, change remotes, reach new hosts or change the report contract. A launch refuses when a role's required skill is definitely absent from the crew's config dir. Studio checks only the owner's own `settings.json` for API billing keys.

Stored Claude accounts (`studio account add`) lie in `tokens/` in the owner config directory: the directory mode 0700, each `<label>.json` mode 0600, both owned by the user and never a symlink; anything else makes a launch refuse rather than fall back to another login. Only processes of that user can read them, which includes anything else running as that user. Studio reads a token only at launch and passes it only as `CLAUDE_CODE_OAUTH_TOKEN` in the crew process's environment; it never writes it to state, board, brief, settings, logs or output, and the plugin setup runs without it. The crew's Claude config dir (`claude/` in the owner config directory) holds no token, and of it only the plugin and skill folders are open to crew reads; `tokens/` stays denied to crew shell commands and file tools. A crew process can see its own token in its environment, as with a provider. Not yet checked, and due in the first real run: whether a crew shell can see the environment of other crews' processes, which holds their tokens (for example with `ps eww` or `ps -E`), and what Claude Code writes into shell snapshots in the config dir.

The owner config directory, including the `crew-token` and `notify-secret` files, is denied to crew shell commands and file tools, also when `XDG_CONFIG_HOME` lies outside the home. Of the Claude config dir a crew gets, a provider's `CLAUDE_CONFIG_DIR` or the crew config dir `claude/`, crew shell commands may read only `skills/`, `plugins/cache/` and `plugins/marketplaces/`, which skills need. The rest of it, with the transcripts of all crews using it (`projects/`), `.claude.json`, shell snapshots and any stored login, stays denied to them. Claude Code itself runs outside the sandbox and uses the whole directory; the sandbox covers only the shell commands it starts. The crew's file tools reach the same three places and its own saved tool outputs (`projects/<this clone>/*/tool-results/`), see below. Other logins below the owner config directory stay denied.

The provider is a program the owner configured: it is accepted only from the owner config, as an absolute path to a regular file owned by the current user that neither group nor others can write. It gets a minimal environment, and its output is parsed strictly and never echoed. API billing is off by default, see the README.

Limit and account block detection read crew logs, which contain untrusted tool output, so they match only top-level events from Claude Code. A forged limit event could at worst stop that run and park its label for at most 8 days. A forged block event could stop all crews of all the owner's projects, because they share the account, until the owner clears it with `studio accounts-clear`, which needs a terminal; that is the safe direction, since it only stops work. In the same way, content that provokes a Usage Policy refusal, for example in a repository a crew reads, can stop all crews of all projects until the owner clears it. The block state lies in the owner root below the state base, and the barrier that keeps crews from changing it is the sandbox: it allows writes only to the clone, the tmp dir and the crew `HOME`, so a crew cannot clear a block. The guard's denial of the owner root, `blocks.json` and the `studio` command is only a second net; a program a crew writes itself, or a `package.json` script, can still start the CLI. `accounts-clear`, `pause` and `resume` also need a terminal, which a crew does not have. Detection runs whenever a `studio` command runs in any project: with a block recorded, each run also stops the verified live crews of every other project root, and it does so for stops only, never moving another project's board. A project with no lead running is therefore swept only when another project reconciles. A forged block now stops all projects on the machine, not just one. Crews cannot read the state base, except their own clone, tmp dir and `HOME`, and can write only those three; the owner root is not among them. Push notifications (`notify` in the owner config) are trusted like the credential provider: an absolute path to a regular file you own, not group- or world-writable, run without a shell and with a minimal environment; the message text is passed in the environment with control characters replaced by spaces, and the same stripping applies to titles in the Studio board pane and toasts. Phone pushes (ntfy) carry only fixed phrases, item ids and the project name, never crew text; the topic is their only secret, sent only in the URL path of an HTTPS POST (never in argv), printed once by `studio setup`, and redirects are not followed. A block stops every live crew except on `merged` and `dropped` items, and also when the board cannot be read. Because a recorded pid may by now belong to another process, Studio stores the process start time at launch and compares it before each signal on a block: a mismatch means the crew is gone and nothing is signalled. A live crew with no stored or readable identity is not signalled either; it is reported with item and pid for the owner to check, its block event still counts, and launches stay refused. A launch whose new process has no readable identity is stopped and refused; that child, just spawned by Studio, is the one process signalled without a stored identity. The comparison and the signal are separate steps, so a very small window remains.

## TLS for Go tools on macOS

Go tools such as `gh` verify TLS certificates on macOS only through the system trust service `com.apple.trustd.agent`, which the sandbox blocks. Blocked, `gh` fails with `x509: OSStatus -26276`; `SSL_CERT_FILE` does not help on macOS. Checked locally with `sandbox-exec`: denying that one service reproduces the error, and allowing it fixes it.

By default this service stays shut, and a crew on macOS runs no `gh` at all. It pushes its branch and names the pull request title in its report, with the pull request text as the report body. `collect` then opens the pull request outside the sandbox, with the crew token: title and body are crew text, so control characters are removed, the body is cut to 20,000 characters and passed as a file, and a line says that the crew wrote it. An open pull request of that branch is taken instead of a second one. Without the trust service a crew cannot read CI checks, view workflow runs, start an allowed workflow or call `gh api`; `git` over HTTPS works.

The owner can opt in with `crew_allow_macos_trust_service: true` in the owner config. Crew settings then set `sandbox.network.allowMachLookup` to exactly this service, and crews open their own pull requests. This weakens the network boundary: the sandbox does not confine what the trust service does, and a crew can hand it a certificate it built itself whose issuer (AIA) or revocation (OCSP, CRL) address points to any host. The trust service then fetches that address outside the network allowlist, which is a real channel out of the sandbox. Opt in only when you accept that.

## What a review binds

A launch refuses a pull request from a fork, or one it cannot read, because a reviewer loads that head and runs its tests with the crew token and network. Launch records the head its tier and analyzers were chosen for; an approval of any other head needs a relaunch. A launch also refuses a pull request whose base is neither the repository's default branch nor listed in `review_bases` (empty by default), so a crew cannot get its work approved against a branch of its own. The reviewer's brief names that base for its fetch and its diff, so the verdict is about the diff against the base it is bound to; a base name that is not safe to write into a command refuses. A launch writes its record with its start, then clears any earlier approval of that pull request under the board lock, so a review that fails or never finishes leaves none, and a collect running at that moment sees the newer review. While a review is open, `queue add` and the merge refuse as a second net. `collect` stores the approved head and the base branch from the launch record on the builder item, and a request for changes clears both. Only one review of a pull request runs at a time, and only the verdict of the review started last counts; a superseded verdict changes nothing and is not counted as a round. A review counts as running unless its record says it was stopped, its item is merged or dropped, its process is gone or the pid has another start time; one that cannot be verified counts as running. `studio stop` signals only a process with the start time stored at launch. When something lives on the pid that cannot be shown to be that crew, for example a process group whose leader ended, it gets no signal from any command: `studio stop <id> --release` closes the record for the owner, and it and `collect` print the pid and what to check by hand. A pid another process holds now blocks nothing, because that crew is gone. `queue add` and the last step before the merge require that base and that head, and `--match-head-commit` pins the merge to the head.

Merging the base into a branch changes the head without changing what was reviewed, so one more commit counts as approved, whoever made it, if it passes all of this: two parents, the approved head first, the other already on the approved base, committed by `web-flow` with a verified signature, and a tree identical to what `git merge-tree --write-tree` gives for those two parents in the owner's checkout. The signature alone would prove little; the tree comparison is what shows that nothing else came in. A conflict makes that merge fail, so a conflict resolved by hand needs a new review, and so does a merge result where GitHub and the local Git differ. A second update on top of the first has another first parent and needs a new review too. Limit: `gh pr merge` cannot pin the base, so a pull request moved to another base between the last check and the merge is merged there; branch protection remains the boundary. The pause and block check is the last step before the merge, and the same small window applies.

## Exceptions by evidence

An exception waives failed checks of a guard job for one pull request at one base and one head commit. No user-configured command runs: Studio computes the built-in proof (`comments_only`, `paths_only`) itself, in TypeScript, over blobs and paths that git gives it with pinned options, so nothing of the pull request is executed. Both proofs cover every changed file of the pull request, with case-sensitive paths. `comments_only` reads SQL as PostgreSQL does, over the exact bytes, and accepts only plain comment text edited or added: invalid UTF-8, a backslash, a lone carriage return, form feeds, vertical tabs and changed line endings prove nothing, a line comment always ends a line, and the tokenizer is linear and errs towards "not proven": comments with a meaning (migration and query directives, tool names) count as code, executable comments and hints prove nothing, what it cannot classify for sure proves nothing, and so does an added, deleted or renamed file, a mode change, a symlink, a submodule, a binary or very large file, or a path with a control character. The rules are read from `.studio/studio.yaml` at the pull request's base commit on the default branch, never from the working tree or the pull request, so a pull request cannot bring the rule that waives its own hit, and one that changes the `evidence:` block gets no approval from Studio (checked for every approval from the base; the approval waits when that cannot be read). The merge queue judges the waiver again right before the merge and reads the base commit once more immediately before it merges, so a base that moved is judged on its own. The log `exceptions.jsonl` lies in the state root, which crews cannot write; `studio exceptions grant` refuses `STUDIO_ROLE=crew`, and the crew guard denies crews the studio CLI. Custom proof commands come later, with a real sandbox model.

The lead is trusted here: it runs as the owner and can grant an exception. `owner_only` tells the owner's grant from the lead's by a terminal, not by authentication, so it guards against a lead's mistake, not against a compromised lead session. A guard that branch protection requires still blocks the merge on GitHub: waiving is Studio's gate only, never the server's.

## Releases

A release starts one workflow file named in the component's `release:` block of `studio.yaml` at the release commit on the default branch; Studio runs no command of its own and never the way back. A block with commands is refused for the reason 0.17 gave for evidence: a command would need a real sandbox. GitHub dispatches on a branch only, so the commit travels as the input `sha`, and the workflow must deploy exactly that input: Studio cannot check what a workflow does with it, only that the file is byte for byte the one at the release commit and declares the input. An entry of `crew_allowed_workflows` that `gh workflow run` would resolve to the release, a post-check or the rollback workflow (by id, file or display name, ignoring case, against `gh workflow list`) refuses the trigger, and `studio release` refuses `STUDIO_ROLE=crew`; the guard also denies crews the `studio` CLI, but as everywhere the sandbox and a least-privilege crew token without `actions: write` on the deploy are the boundary, not the guard. Branch protection on the default branch matters here too: whoever can push to it can change the release workflow for the next release. A pull request that changes a component with a release (its whole entry), a workflow such a release starts or names, or `crew_allowed_workflows` while a release exists gets no approval from Studio. Once a release exists, everything below `.github/` (the scope of the pin), and every file a component's `guarded_paths` match, is the owner's as well for Studio's approval; a link or submodule added there, or on the way there, too. Links and submodules inside the pinned scope refuse a draft or trigger, because the pin cannot follow them: what a release workflow runs is part of the release. The owner must list the scripts the workflows call outside `.github`; Studio does not read workflows to find them, so an unlisted script is a gap. The announced record pins each workflow's blob, the tree of `.github` and the guarded files; the trigger refuses another one at the release commit or the branch head, reads the head again right before the dispatch, and holds the release run to that head. A small window remains between that last read and GitHub's dispatch; a run of another head is then failed closed, but it ran. The rollback workflow is pinned the same way, and its pin is checked again whenever Studio shows the way back; one that changed is not offered.

While a release exists, all of `studio.yaml` but `stacks` is the owner's for Studio's approval, compared camelized, and a key written in two spellings is refused. A run is the release's only when its id lies above the newest run of the workflow before the dispatch, and nothing starts while a run of the workflow is on its way. A release whose deploy Studio could not confirm blocks the next one until the lead or the owner resolves it after checking production; that check is theirs, not Studio's. The announcement is pushed by the release command itself, recorded, and the trigger waits a tick or 5 minutes after it.

The owner's approval for a migration that is not clearly additive needs a terminal, as `pause` does: that tells the owner from the lead by the terminal, not by authentication, so it guards against a lead's mistake, not against a compromised lead session. The lead is trusted: it runs as the owner, records third parties' approvals, and could record one nobody gave. The record states who said it, when and the words, and the log `releases.jsonl` keeps it, but nothing proves the words were said. Studio sends nothing to anyone but the owner's phone (fixed phrases and ids). Notes, the log and the board carry Studio's own text, board titles, paths and configuration names, never file contents or values; an approval text shaped like a credential is refused, which catches common token formats only.

The migration kinds come from an allow-list of exact statement shapes over a tokenizer, not a SQL parser: a statement that does not match a shape from its first token to its last is `unclear` and needs the owner, so a mistake lands on the side of asking; queries, copies, partitions, computed or non-literal defaults, call shapes, triggers, rules, functions and `DO` blocks are never additive. It reads only `.sql` files; a migration in another language is `unclear` by definition, and one outside the configured `migrations` paths is caught when it is a `.sql` file of the component or a path segment contains `migrat`.

## Workers on other machines

A worker (`studio worker`, see the README) runs crews on a machine other than the lead's. The boundary there is the same as on the lead's machine: Claude Code's sandbox, a least-privilege token and server-side branch protection. The guard is a convenience on a worker too. What crosses between the machines is public: offers are issues, claims and reports are commits on `refs/studio/claims/<id>` of the primary repository. Treat both as visible to everyone who can read the repository, even when it is private: an offer carries only board fields, a claim only Studio's own lines and numbers, and a report the crew's report as the pull request body carries it anyway. A report that matches a credential pattern, or holds one of the worker's own tokens, is never published; the pattern check catches common token formats only.

**Sandbox and platform.** A worker never starts a crew without Claude Code's sandbox (`failIfUnavailable`), which runs on macOS, Linux and WSL2 only. On native Windows Claude Code runs commands unsandboxed, so `studio worker` refuses there, and under WSL1 as well. Under WSL2 a sandboxed command can hand a Windows program to the host through interop; that program runs as the Windows user, outside every Linux rule, so the worker refuses while interop is on or its state cannot be read. The consequence is plain: a worker can analyse files of a Windows machine (read-only, through the WSL drive mounts, wherever the deny list allows) and run Linux tools there, but it cannot run Windows programs, builds or device tools. Those stay on the CI's Windows runner or with a person, as 0.17 decided for commands Studio cannot sandbox.

**Deny lists.** Each denied path goes into the sandbox's `denyRead` and `denyWrite` (literal and real spelling) and into the guard's secret paths. Windows drives under WSL2 ignore case, and a sandbox rule names one spelling, so a Windows path denies the whole drive it lies on; a narrower rule would not hold. The rule is checked against the paths and the settings, not with a crew on a real Windows machine. Ports are enforced by the sandbox's network rules: a command has no direct route, and the proxy refuses names that resolve to local addresses. What could reach a port of the worker machine is an allowed host that is local (an IP literal, `localhost`, a bare `*`, a single-label or local-suffix name); with ports denied, such an entry refuses the claim. Not covered: a public DNS name that points to a private address of the network (the proxy checks local addresses, not private ranges), and a port on another host that an allowed name without a port leads to. Name ports in `sandbox.network_allow` on workers whose network holds such services. The guard's check of port numbers in commands is a convenience: a script can compute a port.

**Identity and trust.** A worker acts with its own GitHub token (`worker-token`), never the owner's login and never a token a crew holds: it refuses a token whose login is the lead's and one equal to the crew token, and it never passes its token into a crew session. A crew gets at most the crew token, or none, in which case the worker pushes the crew's branch after it ended, from a fresh repository that only fetches from the clone. The claim ref is only the lock. Nothing in a claim commit identifies its writer: the content is the writer's, GitHub matches author and committer by e-mail, and API commits of a user token are unsigned (checked on GitHub). Identity comes from an authenticated action instead: right after creating a claim the worker posts a one-line comment on the offer with the claim commit and the offer's nonce, and GitHub sets the comment's author from the token. The lead counts a claim only when the first unedited such comment for the commit that started the attempt comes from the account the claim names, and that account is listed for the label under `workers.accept` in the owner config, which lives outside every repository. Comments of others, edited ones and second claimers go to the lead. Leases run from the time the lead (or a worker) first saw a claim commit, on its own clock, never from the commit's dates. It takes the pull request the claim names only when that pull request comes from `studio/<id>` of the item's own repository, its head equals the report's `head_sha`, and its author (set by GitHub) is the claiming worker. Offers are taken only from the configured lead login and only when nobody else edited them; the worker token needs issue write for its claim comment, so it could open or edit an issue: a worker ignores offers others opened or edited, and the lead ignores edited claim comments. A worker that deletes another worker's comment can at most leave that claim unproven, which goes to the lead; it cannot take it over, because the first comment must come from the account the claim names. Any account with contents write, a crew token included, can write or remove claim refs: a claim without its comment counts for nothing and a removed claim goes to the lead, but a heartbeat or `done` commit forged on top of a proven claim is not told apart from the worker's own, so such a writer could hand the lead a report (the pull request checks still hold: author, branch, head). Restrict the claim refs with a ruleset (README, "Protect the claim refs"); whether GitHub applies a ruleset to refs outside `refs/heads/` was not checked. The guard refuses crew pushes to `refs/studio/*` (also short names git would match there) and every `gh api`, as a convenience. Usage figures are what the worker reports; a worker could report less than it spent. Accept only machines you control. A worker cannot approve or merge anything for Studio: approvals come from the lead's reviewer crews, merges from the lead's queue with the owner's login. It can still do on GitHub what its token allows, so protect `main` server-side against pushes and merges by worker accounts, and do not let their GitHub reviews count toward required approvals.

## What a crew can read

Two rules cover two kinds of reads. Crew shell commands are limited by the sandbox: `denyRead` covers the real home and the state base, and `allowRead` lets back in the clone, the crew's tmp dir and `HOME`, the owner's `crew_toolchain_paths` and the plugin and skill folders of the crew's Claude config dir. The sandbox does not apply to Claude Code's own file tools, so the guard has one plain rule for `Read`, `Glob` and `Grep`, on the real path: allowed are the clone, the crew's own brief with `briefs/<id>.caps/` and `briefs/<id>.rules/`, its `HOME` and tmp dir, and in its config dir `skills/`, `plugins/cache/`, `plugins/marketplaces/` and `projects/<this clone>/*/tool-results/`, where Claude Code saves a tool output too long to show; the transcripts beside it stay out. Everything else is denied. Paths a tool might read differently from the guard are refused: leading or trailing whitespace, control characters, a leading `~`, and any `..` segment in a read path, a search path or a Glob pattern, because a tool may drop it before or after following a link. A crew writes the path without `..`; the real path then decides. The Glob check is deliberately an allowlist, not a model of glob syntax, and the outer boundary remains the sandbox: a pattern may hold only letters, digits and `_ - . / * ? , { }`, its braces must close and not nest, no brace may remain after expansion, neither the text nor an expansion may hold `..`, and a segment may not be `.?`, `?.` or `??`. Anything else is refused with a message; a crew uses a narrower pattern or Bash in the sandbox. The `glob` field of `Grep` only filters the files below the search path and is not held to this rule. The working directory a tool reports must be absolute, with no `..`. Limit: `*`, `.*` and longer wildcards stay allowed, though a matcher that lets them match `..` would leave the area; the tools are not known to do so, but this was not tested. A symbolic link that a Glob wildcard matches is not resolved by this rule. Inside these locations only a secret rule over a whole directory holding the login gives way; the default secret names and the rules for a single file still apply. A crew's file tools therefore cannot reach other briefs, other clones, a login's credentials or the rest of the home. `CLAUDE_CODE_TMPDIR` points to the crew's tmp dir, so Claude Code's temp files of the run do not land in a directory crews share. Limits: the guard is not a boundary against a malicious crew (see above), so a program a crew runs is limited only by the sandbox, and that still lets it read a provider's whole login dir. This has been checked against the rule and the settings, not in a live run.

## Third-party sources, lessons and review results

Studio fetches a referenced source with `core.hooksPath=/dev/null` and `core.symlinks=false` and only reads it as text: it runs no install step, script or hook of a source. A candidate update stays beside the active copy until `studio sources apply` judges it `fits`, which means every file the contract reads is byte-identical to its recorded hash. Studio does not try to judge changed text: any change is `unclear` for a person or the lead to read. The first fetch is taken on trust, so a copied source file is labelled as data in the brief.

Files a crew reads are copied to `briefs/<id>.caps/`, out of its write reach: only what a matching row names, regular files of at most 256 KiB, with no link on the way. A source file failing this reads `skipped:`.

Lessons are crew output and can carry an injection to every later crew of a role. They are stored as proposals, cleaned to one plain line, need the lead's `lessons accept` and are shown in a labelled data block. The role file is reached with no link on any segment.

Title and text of the pull request reach the reviewer only as a file written by Studio at launch, marked as crew text to read as data, with control characters removed and the text cut to 20,000 characters; the brief names the file, never its content. A builder's `not_run_here` list (commands a missing service kept from running in its sandbox) is crew text as well: each field is one plain line by the report schema, format characters (bidi overrides, zero-width) are stripped, and it reaches the pull request body in a fenced block below Studio's own lines and the reviewer as `pull-request/not-run-here.txt`, labelled as data. `collect` prints only the count and the missing services. It never weakens a gate: an approval still needs green checks, and a skipped check that is not required counts as green there, so the reviewer names for each command the job at the base that runs it and states why that job covers the command (`covers`, one plain line, format characters stripped, at most 300 characters), and `collect` refuses the approval unless that job's check passed on the pull request. The reviewer reads workflows at the base, not in the head the crew wrote, and `collect` checks each named job in the owner's checkout at the pull request's base commit (`baseRefOid`) and at its head: the job is in the named file with no `if:` or `continue-on-error`; the file either runs on `pull_request`, or is a reusable workflow (`workflow_call`) that a job of a `pull_request` workflow calls with `uses: ./.github/workflows/<file>`, that calling job also without `if:` or `continue-on-error`; the workflow whose name the checks carry (the caller's, for a reusable workflow) has a name no other workflow file shares; the check names are the same at the base and at the head; the job's definition, with its calling jobs, is the same at both unless the item is a CI item; and every check of that job passed, `<job>` or `<caller job> / <job>`, each matrix leg ` (<leg>)` included (the leg is everything inside the outer parentheses), skipped, cancelled and missing counting as not passed. A check of that workflow whose name starts with the expected name and a space but does not parse as it (`<job> (1) / x`, `<job> / x`, `<job> (1`) refuses the gate, at collect and before the merge, rather than being dropped from "every check passed". The jobs are stored with the approval and checked again before the merge. What the gate proves is that the named job ran unchanged on the pull request and passed. Whether it covers the command is the reviewer's judgement, recorded in `covers` and shown to the lead by `collect` as reviewer text; no test of the job's steps backs it, because task runners (`turbo`, `nextest`, `make`) hide the command from any text check, and an earlier run-step test gave false assurance. Limits: one level of reusable workflows only; a job that calls a further reusable workflow, a file called only through another reusable workflow, and a remote `uses: <owner>/<repo>/...@<ref>` are refused rather than followed; a calling job with a matrix reports checks the gate does not match, so it is refused as missing; checks are matched by workflow name, which is why a name two workflow files share is refused. A change under `.github/` blocks the approval unless the item holding the pull request declares the changed path in its `paths` or `touches` (a symbolic link at `.github` or below always counts); launch reads the change in the owner's checkout with `git diff --name-only --no-renames <base>...<head>`, counts a symbolic link at `.github` or below, and counts a change it cannot read as one. Limit: the base workflows run the pull request's own code, so `package.json` scripts, test configuration and build files from the pull request still decide what a named job actually does; the gate shows that a base job ran and passed, not what it ran or that it tested what it should. That part stays with the reviewer and with branch protection. The checks the reviewer sees are a snapshot at launch, so `collect` reads them again and refuses an approval unless they pass. A review report is untrusted too. A reviewer loads the pull request into its clone, so a pull request could carry a report file: each launch draws a random 128-bit report name, known only to that crew's brief, and `collect` reads only that name. The report stays inside the clone, because the guard allows crew writes nowhere else. A verdict must name the pull request's head (`head_sha`). `collect` takes the pull request a verdict acts on from the record written at launch, not from the report, and prints analyzer ids, never reasons. Paths from a pull request are matched but never written into a brief. Limit: GitHub reports a renamed file under its new name, so a rename out of a sensitive folder alone does not turn the security analyzer on; the diff review still sees it.
